# Roadmap и спецификация

## Архитектура (кратко)

Три канала входа — Telegram-бот (голос+текст), Tasker→Google Assistant relay,
Telegram Mini App — сходятся в единый backend-оркестратор. Там Groq
транскрибирует голос, Claude Haiku решает, какой сценарий это, и либо
обрабатывает сам, либо эскалирует на Sonnet для сложных задач. Дальше —
хендлер конкретного сценария, который читает/пишет в Notion и в
Postgres/Redis.

**UI: 4 кнопки-режима** (Задача / Заметка / Вопрос / Напоминалка) —
постоянная reply-клавиатура в Telegram. Тап → бот спрашивает содержимое →
следующее сообщение идёт напрямую в нужный хендлер без обращения к
classify_intent (экономия). Без кнопки — свободный ввод по-прежнему
классифицируется автоматически тем же Haiku, на тот же набор из 4 intent'ов.

## Notion: базы данных

Tasks и Habits с Phase 10 больше не в Notion — см. раздел ниже. Остались
только Notes и Diary: пишутся редко и выигрывают от родного мобильного
редактора Notion для длинного текста.

**Notes** — Name (title), Content (text)

**Diary** — Name, Date, Physical/Social/Productivity/Happiness (number,
1-3), Highlight, Reflection, Summary (авто от Claude, только если
пользователь реально что-то написал в Highlight/Reflection)

Важно: используем свойства базы данных (не текстовые чек-листы внутри
страницы) — так остаётся возможность добавить автоматизации позже.

## Напоминалки (не в Notion — в Postgres)

Заменяют изначальный план с Notion-базой Subscriptions. Пользователь
описывает расписание человеческим языком ("в последний день месяца
напомни выбрать кэшбэк", "каждую среду", "раз в 5 дней", "5 сентября",
"когда буду у Пятёрочки") — Claude (Haiku) разбирает в структуру
(`schedule_kind`: once/monthly_day/weekly_day/interval_days/location),
хранится в таблице `reminders`. Время- и дато-based — проверка раз в
день в то же время, что рассылка задач (8:00); location — по вебхуку от
MacroDroid (см. Phase 9/F13), без ожидания расписания. `/reminders` в
слэш-меню — список с кнопками удаления.

## Мультиаккаунт (F14)

Один владелец, несколько своих Telegram-аккаунтов. `/start` от аккаунта,
которого нет в `TELEGRAM_USER_ID` и не сохранён в Postgres
(`authorized_users`) — бот просит пароль (`BOT_ACCESS_PASSWORD`, по
умолчанию "это читинец"). Правильный пароль — аккаунт сохраняется и с
этого момента имеет полный доступ наравне с основным, включая Mini App.
Без разграничения данных по пользователям — это тот же владелец, просто
с другого аккаунта, данные (Notion, напоминалки и т.д.) общие.

## Фазы разработки

### Phase 0 — Skeleton
Repo structure, pyproject (uv), .env.example, Docker Compose (bot, api,
postgres, redis, caddy-stub). aiogram-бот отвечает на /start только для
TELEGRAM_USER_ID.
**Готово когда:** `docker compose up` поднимает всё, /start отвечает.

### Phase 1 — F1 + интеграция с Notion
`notion.py` — обёртка над API (create/update page). STT (Groq) за
интерфейсом. Haiku извлекает title/due date/priority из сообщения.
**Готово когда:** голосовое "задача купить хлеб завтра важно" создаёт запись
в Notion Tasks с нужными полями.

### Phase 2 — LLM-роутинг + F2
Оркестратор: Haiku классифицирует intent → роутинг к хендлеру; Sonnet — для
сложных сценариев. Web search интеграция (нативный tool у Claude API).
**Готово когда:** "подбери аэрогриль до 5000" отдаёт 3-5 вариантов со
ссылками и ценами.

### Phase 3 — pull-синк Notion + Mini App
Входящие Notion webhooks оказались источником постоянных проблем именно в
этой среде разработки (сеть режет туннели, антивирус блокирует ngrok) —
решили не зависеть от публичного URL для синка статусов. Вместо
`/webhooks/notion`: `core/notion_sync.py` тянет все задачи из Notion и
апсертит в Postgres — по расписанию (APScheduler, раз в 10 минут — Mini
App читает только из Postgres, без похода в Notion при каждом открытии,
чтобы список задач подгружался мгновенно) плюс сразу же при мутациях
из самого Mini App (создание/отметка/дата/архивация). Уведомление в
Telegram шлётся, когда плановый синк обнаруживает реальное изменение
статуса. Mini App: список задач + кнопка "выполнено" → обновляет
Postgres и Notion (без изменений, эта часть не зависела от вебхуков).
**Готово когда:** статус, изменённый в Notion, попадает в Telegram при
следующем плановом синке или при открытии Mini App; кнопка "выполнено" в
Mini App синхронна с Notion сразу.

### Phase 4 — Scheduler + F4, F5
APScheduler джобы. aiogram-dialog для многошагового вечернего опроса. Redis
хранит состояние "жду ответ N из M".
**Готово когда:** бот сам присылает утреннюю сводку и вечером задаёт вопросы
дневника.

### Phase 5 — F3, F8 + пересмотр UI (кнопки-режимы, общие напоминалки)
Изначально планировали F7 через Notion-базу Subscriptions — по ходу решили
сделать общую систему напоминалок в Postgres (см. раздел выше) вместо
привязки к подпискам конкретно, и заодно ввели 4 кнопки-режима
(Задача/Заметка/Вопрос/Напоминалка), объединив F2+F3 в один хендлер.
Habits (F8) — через Notion+Mini App, без изменений.
**Готово когда:** рецепт/вопрос отвечает в чат; привычки отмечаются в Mini
App со streak; напоминалка, заданная человеческим языком, сохраняется и
срабатывает по расписанию; `/reminders` показывает и позволяет удалить.

### Phase 6 — F9, F10, F11
**F9**: 1-го числа месяца в 8:00 бот присылает напоминание с гайдом, как
выгрузить CSV-выписку из Т-Банка; пользователь в любой момент шлёт файл
документом (независимо от кнопок-режимов) — Sonnet сама определяет
колонки CSV и считает траты по категориям, топ-статьи, крупные операции.

**F10**: `POST /webhooks/tasker/screen-time` (секрет — заголовок
`X-Tasker-Secret`, сверяется с `TASKER_WEBHOOK_SECRET`) принимает дневной
итог экранного времени, апсертит в Postgres по дате. В 8:00 бот шлёт
сводку за вчера, если данные пришли (тихо пропускает, если Tasker не
сработал — без спама).

**F11**: по воскресеньям в 19:00 бот собирает саммари недели — выполненные
и просроченные задачи (Postgres-кэш), средние оценки и хайлайты дневника,
стрики привычек (оба — напрямую из Notion). Финансы и экранное время в
ревью не входят — у них свои сводки.

**Готово когда:** все три сводки приходят по расписанию корректно.

### Phase 7 — F6, F12
F6 не отдельный сценарий — расширение кнопки "❓ Вопрос" (F2+F3): принимает
текст/голос/фото/PDF, один вызов Sonnet (forced tool-use), ответ — текст +
опциональный файл-приложение (.md/.txt, модель сама решает, нужен ли).
Сразу шлёт "взято в работу", т.к. фото/PDF обрабатываются не мгновенно.

Утренний брифинг (F12) объединяет F5 (задачи) + погоду (Open-Meteo, без
ключа, город — `WEATHER_CITY`) + F8 (привычки со streak) в одно сообщение.
"Дедлайны целей" из исходной идеи убраны — отдельной системы целей в
проекте нет.

**Готово когда:** вопрос с фото/PDF даёт разбор + план подготовки; утренний
брифинг — одно сообщение со всем сразу.

### Phase 8 — Deployment & CI/CD
VPS — Timeweb Cloud (Амстердам/Франкфурт, оплата из России, сервер за
рубежом — нужно для доступа к Telegram/Notion/Claude-прокси). Домен —
reg.ru. HTTPS — уже готовый Caddy (`Caddyfile` теперь читает `DOMAIN` из
`.env`). CI/CD — GitHub Actions (`.github/workflows/deploy.yml`): пуш в
`master` → SSH на сервер → `alembic upgrade head` → `docker compose up
--build -d`.

Пошаговый runbook (аренда VPS, домен, первичная настройка сервера,
перенос `.env`, переключение BotFather/MacroDroid на новый домен,
GitHub-секреты) — в `DEPLOY.md`.

**Готово когда:** бот отвечает на `/start` уже с публичного домена по
HTTPS; `git push` в `master` сам доезжает до сервера без ручных команд.

### Phase 9 — F13: гео-напоминания
Расширение общей системы напоминалок (см. раздел выше) новым
`schedule_kind: "location"`. Место из текста напоминалки геокодируется
через Nominatim (OpenStreetMap, бесплатно). MacroDroid раз в 5 минут шлёт
координаты на `POST /webhooks/tasker/location` (та же проверка секрета,
что у `/screen-time`) — бэкенд сравнивает с сохранёнными точками
(радиус 200 м) и присылает напоминание сразу через отдельный лёгкий
инстанс бота в процессе `api` (`src/core/bot_client.py`). Одноразовые —
сработало и удалилось, как `once`.

**Готово когда:** напоминалка с местом сохраняется с координатами;
вебхук с координатами внутри радиуса присылает напоминание и удаляет
его из списка.

Известное ограничение: Nominatim неоднозначно матчит общие/разговорные
названия мест (проверено живьём — "Кремль, Москва" дал точку в ~15 км от
настоящего Кремля). Для надёжного срабатывания лучше указывать конкретный
адрес, а не общее название.

### Phase 10 — Tasks + Habits: Notion → Postgres

После MVP пересмотрели архитектуру хранения. Notion как источник правды
для задач был самым частым, самым чувствительным к задержке сценарием —
именно из-за него уже пришлось городить Postgres-кэш
(`sync_tasks_from_notion`, раз в 10 минут) и optimistic UI в Mini App,
чтобы приложение открывалось быстро. Плюс адаптивное чтение чужой
Notion-схемы (`select` vs `status` vs `multi_select`) было источником
реальных багов (`TaskStatus` оказался `multi_select`, хотя ожидался
`select`).

Решение — гибрид, не полный переезд: Tasks и Habits переехали на
Postgres как единственный источник правды (Notion для них больше не
используется вообще, ни чтение, ни запись), а Diary и Notes остались в
Notion — пишутся редко и выигрывают от родного мобильного редактора для
длинного текста. Habits зацепили за компанию — кэш и паттерн были уже
почти готовы, объём небольшой.

`Task.notion_page_id` → `Task.id` (свой суррогатный ключ,
`legacy_notion_id` оставлен только для истории), `status: str` →
`done: bool`, добавлено поле `archived: bool` (замена
Notion-свойства `TaskStatus` — новая "корзина"). Новая таблица
`habits`. Существующие привычки перенесены один раз скриптом
`scripts/backfill_habits.py` (сами задачи уже были в Postgres благодаря
старому синку — переносить отдельно не нужно, миграция просто меняет
им форму).

Явное следствие: Notion Tasks/Habits базы стали неиспользуемыми —
доступ к задачам и привычкам теперь только через Telegram-бота и Mini
App, родного Notion-приложения для них больше нет. Осознанный
компромисс, принятый при выборе гибридного варианта.

**Готово когда:** создание/отметка/дата/архивация задачи и отметка
привычки не делают ни одного обращения к Notion API; синк-джоба и
адаптивное чтение Notion-схемы для Tasks/Habits удалены из кода.

## Конфигурация (.env)

См. `.env.example` — источник истины по актуальному списку переменных
(модель Claude/base URL для прокси, ID баз Notion Diary/Notes,
Postgres/Redis). `NOTION_HABITS_DB_ID` используется только разовым
`scripts/backfill_habits.py`, не основным приложением (см. Phase 10).
Раньше список дублировался и здесь, но расходился с реальностью быстрее,
чем обновлялся — не повторяем.
