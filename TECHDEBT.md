## Круговая карусель аналитики — мигание на обычном/быстром свайпе

**Что не так.** Свайп между самой правой и самой левой страницей
аналитики (обе идут по кругу — с последней снова на первую, и
наоборот, см. SPEC.md, Phase 29 item 12) на медленном, "подконтрольном"
пальцем свайпе работает чисто. На обычном/быстром — на долю секунды
видно мигание/пропадание контента, потом всё само нормализуется.

**Что уже пробовали:**

1. **Phase 29** — базовая реализация: два "теневых" дубля страниц по
   краям (`analytics-ai-lead`/`analytics-spheres-trail`), после
   отпускания на дубле — мгновенный (`scrollLeft`, без transition)
   переход на настоящую страницу с тем же содержимым.
2. **Phase 32** — заметили, что нативный `scroll-snap-type` браузера
   иногда ещё доигрывает свою анимацию в момент программной установки
   `scrollLeft` и "спорит" с ней — на время самого прыжка и пару кадров
   после снимали `scroll-snap-type` (класс `.no-snap`).
3. **Phase 33** — снятия `scroll-snap-type` оказалось недостаточно на
   обычном свайпе: судя по всему, к моменту прыжка ещё жив не сам
   snap, а **momentum-скролл** (инерция от пальца) — простое
   присвоение `scrollLeft` его не останавливает. Добавили более
   жёсткий приём: на мгновение переключаем `overflow-x` в `hidden`
   перед установкой `scrollLeft` (физически обрывает недоигранный
   momentum, скроллить уже нечему), потом возвращаем как было.
4. **Проверено (Phase 34)**: пользователь подтвердил, что баг всё ещё
   воспроизводится на обычном свайпе после пункта 3 — то есть и
   момент-хак не докрыл проблему целиком, либо есть ещё один
   конкурирующий источник анимации, который пока не идентифицирован.

**Не проверено:** синтетические `PointerEvent` в автотестах не создают
настоящей momentum-физики (см. также Phase 33 — при попытке
воспроизвести баг через `dispatchEvent`/`scrollTo` в JS момент-эффект
не проявляется вообще, тестировать реально можно только на устройстве)
— значит и итеративно проверять гипотезы без реального телефона под
рукой неэффективно, каждая новая гипотеза требует живого теста
пользователем.

**Где искать в коде:** `src/adapters/miniapp_static/index.html`,
функция `silentJump` и обвязка `analyticsCarousel.addEventListener("scroll", ...)`
рядом с ней (поиск по `no-snap` или `ANALYTICS_REAL_COUNT`).

**Возможные направления, если возвращаться:**
- Отказаться от нативного scroll-snap для этой карусели целиком и
  перейти на ту же архитектуру, что уже работает для месячного
  календаря (Phase 29, item 4) — трек на `transform`, палец двигает
  1:1, без нативной физики скролла вообще (там кругового мигания нет,
  потому что нет конкуренции с нативным скроллом/momentum).
- Слушать `touchend`/`pointerup` на самой карусели и явно гасить
  momentum через `e.preventDefault()`/blocking там, а не постфактум в
  обработчике `scroll`.

## Одноразовый код входа не одноразовый при параллельном вводе — `get`/`delete` неатомарны

**Что не так.** В `src/core/login_codes.py:63-66`:

```python
value = await r.get(key)  # строка 63
if value is None:
    return None
await r.delete(key)  # строка 66
return int(value)
```

`get` и `delete` — две отдельные операции с точкой ожидания между ними. При
двух одновременных `POST /auth/verify` с одним 4-значным кодом: корутина A
выполняет `await r.get(key)` и уступает управление; корутина B успевает
прочитать тот же ключ до того, как A дойдёт до `await r.delete(key)`. Обе
получают непустой `value`, обе возвращают `int(value)` и обе выпускают сессию
— код, объявленный одноразовым в докстринге, аутентифицирует двоих.

**Сценарий отказа (из VR-001):** два одновременных `POST /auth/verify` с одним
и тем же 4-значным кодом в процессе `api`; корутина A прочитала ключ, корутина
B успевает прочитать тот же ключ до того, как A удалит его. Обе авторизуют
пользователя. Для 4-значного кода при переборе это превращает выигранную
гонку в лишнюю сессию.

**Что уже пробовали.** Тест `tests/test_login_codes.py::test_code_is_one_time_use`
зелёный и не может ловить эту ветку: он вызывает `verify_code` последовательно,
а `FakeRedis` (tests/conftest.py:21-69) однопоточен и не моделирует чередование.
Асинхронный код на FakeRedis выполняется последовательно, без реальной
параллельности, поэтому race condition невидима.

**Где искать в коде:** `src/core/login_codes.py:63-66`, `tests/test_login_codes.py::test_code_is_one_time_use`.
Решение: атомарный `GETDEL` в Redis вместо `get`+`delete`.

## Счётчик попыток входа может остаться без TTL и запереть IP навсегда

**Что не так.** В `src/core/login_codes.py:78-80`:

```python
new_count = await r.incr(key)  # строка 78
if new_count == 1:
    await r.expire(key, _VERIFY_WINDOW_SECONDS)  # строка 80
```

TTL ставится отдельной операцией и только на первой попытке. Если между
строками 79 и 80 процесс `api` перезапустится или рвётся соединение с Redis,
`EXPIRE` не выполняется. Ключ `webcode:verify_attempts:<ip>` остаётся в Redis
**без TTL** и никогда его не получит: условие `new_count == 1` больше никогда
не истинно. Счётчик растёт монотонно, и на 20-й попытке `can_attempt_verify`
(строка 72) перестаёт возвращать `True` — пользователь теряет вход в веб-версию
с этого IP навсегда, до ручного удаления ключа из Redis.

**Сценарий отказа (из VR-001):** первая за окно попытка верификации с некоторого
IP; `INCR` выполнен, `EXPIRE` не выполнен (краш/деплой/разрыв соединения в
промежутке); ключ остаётся без TTL; после 20 попыток пользователь от этого IP
навечно заблокирован. Кроме того, `can_attempt_verify` и `record_verify_attempt`
на строках 72-80 — check-then-act; параллельные запросы могут суммарно
превысить лимит в 20.

**Что уже пробовали.** FakeRedis не умеет отказывать, не умеет чередовать и
не переживает рестарт, поэтому ни один из 134 тестов эту race condition не
проходит. Тесты зелёные, поведение неопределённо.

**Где искать в коде:** `src/core/login_codes.py:72-80` (обе функции),
`tests/test_login_codes.py::test_request_cooldown`, `test_verify_rate_limit_per_ip`.
Решение: атомарный `SET` с флагами `NX` (only if not exists) и `EX` (expiry)
вместо `INCR`+`EXPIRE`, или Redis Lua-скрипт/pipeline.

## `tzdata` не объявлена, и на Windows без неё падает планировщик

**Что не так.** `pyproject.toml:17` объявляет `apscheduler>=3.10`, но не
`tzdata`. На Linux `ZoneInfo` берёт системную базу зон, на Windows системной
базы нет — там `zoneinfo` работает только при установленном пакете `tzdata`.
Сейчас `tzdata-2026.3` в `.venv` пользователя есть, но приезжает транзитивно
через `apscheduler → tzlocal`, а не по прямому объявлению в `pyproject.toml`.

**Сценарий отказа (из VR-001):** будущая версия `apscheduler`/`tzlocal`
перестанет тянуть `tzdata` транзитивно; пользователь пересоздаёт `.venv` на
Windows командой из `stack.md`; `tzdata` не ставится; на старте планировщика
`ZoneInfo(settings.timezone)` с дефолтом `"Europe/Moscow"` (src/core/config.py:31)
на `src/scheduler/jobs.py:215` бросает `ZoneInfoNotFoundError` — бот поднимается,
а `_screen_time_digest` и соседние джобы не стартуют. Та же семья багов, что
про транзитивный `anyio` в тестах: зависимость приезжает случайно, а не по
гарантии.

**Что уже пробовали.** Юнит-тесты этого не ловят и не могут: они гоняются на
Linux (`platform linux` в прогоне WO-001), где `tzdata` в системе всегда.
Эмуляция отказа на `ZoneInfo()` требует мока платформы или отключения
системной базы, обычно не делается в ходе.

**Где искать в коде:** `pyproject.toml:17` (секция `[project] dependencies`),
`src/scheduler/jobs.py:215` (`ZoneInfo(settings.timezone)`),
`src/core/config.py:31` (дефолт `timezone`).
Решение: добавить `tzdata` в явные зависимости, в том же разделе с `apscheduler`.

историческому и будущему нестандартному периоду без миграции данных —
`api.py` по-прежнему технически принимает произвольные
`start_date`/`end_date` от Mini App для целей, это больше не проблема.

**Где искать в коде:** `src/adapters/miniapp_static/index.html::

этого дойдут руки:

- Нужна отдельная страница/пункт согласия в Mini App (или в самом
  боте) — сейчас нет ни одного UI-элемента, спрашивающего согласие на

  привязки к `telegram_user_id` тексты задач/заметок сами по себе
  могут быть идентифицирующими (имена, места, специфичные проекты) —
  нужно решить, что именно попадает в "аналитику" (агрегированные
  метрики типа "сколько задач выполняется в срок" — низкий риск;
  сырые тексты задач — высокий риск, вероятно вообще не стоит
  включать в это согласие).
- Дефолт для НОВЫХ пользователей при регистрации и для уже
  СУЩЕСТВУЮЩИХ (аналог `added_at`-бэкфилла Phase 68/70) — по умолчанию,
  скорее всего, `false` (согласие явное opt-in, не opt-out) что для
  новых, что для старых пользователей — юридически безопаснее, хотя
  тут не заменяет консультацию с юристом, если проект когда-нибудь
  выйдет за рамки личного использования.
- Раз данных пока нет — куда именно они пойдут ("аналитика и
  улучшение продукта") тоже не определено предметно: свой дашборд?
  Экспорт разработчику вручную? Нужно решить перед тем, как заводить
  флаг, иначе он повиснет без реального потребителя.

**Где искать в коде:** `src/adapters/public_pages.py::privacy_policy`
(текст политики), `src/models/authorized_user.py` (куда добавлять флаг

## Прокси CLAUDE_BASE_URL — нестабильный невидимый расход токенов на reasoning перед ответом

**Что не так.** Живой прогон Phase 98 (профиль пользователя) нашёл
конкретный, воспроизводимый случай: при увеличении системного промпта
(добавили абзац с контекстом о пользователе — `_profile_context_block`
в `core/prompts.py`) несколько Claude-вызовов через
`CLAUDE_BASE_URL=https://limitdeckai.ru` стали НЕСТАБИЛЬНО упираться в
`max_tokens` с ПУСТЫМ содержимым ответа (`stop_reason="max_tokens"`,
текстовый блок или даже `tool_use` не появлялись вообще), хотя раньше
(с более коротким промптом, без контекста профиля) те же вызовы
стабильно укладывались в тот же бюджет. Замерено живьём: один и тот же
вызов (`suggest_tasks_for_today` с контекстом профиля) один раз
успешно отработал на 42 output_tokens, в другой раз — съел все 500 без
единого символа видимого ответа. Для `aggregate_user_profile`/
`update_user_profile` (длинные, насыщенные инструкцией промпты)
замерено до ~2700 output_tokens на 3-5 предложений видимого текста —
похоже на невидимый reasoning-расход, который прокси не выставляет
отдельным блоком в ответе (`response.content` — просто один пустой или
короткий `TextBlock`, никакого `thinking`-блока), но списывает с того
же `max_tokens`.

**Чем это опасно, если не знать:** код, который интерпретирует "нет
`tool_use` в ответе" или "пустая строка" как легитимный исход (пустой
список предложений, "добавить нечего") — именно так написан практически
весь `claude_client.py` (`if tool_use is None: return []` и т.п.) — молча
проглатывает эту ситуацию как нормальную, а не как сбой. Баг не бросает
исключение, не логируется как ошибка — просто результат выглядит как
"модель ничего не предложила", хотя на деле она не успела ответить.

**Что уже пробовали.** Единственный надёжный фикс, подтверждённый живым
прогоном — щедрый запас `max_tokens` (в Phase 98 подняли с 500-1500 до
4000-6000 для всех промптов, тронутых добавлением контекста профиля, см.
`src/integrations/claude_client.py`). Не найдено способа предсказать
заранее, у какого именно промпта/контекста это проявится — похоже,
зависит от содержания промпта, не от его длины напрямую (короткие
тестовые промпты тоже иногда проявляли эффект, иногда нет).

**Что делать, если встретится снова:** если новый/изменённый
Claude-вызов (особенно с длинным/насыщенным системным промптом)
начинает стабильно возвращать пустые/неожиданно скудные результаты —
первым делом проверить `response.stop_reason` и `response.usage.output_tokens`
напрямую (не через готовую обёртку функции) — если `stop_reason ==
"max_tokens"` при пустом/урезанном содержимом, щедро поднять
`max_tokens` и повторить вживую несколько раз (эффект нестабильный,
один удачный прогон ничего не доказывает).

**Где искать в коде:** `src/integrations/claude_client.py` (сами
вызовы с комментариями у каждого изменённого `max_tokens`, Phase 98),
`CLAUDE.md` (уже отмечает другие ограничения этого прокси — нет
`web_search`, обязательны `name`+`input_schema` у тулов).

## Прокси CLAUDE_BASE_URL — forced tool_choice сейчас отбивает 400 (новый сбой, обнаружен в Phase 99)

**Что не так.** При живой проверке Phase 99 (`analyze_chat_batch`)
обнаружено: ЛЮБОЙ вызов с `tool_choice={"type": "tool", "name": ...}`

`anthropic.BadRequestError: Error code: 400 - {'type': 'error',
'error': {'type': 'invalid_request_error', 'message': 'The upstream
service rejected the request'}}`. Проверено и локально, и прямо на
проде (`docker compose exec api`), воспроизводится стабильно (3+ раза
подряд), не зависит от схемы/имени тула — упрощённый тул с одним полем
падает точно так же. `tool_choice={"type": "auto"}` с теми же
`tools=[...]` — работает нормально, модель сама решает вызвать тул.
Обычный вызов без `tools` — тоже работает.

Это НЕ тот же баг, что выше (невидимый расход токенов на reasoning) —
там HTTP-запрос проходил успешно, просто ответ был пустым при
`max_tokens`. Здесь запрос отбивается целиком, до какого-либо ответа.
Похоже на новую, недавнюю регрессию на стороне прокси — живые прогоны
Phase 98 (чуть раньше в той же сессии) получали нормальные
`tool_use`-ответы через `tool_choice={"type": "tool", ...}`.

**Чем это опасно.** Затрагивает ВСЕ существующие ИИ-функции с
forced tool-use одновременно, не только новый код — советы на день,
генерация задач под цели/проекты, triage фидбека, наблюдение за
каналами. Там, где исключение не словлено явным try/except вокруг
конкретного вызова (а не вокруг всего хендлера) — пользователь может
получить невнятную ошибку вместо результата; там, где словлено (как в
`process_batch`) — тихо логируется и просто "не случилось".

**Статус (обновлено 2026-10-18) — временный обход применён.** Два дня
после обнаружения (2026-10-16) проблема не прошла сама — наоборот,
поведение прокси изменилось с явного 400 на молчаливое игнорирование
forced tool_choice (200 OK, но модель просто отвечает текстом, как
будто `tools`/`tool_choice` не передавались вовсе), из-за чего
владелец заметил реальный пользовательский симптом ("задачи не
создаются, всё связанное с апи") — раньше это было выявлено только
тестами, не живым использованием. По просьбе владельца применён
временный обход: **`src/integrations/claude_client.py::call_with_tool`**
— единая обёртка, которую теперь зовут все ~16 мест с forced tool-use
вместо `client.messages.create` напрямую. Она сама подставляет
`tool_choice={"type": "auto"}` и дописывает в системный промпт явное
требование "обязательно вызови инструмент X". Проверено живьём (и
локально, и это именно то, что сейчас задеплоено) — `extract_tasks_fields`,
`analyze_chat_batch`, `triage_feedback` несколько раз подряд реально
вызывают тул и возвращают осмысленный результат.

**Риск, который остаётся:** `tool_choice="auto"` — не гарантия, модель
теоретически может всё равно ответить обычным текстом вместо вызова
тула (менее вероятно с явной инструкцией в промпте, но не исключено) —
в этом случае поведение не хуже, чем было (тот же `if tool_use is
None: ...` фоллбэк).

**Что делать, когда прокси починят:** вернуть forced tool_choice одной
правкой — в `call_with_tool` заменить `tool_choice={"type": "auto"}`
на `{"type": "tool", "name": tool_name}` и убрать дописывание
инструкции в system (либо оставить — не мешает). Все 16 call site'ов
трогать не придётся, они уже зовут только `call_with_tool`. Стоит
также разово написать в поддержку прокси (limitdeckai.ru) с точным
симптомом (forced tool_choice молча игнорируется / раньше отбивал 400,
`{"type": "auto"}` всегда работал) — это всё ещё баг на их стороне,
обход не чинит его в источнике.

**Где искать в коде:** `src/integrations/claude_client.py`
(`call_with_tool` + все функции, которые его зовут).
