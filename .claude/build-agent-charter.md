# Хартия: агент `/build` (мгновенная реализация для владельца)

Предложение/архитектура: https://claude.ai/artifact/8xwZx1gqfuuM2KRKmSrNfA
(§8). Репозиторий: `murat0rr/personal-assistant-bot`
(https://github.com/murat0rr/personal-assistant-bot). Прод-сервер:
`https://shitinez.shop`. Внутренний API — секрет в переменной
окружения `AGENT_WEBHOOK_SECRET`, заголовок `X-Agent-Secret`.

## Другой уровень доверия, чем у агента автофикса

Здесь нет allowlist по размеру/теме — запрос в `build_requests.text`
пришёл от владельца бота (гейт `telegram_user_id` уже применён в
`handlers/f_build.py`, до этой хартии ничего постороннего не
долетает), и после approve он и есть легитимная инструкция, тот же
уровень доверия, что у обычной сессии в Claude Code. Предохранитель —
не allowlist, а explicit approve самого владельца на шаге плана.

## Что делать за один прогон

1. `GET https://shitinez.shop/internal/build/next` — текущий активный
   запрос, если есть (на любой момент времени он максимум один, см.
   `core/build.py::_ACTIVE_STATUSES`). Пусто — прогон ничего не делает,
   выходи.
2. `status == "pending_plan"` — шаг планирования:
   - Прочитай `SPEC.md`, `PLAN.md`, `CLAUDE.md`, релевантные файлы по
     теме запроса — как перед обычной фазой, не гадай по одному
     сообщению.
   - Составь короткий план для Telegram (не для кода): что понял,
     что собираешься менять (файлы/область), нужна ли миграция,
     примерный масштаб, тест-план в одно предложение. Коротко — это
     читает человек с телефона, не ревью диффа.
   - `POST /internal/build/{id}/plan` `{"plan_text": "<план>"}` —
     сам отправляет сообщение с кнопками в Telegram и переводит
     запрос в `awaiting_approval`. Дальше ничего не делай, жди
     следующего прогона.
3. `status == "approved"` — шаг реализации:
   - `PATCH`-подобного перевода в `in_progress` сейчас нет отдельным
     эндпоинтом — просто начинай, финальный статус появится на шаге 4.
   - Полный фазовый цикл проекта, **без укороченного allowlist**:
     реализация (включая миграции, новые эндпоинты, что угодно — план
     уже одобрен) → `pytest` → `ruff check`/`ruff format` → живая
     проверка в докере, если доступен в этой среде (включая реальный
     прогон миграции, если она есть) → запись в `SPEC.md` → `security-review`
     на свой диф как вторая независимая проверка → коммит (без
     спецпрефикса, обычное сообщение фазы, трейлер
     `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`) → пуш
     в `master` (дальше CI на сервере задеплоит сам).
   - Упёрся в то, что требует решения владельца (неоднозначность в
     самом запросе, живая проверка недоступна для чего-то, что реально
     нужно проверить, тесты не сходятся после разумного числа попыток)
     — НЕ гадай и не додумывай масштабные решения за него: см. шаг 4
     со `status="needs_input"`, подробно опиши, чего не хватает.
4. Финал — ОДИН раз, какой бы исход ни был:
   `POST /internal/build/{id}/finish`
   `{"status": "done"|"needs_input"|"failed", "summary": "<для владельца>", "commit_sha": "<hash или null>"}`
   — сам отправит сообщение в Telegram и закроет запрос. `summary`
   пиши для человека с телефона: что сделано/что проверено, либо что
   именно нужно решить.

## Что всё равно не делать, даже с approve

- Не трогай сам этот конвейер (`src/adapters/internal_api.py`,
  `.claude/*-agent-charter.md`, секреты) в рамках одного `/build` —
  если именно это и есть запрос, он особенно заслуживает твоей
  обычной осторожности с правками затрагивающими безопасность: делай,
  но перепроверяй тщательнее обычного и явно отметь это в финальном
  summary.
- Не форсируй деплой, если живая проверка показала реальную проблему —
  честный `needs_input` лучше тихо заброшенного деплоя.
- Один активный запрос за раз — не начинай второй, пока текущий не в
  терминальном статусе (это и так гарантирует `f_build.py`, но не
  пытайся обойти игнорированием `/internal/build/next`).
