# Спецификация системы

Формальное описание того, что система делает и каким требованиям должна
соответствовать — снимок текущего состояния, а не хронология. Как и
почему дошли до этого состояния (обсуждения, отвергнутые варианты,
разбивка на фазы) — в [`PLAN.md`](PLAN.md), это по-прежнему источник
истины для истории решений. Здесь эта история не повторяется.

Разработка ведётся через Claude Code-сессии (см. `CLAUDE.md` и
`.claude/skills/assistant-dev-workflow/`) — этот документ в первую
очередь для них: следующая сессия, начиная новую фазу, должна суметь
понять систему целиком по нему, не перечитывая весь git log.

## 1. Обзор

Личный Telegram-ассистент для одного пользователя (с опцией пустить
ещё несколько своих аккаунтов через общий пароль, см. F14) — единая
точка входа для задач, заметок, дневника, напоминаний и нескольких
персональных автоматизаций (финансы, экранное время, привычки).
Взаимодействие — голосом или текстом в Telegram, плюс отдельный Mini
App для визуального управления доской задач. Развёрнут на
собственном VPS, без внешних пользователей и без модели монетизации —
нефункциональные требования соответственно рассчитаны на нагрузку
одного человека, не на масштабирование.

## 2. Функциональные требования

### 2.1 Каналы входа

| Канал | Транспорт | Кто дёргает |
|---|---|---|
| Telegram-бот | aiogram long polling | пользователь, голосом или текстом |
| Tasker webhook | `POST /webhooks/tasker/{screen-time,location}` | MacroDroid на телефоне пользователя, по расписанию |
| Mini App | `GET/POST /miniapp/api/*`, статика на `/miniapp/` | тот же пользователь, из Telegram WebView |

Все три канала сходятся на общее хранилище (Postgres/Redis) и общий
слой авторизации (`src/core/auth.py`) — см. §3.1.

### 2.2 Сценарии (F1–F14)

Полные описания и история решений — в `PLAN.md`, §«Фичи v1». Здесь —
краткая сводка того, что каждый ДОЛЖЕН делать сейчас:

| # | Требование |
|---|---|

| — | Сообщение с намерением "заметка" создаёт страницу в Notion Notes без обращения к Claude |

| F5/F12 | В 8:00 бот присылает одно сообщение: задачи на сегодня + погода + привычки без отметки за сегодня |
| F8 | Привычки хранятся в Postgres со streak; пропущенная дневная привычка порождает вечернее напоминание (20:00) |
| F9 | 1-го числа месяца — напоминание с инструкцией; CSV-выписка Т-Банка, присланная документом, разбирается Claude Sonnet на категории трат |

| F11 | По воскресеньям в 19:00 — сводка недели: выполненные/просроченные задачи, средние оценки и хайлайты дневника, стрики привычек |
| F13 | Напоминание с местом геокодируется (Nominatim); `POST /webhooks/tasker/location` раз в ~5 мин сверяет координаты с сохранёнными точками (радиус 200 м) и присылает сработавшие, одноразово |

**Известный пробел:** F8 (привычки) полностью реализован на бэкенде
(`src/core/habits.py`, `/miniapp/api/habits/*`, вечернее напоминание
о пропуске), но нигде не выставлен пользователю — ни команды в боте,
ни разметки в Mini App (`grep habit src/adapters/miniapp_static/index.html`
— пусто). Отметить привычку выполненной сегодня физически неоткуда,
поэтому вечернее напоминание «не забудь отметить привычки» всегда
будет актуально. Нужно либо доделать UI (вероятно в Mini App, тем же
паттерном, что доска задач), либо явно вычеркнуть F8 из v1.

### 2.3 Mini App — доска задач

Не описано в `PLAN.md` (появилось и много раз менялось уже после
Phase 10 несколькими сессиями подряд) — фиксирую здесь как есть.

**Отображение.** Три экрана в горизонтальной карусели — Вчера /
Сегодня / Календарь (неделя, свайпаемая тройками панелей) — плюс
отдельно Инбокс (задачи без даты или просроченные, свёрнут по
умолчанию). Задача в списке показывает: кружок статуса (галочка если
выполнена; булавка, если это событие и не выполнена; иначе пусто),
заголовок (жирный, если приоритет "высокий" и не выполнена;
зачёркнутый и тусклый, если выполнена), время — только для
событий и только если не полночь.

- **MA-1.** Порядок задач внутри дня — только ручной
  (`Task.sort_order`, float), не пересчитывается автоматически ни по
  приоритету, ни по статусу выполнения. Новая или перенесённая на
  другой день/группу задача получает наибольший на данный момент
  `sort_order` (эквивалент `time.time()`) — то есть уходит в конец.
- **MA-2.** Список Вчера/Сегодня/дня календаря не делится на
  подгруппы "события/обычные" — сортировка единая, событие может
  располагаться между обычными задачами и наоборот.
- **MA-3.** Горизонтальный свайп с правого края строки (72px "зона")
  открывает шторку с 4 действиями: важность (тумблер), событие
  (тумблер, взаимоисключающий с важностью), дата/время, архивировать.
  Доступно только на экранах Вчера/Сегодня/Календарь — не в Инбоксе
  (там вместо шторки — всегда видимые кнопки даты и корзины).
- **MA-4. Режим переноса.** Долгое нажатие (~450 мс) в любом месте
  списка включает режим редактирования для этого списка:
  - весь остальной интерфейс затемняется и размывается
    (`backdrop-filter`) и становится некликабельным; сам список
    рисуется поверх этого слоя;
  - кружок статуса каждой задачи заменяется ручкой-хватом слева;
    текст показывается полностью, без усечения, без жирности/
    зачёркивания;
  - перетаскивание — сразу с касания ручки, слежение за пальцем
    через `document`, а не через саму ручку (не зависит от
    надёжности `setPointerCapture` в Telegram WebView — см. §5);
  - тап по тексту задачи — инлайн-правка с курсором в точке тапа,
    двойной тап выделяет весь текст;
  - у каждой задачи — кнопка отложенного удаления (тускнеет и
    помечается, реально не удаляется);
  - выход из режима — тап где угодно вне списка (по затемнению);
    в этот момент помеченные на удаление задачи архивируются одним
    batch-запросом (`POST /miniapp/api/tasks/archive-batch`).
  - строка добавления новой задачи — часть списка (последняя
    строка), без ручки, не участвует в перетаскивании; перетаскиваемые
    задачи не могут пройти мимо неё.
- **MA-5.** Черновик текста в любом поле добавления задачи (включая
  необязательную дату у Инбокса) переживает пересборку списка —
  `render()` перестраивает все списки на любое действие в
  приложении, черновик не должен теряться от несвязанного события.
  Кнопка подтверждения добавления неактивна и приглушена, пока поле
  пустое.
- **MA-6.** Фокус на поле ввода снимается программно при свайпе
  карусели Вчера/Сегодня/Календарь на другой экран (карусель
  прокручивается нативно, без `render()`, иначе клавиатура и фокус
  остаются висеть на невидимом экране). При возврате на экран
  повторный фокус не выставляется — только сохранённый черновик.
- **MA-7.** Выделение текста везде в приложении запрещено
  (`user-select: none`) кроме активного поля инлайн-правки —
  одновременно и осознанный UX-выбор, и обход ненадёжного поведения
  Telegram WebView, где долгое нажатие без этого перехватывалось
  нативным выделением текста раньше, чем JS видел начало жеста.

**Шаблонные задачи (Phase 18).** Отдельная коллекция (`task_templates`,
не часть доски) — список готовых формулировок для быстрого заполнения
дня, вызывается значком-звездой слева от кнопки добавления задачи на
экранах Вчера/Сегодня/Календарь (не Инбокс). Открывается в bottom
sheet, переиспользующим тот же затемняющий фон, что и MA-4.

- Тап по шаблону в обычном режиме — мгновенно создаёт задачу с тем же
  `due_date`, что предложила бы строка добавления в списке, откуда
  открыли sheet; сам sheet закрывается.
- Тот же режим переноса, что MA-4 (долгое нажатие в sheet), с тем же
  набором действий (drag/inline-edit/отложенное удаление), только без
  кружка статуса/даты — у шаблона их просто нет.
- `stale_after_days` (по умолчанию 14, не редактируется через UI) —
  подсветка едва заметным тёплым тинтом шаблонов, которыми давно не
  пользовались. Таймер считается от `due_date` задачи, созданной из
  шаблона (не от даты нажатия), никогда не показывается числом.
- Раз в неделю (воскресенье, 09:00) `_suggest_templates_job` смотрит
  на заголовки задач за 7 дней и предлагает Claude Haiku 0-3 новых
  шаблона (`source="ai"`), если есть что предложить.
- 8 затравочных шаблонов добавлены миграцией при релизе.

**Проекты (Phase 19).** Своя табличка (`projects`: title, description,
sphere, start_date, end_date, archived), отношение к задачам один ко
многим (`Task.project_id`). Раскрывается собственной свёрнутой по
умолчанию секцией "Проекты" (тот же паттерн, что Инбокс) под доской
задач — карточка показывает сферу (если задана), диапазон дат,
прогресс-бар и счётчик `done/total` по непроигнорированным привязанным
задачам. Создание — инлайн-форма в конце списка (название,
описание, сфера-чипсы, даты). Привязка задачи к проекту — 5-я кнопка
свайп-шторки (после важности/события/даты), открывает bottom sheet
(тот же общий `.bottom-sheet` каркас, что и шаблоны) со списком
проектов + "Без проекта". `Task.sphere` тоже добавлен этой миграцией
(глобальная классификация для будущей аналитики и целей, Phase 20) —
пока выставляется только вручную через `/miniapp/api/tasks/{id}/sphere`
(эндпоинт есть, отдельного UI под него в этой фазе нет).

**Цели (Phase 20).** `goals` (sphere, tier, period_start/end nullable,
text) — 5 тиров: weekly/monthly/quarterly/yearly/5year. Бот сам
инициирует опрос по расписанию: недельные — воскресенье 12:00 (на
предстоящую неделю); месячные — 2 числа 10:00 (текущий месяц);
квартальные — 3 числа 10:00, только в месяцы начала квартала (1/4/7/10);
годовые — 4 числа 10:00, только в январе. Пятилетние — только вручную,
командой `/goals5y` (нет естественной границы периода, которую имело бы
смысл сбрасывать по расписанию). Один общий FSM-опрос
(`src/handlers/f_goals.py`) для всех тиров: инлайн-кнопки 5 сфер (та же
таксономия, что `Task.sphere`/`Project.sphere` — учёба/работа/спорт/
развитие/отношения) + "Готово", по каждой выбранной сфере — один вопрос
свободным текстом, можно повторять по кругу.

- Только weekly и monthly автоматически раскладываются на задачи
  (`generate_tasks_from_goals`, Claude Sonnet, с учётом уже существующих
  задач/активных проектов для дедупликации и авто-привязки
  `project_id`). Задачи создаются **без даты** — уходят в инбокс,
  пользователь сам расставляет их по дням (не ставим дату
  автоматически — ИИ не знает реальной загрузки пользователя на
  конкретный день лучше него самого). Квартальные/годовые/пятилетние —
  только фиксируются для будущей аналитики, задачи из них не создаются
  (явно не просилось в исходных требованиях).
- Только monthly дополнительно предлагает новые проекты
  (`propose_projects_from_goals`, Claude Sonnet) — 0-3 проекта со
  сроками по контексту, только если цель реально тянет на отдельную
  многошаговую инициативу.
- Цели накапливаются (append-only, без апдейта существующих) — повторный
  опрос за тот же период просто добавляет ещё строки; агрегация "самое
  свежее" — на будущей аналитике (Phase 24), в этой фазе Mini App-вьюхи
  под цели нет вообще, только Telegram-опрос + бэкенд.

**Повторяющиеся задачи (Phase 21).** Кнопка "🔁 Повторяющаяся" в главной
клавиатуре бота — свободный текст ("каждый понедельник разгрести
почту"), Claude (переиспользуется `parse_reminder`, та же схема разбора
паттерна, что у напоминалок F13 — `weekly_day`/`monthly_day`/
`interval_days`; `once`/`location` отклоняются с просьбой описать
периодичность) сохраняется как `RecurringTaskRule` (title,
schedule_kind, schedule_value — тот же JSON-паттерн, что `Reminder`).
Никаких задач не создаётся заранее ("миллион записей" из требований) —
ежедневная джоба в 07:00 (до утренней сводки в 08:00) материализует
только сегодняшний occurrence как обычную `Task`-строку для каждого
подходящего под сегодня правила (`last_materialized_date` — защита от
повторной материализации в тот же день, тот же приём, что
`last_fired_date` у напоминалок). Дальше это уже обычная задача — ни
утренняя сводка, ни Mini App не нуждаются в отдельной логике под
повторяющиеся, ровно как и требовалось.

**Ночной разбор инбокса (Phase 22).** `_tidy_inbox_job`, 03:00 (до
материализации повторяющихся в 07:00 и утренней сводки в 08:00) —
берёт текущий Инбокс (та же выборка, что `build_task_board`), одним
batched-вызовом Claude Haiku (`tidy_task_titles`) просит причесать
заголовки (опечатки/лишние слова/невнятность), не меняя смысл.
Обновляет только реально изменившиеся заголовки (`changed=true` и
текст отличается) и присылает сводку "было → стало" в Telegram — тихая
ночь без правок ничего не шлёт.

**Совет по задачам на сегодня (Phase 23).** Отдельным сообщением сразу
после утренней сводки (08:00, тот же `_morning_digest`) — смотрит на
невыполненное со вчера, уже стоящее на сегодня и весь бездатный инбокс,
и с учётом графика 5/2 по 8 часов (Claude Sonnet, `suggest_tasks_for_today`)
предлагает, что из инбокса стоит подтянуть на сегодня, не перегружая
день. Пустой список — нормальный исход, тогда сообщение не шлётся.
Кнопки "Добавить"/"Не сегодня" под сообщением; выбранные id хранятся в
FSM-данных (не в `callback_data` — список id может не влезть в лимит
Telegram), по "Добавить" — выставляет `due_date` на сегодня выбранным
задачам.

**Аналитика (Phase 24).** Новая секция внизу доски — свайпаемая
карусель из 4 страниц (тот же native scroll-snap паттерн, что у
карусели Вчера/Сегодня/Календарь, контролируемо продублирован под
своими классами `.analytics-*` — см. комментарий в коде, риск трогать
уже отлаженную `.day-carousel` не стоил общего компонента). Все данные
читаются один раз при загрузке, вне обычного optimistic-UI `render()`-
цикла (только для чтения).

1. **Тортик по сферам** (`GET /miniapp/api/analytics/spheres`) — SVG-
   donut (stroke-dasharray, без внешних библиотек) + легенда с
   процентами. Считает все неархивированные задачи со сферой,
   независимо от статуса "готово".
2. **График месяца** (`GET /miniapp/api/analytics/month`) — bar-chart
   выполненных задач по дням текущего месяца + компактный список
   "по проектам" (суммарно за месяц) под ним — не отдельный
   полноценный график наложением, а текстовая разбивка ради простоты.
3. **Гант по проектам** — переиспользует уже загруженные `projectsData`
   (тот же `GET /miniapp/api/projects`, что раздел "Проекты", отдельный
   эндпоинт не заводили), горизонтальные полосы по `start_date`/
   `end_date`, с оверлеем прогресса (`done_count`/`task_count`) внутри
   полосы. Проекты без обеих дат в гант не попадают.
4. **ИИ-аналитика** (`GET /miniapp/api/analytics/summary`) — Claude
   Sonnet (`analyze_productivity`), обычный текст (не forced tool-use)
   по агрегатам выше: 2-3 наблюдения, что хорошо/что настораживает.
   Считается заново при каждом открытии Mini App (кэша нет — личный
   низкочастотный трафик, цена пересчёта признана приемлемой).

**Кнопка меню чата.** `MINIAPP_URL` (`.env`) → `bot.set_chat_menu_button`
при старте (`telegram_bot.py::main`) — заменяет иконку "/" рядом с
полем ввода на прямой запуск боевого `/miniapp/`, виден сразу в строке
чата в списке чатов, без `/start` и без похода в меню команд. Пусто =
кнопку не трогаем, в лог — предупреждение.

**Главный и расширенный экран (Phase 25).** Доска разделена на два
полноэкранных `.app-screen` внутри `#screen-stack` — главный (карусель
Вчера/Сегодня/Календарь, Инбокс, утренний дайджест) и расширенный
(Проекты, Аналитика — временно перенесены как есть; полноценный
переключатель целей/проектов в стиле задач — следующий инкремент).
`body`/`html` больше не скроллятся сами — скроллится конкретный видимый
`.app-screen`, тело всегда `overflow:hidden`. Сам `.app-screen` тоже
`overflow:hidden` — скроллится только его дочерний `.screen-content`.
Полоска-переключатель (`.bottom-pill-wrap`) — **последний обычный
элемент внутри `.screen-content`** ("привязана к полотну", не к
экрану/вьюпорту — уточнено в Phase 27): 100vh в Telegram WebView не
всегда совпадает с реально видимой областью (шапка/жесты/полноэкранный
режим), поэтому вариант "прижать к нижнему краю вьюпорта" (`position`
вне потока скролла) на практике оказывался не там, где на самом деле
кончается видимый контент. Простой элемент в конце потока — надёжнее,
всегда сразу после последнего реального блока контента.

- Переход — свайп вверх снизу текущего экрана (тонкая плоская "галочка"
  + подпись, в конце потока контента экрана). Стандартный порог
  активации (70px пальцем, не доля высоты экрана), с отставанием от
  пальца по расстоянию (коэффициент 0.55, не по времени/анимации).
  Держание ~0.5с — вибро (`HapticFeedback.impactOccurred`). Зона старта
  жеста (весь `.bottom-pill-wrap`, `pointerdown`) заметно выше самой
  видимой полоски (`padding-top: 30px`, фон совпадает с фоном экрана —
  зона не видна, полоска визуально не растёт), чтобы свайп
  подхватывался, даже если палец стартует не точно на тонкой "галочке".
- Оба перехода — **одним и тем же направлением** (вверх), не парой
  вверх/вниз: `#main-screen` физически всегда в слоте 0, `#extended-screen`
  в слоте 1; при возврате с расширенного main временно переставляется в
  слот 2 (под extended), чтобы жест "тянул к следующему" естественно, а
  после доезда мгновенно (без transition) возвращается в слот 0 — тот
  же приём, что уже даёт бесшовный бесконечный свайп у недельной
  карусели, только переставляется позиция экрана, а не данные внутри
  него (DOM с обработчиками/id не дублируется).
- Тап по подписи — запасной способ переключиться без свайпа.

**Месячный календарь — переработка, тиры целей (Phase 27).**

- **Свайп между месяцами** — активная зона: вся сетка + надпись месяца
  (`#month-cal-swipe-zone` оборачивает `.month-cal-nav`+`.month-cal-grid`).
  Направление жеста (гор./верт.) определяется по первому заметному сдвигу
  (`touch-action: pan-y`, обычный вертикальный скролл экрана не задет);
  порог 40px — тот же класс "стандартный свайп", что и остальные
  пороговые жесты приложения. Кнопки ‹/› остаются как запасной способ.
- **Нет пустых плиток** — ведущие/хвостовые ячейки сетки заполняются
  реальными числами соседних месяцев (`.other-month`, приглушены), тап
  по такой плитке переключает календарь на этот месяц и сразу выделяет
  день. Первое число текущего месяца — нейтрально-красная обводка
  (`--neutral-red`, обводка, не заливка — чтобы не читалось как
  предупреждение), помогает отличить границу месяца среди чужих чисел
  вокруг.
- **Сегодня/выбран** — та же логика, что у `.week-cell` недельного
  календаря: сегодня — лёгкая заливка акцентом
  (`color-mix(... var(--accent) 18% ...)`), выбран — обводка акцентом;
  оба комбинируются на одной плитке естественно (общий `--accent`).
- **Первая строка** чуть выше остальных (`aspect-ratio: 1/1.32`) —
  вмещает подпись дня недели сверху (как `.wc-label` в недельном
  календаре), отдельной строки-шапки под это не заводим, экономим
  высоту: подпись есть только там, где не повторяется на следующих
  строках.
- **Выходные** — число дня подсвечено приглушённым красным
  (`--neutral-red`), тем же нейтральным тоном, что обводка первого
  числа месяца (разные позиции/семантика — обводка vs заливка текста —
  читаются по-разному, несмотря на общий оттенок).
- **Индикатор "как прошёл день" внутри плитки** — максимум один значок
  на плитку: для сегодня/будущего с задачей-событием — иконка геометки
  (переиспользован существующий `eventPinIcon()`, тот же, что уже
  использовался для чекбоксов событийных задач — не новая метафора для
  приложения); для прошлого с заполненной вечерней рефлексией —
  цветной кружок по среднему баллу `physical`/`social`/`productivity`/
  `happiness` (шкала 1-3, см. `handlers/f4_diary.py`): зелёный ≥2.34,
  жёлтый 1.67-2.33, приглушённо-красный <1.67. Паттерн вдохновлён
  привычными mood-календарями (Daylio и подобные) — один цвет на день,
  без текста, читается с одного взгляда по всему месяцу сразу; дни без
  заполненной рефлексии — просто без кружка, не зашумляем сетку.
  Бэкенд: `core/calendar_view.py::month_diary_moods` (переиспользует
  `list_diary_entries`, тот же маленький датасет без серверной
  фильтрации, что и у `/diary/{date}`), эндпоинт
  `GET /miniapp/api/calendar/month-moods?month=YYYY-MM`.
- **Тап по дню** — сразу докручивает экран так, чтобы надпись месяца
  оказалась вверху видимой области (`scrollIntoView({block:"start"})`
  на секции календаря) — иначе после открытия панели информации о дне
  снизу заголовок мог уйти выше видимой части.
- **Порядок секций расширенного экрана** — графики (Аналитика) теперь
  первыми, затем календарь (+ кнопки создания проекта/цели сразу под
  ним), затем переключатель Проекты/Цели — раньше переключатель шёл
  первым.
- **Тиры целей сокращены до трёх** — `weekly`/`monthly`/`yearly`.
  `quarterly` и `5year` убраны целиком: функция периода `quarter_bounds`
  и тир `quarterly` из `GOAL_TIER_BOUNDS` (`core/goals.py`), крон-джоба
  квартального опроса (`scheduler/jobs.py`), команда `/goals5y` и её
  хендлер (`handlers/f_goals.py`), пункты меню бота
  (`adapters/telegram_bot.py`), страницы/точки переключателя и лейблы
  в Mini App. Старые цели этих тиров в БД не трогали (осознанный выбор
  при подтверждении) — остаются в базе, но недоступны через UI ни в
  боте, ни в Mini App.

**Создание/правка проектов и целей — списочная строка + шторка (Phase
28).** Отдельные кнопки "+ Проект"/"+ Цель" под календарём убраны —
вместо них у каждого списка (Проекты, и у каждого тира целей отдельно)
своя строка добавления внизу, в точности как у списков задач (поле +
"+"). Отличие от задач: тап по "+" не создаёт сущность мгновенно —
открывает уже существующую форму `#create-entity-sheet`, предзаполненную
введённым текстом (и, для цели, тиром той страницы, с которой открыли).

- **Создание = закрытие шторки.** Явной кнопки "Отмена" нет — тап по
  затемнённому фону, свайп вниз (`attachSheetOverswipeClose`, уже был) и
  кнопка "Готово" ведут в одну и ту же `closeCreateEntitySheet()`,
  которая сначала пытается сохранить черновик (`commitEntityForm`),
  потом уже закрывает. Без названия (или без сферы у цели — единственное
  по-настоящему обязательное поле после названия) — просто ничего не
  сохраняется, без алертов: блокирующий `alert` несовместим с закрытием
  свайпом. Цвет проекта — не поле «обязательное для заполнения»: если не
  выбран, при создании назначается случайный из `PROJECT_COLORS`.
- **"Не дозаполнено" — красная подсветка плитки.** Только у проектов
  (реально несколько независимо-необязательных полей — описание, сфера,
  даты); `isEntityIncomplete` — `true`, если не хватает хотя бы одного
  из description/sphere/start_date/end_date. Тонкая красная линия снизу
  плитки (`inset box-shadow`, не меняет высоту строки), не бейдж/число —
  ненавязчиво, замечаешь, только если приглядеться, ровно как и
  задумано. У целей сфера обязательна уже на создании — подсвечивать
  особо нечего.
- **Правка — долгое нажатие по строке** (`attachEntityLongPress`, тот же
  таймер/порог сдвига, что у остальных long-press жестов приложения) —
  открывает ту же форму, предзаполненную текущими значениями,
  `createEntityEditingId` вместо `null`. Правка вызывает
  `POST .../edit` (для целей — новый эндпоинт, для проектов уже
  существовал) вместо `POST` создания; ни при каком редактировании поля
  проекта/цели уже привязанные к нему задачи не трогаются — эндпоинты
  правки меняют только сам проект/цель. Известное ограничение: `null` в
  теле `.../edit` значит "не менять", не "очистить" — конкретное поле,
  однажды заполненное, через эту форму пустым не сделать (можно только
  заменить на другое значение); для создания эта проблема не актуальна.
- **Всплывающий календарь** (`#date-picker-sheet`) — общий для дат
  проекта (начало/конец) и опорной даты периода цели, вместо нативного
  `input[type=date]`: компактная карточка по центру экрана поверх формы
  (не ещё один `.bottom-sheet` той же высоты — перекрывали бы друг
  друга), сетка в той же визуальной логике, что у месячного календаря
  (`.month-cal-day`/`.month-cal-grid`). Кнопка "Не указывать" — явный
  сброс к пустому значению.
- **Опорная дата периода цели** — сервер считает `week_bounds`/
  `month_bounds`/`year_bounds` не всегда от сегодня, а от даты, выбранной
  в этом календаре (`reference_date` в запросе), поэтому можно поставить
  недельную цель на неделю через неделю, месячную — на любой будущий
  (или прошлый) месяц; без выбора — прежнее поведение (от сегодня).
  Правка цели пересчитывает период заново, если поменялся тир и/или
  опорная дата — период не редактируется как отдельное поле, это
  производная величина (см. `core/goals.py::update_goal`).

**Критический баг: режим переноса задач визуально не поднимался над
затемнением (Phase 29).** `#screen-stack` — `position: fixed`, а такой
элемент per спецификации CSS безусловно создаёт собственный stacking
context (независимо от z-index/transform). Из-за этого
`.reorder-active-list` (z-index 26) внутри него не мог подняться выше
`.reorder-scrim` (z-index 25, сам тоже `position: fixed`, но СНАРУЖИ
`#screen-stack`) — список навсегда заперт в контексте предка, будь у
него хоть z-index 9999. Баг тихо появился в Phase 25 вместе со
`#screen-stack` и не был замечен раньше. Единственный настоящий выход —
физически вынести DOM-узел списка за пределы `#screen-stack` на время
режима переноса (`applyReorderElevation` в `renderList`): сохраняет
`getBoundingClientRect()`, вставляет comment-маркер на его место,
переносит узел в `<body>` с `position: fixed` и теми же координатами, а
при выходе — возвращает обратно по маркеру. `templates-list` эта
проблема не касалась — он живёт в `#templates-sheet`, который сам уже
верхнеуровневый `position: fixed` сосед `.reorder-scrim`, а не потомок
`#screen-stack`.

**Баг: переход между главным/расширенным экраном показывал прошлую
прокрутку (Phase 29).** `.screen-content` каждого экрана скроллится
независимо и не сбрасывался при переключении — после скролла вниз на
расширенном экране и возврата свайпом был виден низ, а не верх.
`attachScreenTransition` теперь сбрасывает `scrollTop` целевого экрана
в момент, когда становится ясно, что переключение состоится
(`resetTargetScroll`) — и в свайпе, и в тап-фолбэке (`toggleScreen`).

**Месячный календарь — карусель, текст события, правки (Phase 29).**

- **Свайп привязан к пальцу** — три панели (пред./тек./след. месяц) в

- **Текст события в плитке**, не просто иконка — `month_events` теперь

**Круговой свайп аналитики — мигание на обычном свайпе (Phase 33,
продолжение Phase 32).** Снятия `scroll-snap-type` на время прыжка
оказалось недостаточно на быстром/обычном свайпе — нативный

реальном фликовом свайпе (синтетические `PointerEvent` не создают
настоящей momentum-физики) — логика корректности (индекс/точки)
перепроверена, визуальный эффект от momentum-конфликта нужно
подтвердить на устройстве.

структурно не может возникнуть. Для дня с одним событием подпись
осталась как раньше — заголовок события.

что у `.week-cell.today` (`color-mix(in srgb, var(--accent) 18%,

**Шторка шаблонов поверх окна переноса — само окно оставалось чётким

`#templates-sheet` стал корректно всплывать НАД окном переноса, само
окно переноса за шторкой оставалось полностью резким и активным — по

шаблонов не размывает сам себя.

**Автоочистка чата — молча забывала неудалённые сообщения (Phase 38).**
Разбор жалобы "не работает": `_cleanup_old_messages`
(`src/scheduler/jobs.py`) удаляла строку из `chat_messages` СРАЗУ после
`bot.delete_message`, независимо от того, удалилось ли сообщение в
Telegram на самом деле — `except TelegramBadRequest: pass` глотал любую
ошибку (не только "уже удалено", но и, например, временный сбой сети),
а лог рапортовал `len(old_messages)` — количество КАНДИДАТОВ, не
реально удалённых, так что даже полный провал ночи выглядел в логах как
успех. Данные на проде (336 сообщений, накопленных за не более суток)
подтвердили: сам джоб исправно запускается и обычно чистит успешно —
но при любом единичном сбое сообщение терялось из вида навсегда, без
повторной попытки. Исправлено: строка удаляется из БД только если
`bot.delete_message` реально прошёл, либо если Telegram явно ответил
"нечего удалять/нельзя" — тогда, если сообщение ещё не старше 47 часов
(за 48 часов Telegram сам запрещает удаление, дальше пытаться уже
бессмысленно), строка остаётся на повторную попытку следующей ночью.
Лог теперь пишет `удалено N из M` — реальную, а не оптимистичную
цифру.

**Команда /timezone — часовой пояс и место по геопозиции (Phase 39).**
Раньше часовой пояс (`settings.timezone`) и город для погоды
(`settings.weather_city`) были статичными значениями из `.env` —
поменять можно было только правкой конфига и рестартом. Новая команда
`/timezone` присылает кнопку "📍 Отправить геопозицию"
(`request_location=True`), по полученным координатам:

- `resolve_timezone(lat, lon)` — IANA-имя зоны через тот же провайдер,
  что уже используют цели/аналитика для погоды (Open-Meteo,
  `forecast?timezone=auto` сам резолвит зону по координатам — не
  понадобилась ни отдельная библиотека, ни второй внешний сервис);
- `reverse_geocode_label(lat, lon)` — человекочитаемая подпись
  ("Санкт-Петербург, Россия") через Nominatim reverse, только для
  подтверждающего сообщения, ни на что в логике не влияет.

Оба — новые функции в `src/integrations/geocoding.py`, рядом с
существующим `geocode` (используется гео-напоминаниями, F13).

Результат сохраняется в `authorized_users` (новые нулабельные колонки
`latitude`/`longitude`/`timezone`/`location_label`, миграция
`f1a2b4c6d8e0`) — таблица уже была per-Telegram-user (см. F14, механизм
пароля), просто раньше не хранила ничего, кроме факта авторизации.
Схема уже многопользовательская, но **до полноценной
многопользовательской авторизации (см. TECHDEBT.md) реально влияет на
приложение только запись основного владельца**
(`settings.telegram_user_id`) — остальные авторизованные по паролю
могут сохранить свою геопозицию командой уже сейчас (задел на будущее),
но расписание планировщика и погода бота на неё пока не смотрят; ответ
бота честно об этом предупреждает, а не притворяется, что сработало
полностью.

Когда меняет владелец — эффект применяется сразу, без рестарта
процесса:
- `settings.timezone` (обычный, не frozen, pydantic-объект) мутируется
  прямо в хендлере — все последующие `ZoneInfo(settings.timezone)` по
  всему bot-процессу подхватывают новое значение немедленно, без правок
  в каждом месте использования.
- Планировщик — сложнее: `CronTrigger` без явного `timezone=` резолвит
  зону ОДИН РАЗ в момент создания триггера (не держит живую ссылку на
  `scheduler.timezone`), так что просто поменять
  `scheduler.timezone` задним числом ничего не даёт. `setup_scheduler`
  переписан на декларативный список джобов (`_job_specs`, единый
  источник правды — раньше расписание было только внутри
  `setup_scheduler`, теперь ещё используется `reschedule_for_timezone`,
  которая для каждого джоба вызывает `scheduler.reschedule_job(id,
  trigger=CronTrigger(..., timezone=new_tz))`); каждому джобу присвоен
  стабильный явный `id` — раньше не было, был не нужен, теперь
  необходим, чтобы reschedule_job понимал, какой именно джоб трогать.
- `src/core/user_location.py::apply_stored_timezone()` — вызывается на
  старте и bot-, и api-процесса (`FastAPI`-`lifespan`, не устаревший
  `on_event("startup")`), подтягивает то, что уже сохранено в БД,
  поверх дефолта из `.env`. Bot и api — разные процессы с разной
  памятью, у каждого свой `settings`; если `/timezone` сработала без
  последующего деплоя — api-процесс увидит новое значение только после
  своего следующего рестарта (в этом проекте деплой перезапускает оба
  контейнера сразу, так что расхождение живёт недолго).
- Погода (`src/integrations/weather.py::get_weather_summary`) —
  сохранённые координаты владельца теперь приоритетнее
  `settings.weather_city`: точнее (конкретная точка, а не центр города
  по имени) и не нужен лишний geocoding-запрос на каждый вызов
  дайджеста. Без сохранённой геопозиции — прежнее поведение
  (`weather_city` → Open-Meteo geocoding → forecast) не тронуто.

**Ревизия безопасности (Phase 39, по прямому запросу).** Прошлись по
приложению целенаправленно на инъекции и типовые базовые атаки — не
переписывание "для красоты" (расплывчатое "оптимизируй код, нужна
гибкая красивая система" без конкретики оставлено как есть, не наврежу
догадками; если нужен код-ревью/рефакторинг — это отдельная,
самостоятельная задача, не часть этой правки).

- **SQL-инъекции — не обнаружены.** Весь проект систематически ходит в
  БД через SQLAlchemy ORM/query builder (параметризованные запросы), ни
  одного `execute(f"...")`/ручной подстановки значений в SQL-строку не
  нашлось (проверено `grep` по всему `src/`).
- **Хранимый XSS в Mini App — найден и закрыт.** Большинство мест и так
  рендерят пользовательский текст (заголовки задач/проектов/целей)
  безопасно, через `.textContent` (браузер экранирует сам). Но там, где
  разметка собирается одним HTML-блоком через шаблонную строку
  (график "по проектам" в аналитике месяца, гант, легенда сфер, ИИ-
  текст, ревью дня из дневника) — заголовки/текст подставлялись в
  `innerHTML` НЕ экранированными: заголовок проекта вроде
  `<img src=x onerror=...>` выполнился бы прямо в интерфейсе. Заведён
  общий `escapeHtml(str)` (index.html, рядом с `icon()`) — через
  `textContent` временного `<div>`, тот же принцип, что уже
  подразумевали безопасные места, просто явно; применён во всех
  найденных местах. Раньше в одном месте (ИИ-текст) было временное
  `replace(/</g, "&lt;")` — неполное (не экранировало `&`/`>`/кавычки)
  — заменено на общий helper.
- **`sphere` — принимался API без проверки, теперь валидируется.**
  Фронтенд предлагает `sphere` только как закрытый список кнопок
  (`SPHERES` в index.html), но само API (`CreateProjectRequest`,
  `SetTaskSphereRequest`, `EditProjectRequest`, `CreateGoalRequest`,
  `EditGoalRequest`) принимало в этом поле любую строку — прямой запрос
  с валидной подписью initData мог записать в БД что угодно, включая
  HTML/скрипт (который до предыдущего пункта ещё и рендерился бы без
  экранирования — двойная дыра на одной и той же точке входа). Добавлен
  `SphereField`/`RequiredSphereField` (`Annotated[str | None,
  AfterValidator(_validate_sphere)]`) — Pydantic отклоняет запрос
  (422) до того, как значение вообще попадёт в код эндпоинта. Экранирование
  вывода (пункт выше) всё равно остаётся первой линией защиты — эта
  проверка не даёт мусору попасть в БД вообще, а не только не даёт ему
  отрендериться.
- **Сравнение пароля бота — не постоянное время, поправлено.**
  `handle_password_attempt` (`src/handlers/f_auth.py`) сравнивало
  введённый пароль с ожидаемым обычным `!=` — теоретическая утечка по
  времени ответа (чем раньше несовпадение, тем быстрее ответ). Заменено
  на `secrets.compare_digest`, тот же приём, что уже используют секрет
  вебхуков Tasker (`_verify_secret`) и HMAC-проверка `initData`
  Mini App (`verify_miniapp_init_data`, оба были и остаются корректны —
  проверено отдельно, менять было нечего).
- **Проверено и подтверждено корректным, без изменений:**
  `verify_miniapp_init_data` (`src/core/telegram_auth.py`) — валидный
  HMAC-SHA256 по официальному алгоритму Telegram, `hmac.compare_digest`,
  проверка свежести `auth_date`; вебхуки Tasker
  (`src/adapters/tasker_webhook.py::_verify_secret`) — секрет через
  заголовок, `secrets.compare_digest`, 401 при отсутствии/несовпадении.
- **Найдено, не тронуто (не относится к безопасности):**
  `settings.notion_webhook_secret` объявлен в `config.py`, но нигде не
  используется — вебхука от Notion в коде нет (возможно, был
  запланирован и не реализован, либо убран без чистки конфига). Не
  критично и не риск (нечего эксплуатировать без самого эндпоинта), но
  стоит иметь в виду при следующей уборке конфигурации.

## Phase 40 — многопользовательская авторизация

Самая крупная архитектурная работа за всю историю проекта — обсуждена и
согласована с пользователем заранее (два открытых вопроса — судьба
дневника/заметок и посуточность расписания — заданы явно, ответы ниже),
реализована целиком за одну фазу. До этой фазы `AuthorizedUser`/
`is_authorized` (F14) были только пароль-гейтом: кто угодно, кто знает
пароль ("это читинец", не изменился), получал доступ к боту, но все
авторизованные видели и правили ОДИН общий набор данных, а расписание
всегда слало сообщения только основному владельцу
(`settings.telegram_user_id`). Теперь у каждого авторизованного —
свои задачи/привычки/проекты/цели/напоминалки/шаблоны/повторяющиеся
задачи и своё персональное расписание.

### Данные

`user_id: BigInteger` (FK → `authorized_users.telegram_user_id`) —
добавлен на `tasks`/`habits`/`projects`/`goals`/`reminders`/
`task_templates`/`recurring_task_rules` одной миграцией
(`a7c3e9f1b2d4`). Существующие строки бэкофиллены владельцем — ничего
не потерялось, просто стало явно "моим". Миграция сама гарантирует
строку владельца в `authorized_users` перед бэкофиллом (`INSERT ...
ON CONFLICT DO NOTHING`) — раньше `is_authorized` пускала его в обход
этой таблицы (см. ниже), строки там могло не быть вовсе, а без неё FK
не встал бы. Отдельная миграция (`b8d4f2a6c1e3`) переводит
`chat_messages` на составной первичный ключ `(chat_id, message_id)` —
`message_id` уникален только внутри одного чата, не глобально; с
несколькими чатами (несколько пользователей) старый PK рисковал
столкновением между разными людьми. Обе миграции проверены
upgrade+downgrade+повторный upgrade на временном Postgres, плюс полный
прогон всей цепочки миграций с нуля.

Каждая репозиторная функция (`src/core/projects.py`, `goals.py`,
`habits.py`, `task_templates.py`, `recurring_tasks.py`, `analytics.py`,
`calendar_view.py`) и каждый эндпоинт `api.py` теперь принимает/
фильтрует по `user_id` первым параметром. Точечные мутации по id
(`archive_project`, `set_goal_done` и т.д.) — не просто
`session.get(Model, id)`, а `_get_owned(session, id, user_id)`:
запись, принадлежащая другому пользователю, отвечает тем же
`ValueError`/404, что и несуществующая — угаданный/подсмотренный
чужой id не даёт ни доступа, ни даже подтверждения, что что-то по
такому id вообще существует. Batch-операции (`archive_templates_batch`,
`/tasks/archive-batch`) — `user_id` прямо в SQL `WHERE`, не только
`id.in_(ids)`, той же причины ради. Проверено сценарием: владелец не
может архивировать проект другого авторизованного пользователя даже
зная его id (см. живой прогон ниже).

### Личность пользователя — откуда берётся `user_id`

- **Mini App API** — `get_authorized_user` уже резолвил личность из
  подписанного `initData` и раньше (HMAC-SHA256, см. Phase 39), просто
  возвращаемый `user["id"]` до этой фазы никуда не прокидывался
  дальше `_: dict = Depends(...)`. Никакой новой инфраструктуры не
  понадобилось — только реально начать использовать то, что уже было.
- **Бот** — `message.from_user.id`/`callback.from_user.id` напрямую в
  каждом хендлере, который раньше слал/писал от имени
  `settings.telegram_user_id`.
- **Планировщик** — свой контекст, нет входящего сообщения; `user_id`
  приходит как аргумент джобы (см. ниже).

### Планировщик — свои джобы у каждого

Обсуждён и подтверждён явно: расписание учитывает часовой пояс каждого
пользователя индивидуально (не общее время для всех). `setup_scheduler`
стал `async` — на старте перебирает `list_authorized_user_ids()` и
регистрирует персональный набор джобов на каждого через
`register_jobs_for_user`. `_job_specs(bot, storage, user_id, tz_name)`
— единый источник правды расписания (было и в Phase 39, теперь
дополнительно параметризован пользователем и его зоной); каждый job id
включает `user_id` (`f"morning_digest:{user_id}"`) — раньше на имя
джобы был один экземпляр на всё приложение, теперь по одному на
пользователя, id должны быть уникальны в рамках `AsyncIOScheduler`.

Три джобы — `screen_time_digest`, `finance_reminder`, `evening_diary`
— регистрируются **только для владельца**, не для каждого: они
завязаны на что-то физически единственное (конкретный телефон с
MacroDroid, конкретный банк/выписка, Notion-дневник одного воркспейса)
— не "ещё не доделано", осознанное ограничение (см. TECHDEBT.md).

Новый пользователь получает свои джобы СРАЗУ при вводе пароля
(`register_jobs_for_user` в `f_auth.py`), без рестарта процесса — та
же логика, что уже делает `/timezone` (Phase 39) для пересборки
триггеров. `/timezone` тоже стала полностью многопользовательской:
`reschedule_for_timezone` теперь принимает `user_id` и пересобирает
триггеры ТОЛЬКО его личных джобов — раньше эффективно работала только
для владельца, для остальных честно отвечала "сохранил, но не
влияет"; теперь влияет на каждого одинаково. `settings.timezone`
(глобальная мутация, см. Phase 39) остаётся только как дефолт для
владельца и для мест, ещё не ставших per-user — `user_timezone(user_id)`/
`user_today(user_id)` (новые хелперы, `src/core/user_location.py`) —
основной способ узнать "чей сейчас день" где угодно в коде.

### Онбординг

`src/core/onboarding.py::seed_onboarding_data(user_id, today)` —
вызывается сразу после успешного пароля для НОВОГО пользователя
(проверка "не является ли повторным вводом пароля уже авторизованным"
— не пересоздаёт затравку и джобы заново при, например, зависшем
FSM-состоянии). Создаёт: один шаблон ("Разобрать почту"), один
пробный проект, одну пробную цель (тир weekly, сфера "развитие"), две
задачи — одна привязана к проекту (`project_id`), другая — к цели
(через совпадение `sphere`, тот же принцип связи "задача относится к
цели", что и везде в приложении — отдельного `goal_id` у задачи нет).
Дальше — приветственное сообщение с рекомендацией заглянуть в
«Помощь» (Phase 37) для знакомства с жестами.

### Дневник и заметки — осознанно остаются только у владельца

Явный вопрос пользователю, явный ответ: дневник и заметки живут в
Notion, привязанном к ОДНОМУ конкретному воркспейсу/токену, не к
Telegram-пользователю — интегрировать туда несколько независимых
людей нет разумного способа без полной миграции с Notion на Postgres
(отдельная, самостоятельная задача, не часть этой фазы). Пока —
честно "не готово", не тихая пустота:
- Mini App: `api.py::_is_owner`/`_NOT_READY_FOR_OTHERS` — дневник
  (`GET /diary/{date}`) отвечает 403 с понятным текстом для не-владельца;
  индикатор настроения в месячном календаре (`month-moods`) — просто
  пустая карта (плитки не подсвечиваются, без ошибки).
- Бот: `f_notes.py::handle_note` — то же сообщение для не-владельца
  ДО похода в Notion. `f4_diary.py` (вечерний опрос) не тронут вообще
  — просто не регистрируется джобой ни для кого, кроме владельца (см.
  выше), поэтому и трогать нечего.
- Планировщик: `f11_weekly_review.py::build_weekly_review` — раздел
  дневника в итогах недели пустой для не-владельца (`is_owner`
  проверка перед походом в Notion), раздел задач/привычек — как у всех.

Гео-напоминания (`f_reminders.py::check_location_reminders`) — та же
логика, что экранное время: вебхук от Tasker/MacroDroid привязан к
ОДНОМУ конкретному физическому телефону, не абстрактному "текущему
пользователю" — фильтр по `Reminder.user_id == settings.telegram_user_id`
прямо в самой функции, а не через регистрацию джобы (это не джоба
планировщика — вебхук, дёргается извне).

### Побочные находки по дороге

- **Владелец должен быть реальной строкой в `authorized_users`.**
  `_is_primary_owner`/обход БД в `is_authorized` — сохранён (устойчивость
  входа к временно недоступному Postgres), но данные теперь ссылаются
  на эту таблицу по FK, так что `ensure_owner_authorized()` (новое,
  `core/auth.py`) вызывается на старте bot- и api-процессов, гарантируя
  строку идемпотентно.
- **`ChatMessage` PK был потенциальной дырой на многопользовательность**
  (см. миграцию `b8d4f2a6c1e3` выше) — найдено при проектировании
  per-user автоочистки чата, не было бы обнаружено без явной
  многопользовательской работы.
- **Погода стала per-user** (`weather.py::get_weather_summary(user_id)`)
  — естественное следствие того, что `/timezone` (Phase 39) уже хранила
  геопозицию по `user_id`, просто раньше только владельца это
  использовало.
- **Frontend (Mini App) не потребовал ни единой правки** — вся
  многопользовательская логика на сервере, `initData` уже нёс личность
  пользователя с самого начала (Phase 29), фронтенду прозрачно, чьи
  данные он показывает.

### Живой прогон (перед деплоем, на временном Postgres)

Полная цепочка миграций с нуля; `ensure_owner_authorized` + `setup_scheduler`
на пустой БД → 14 джобов (11 общих + 3 владельца). Симуляция нового
пользователя: вставка строки в `authorized_users`, `seed_onboarding_data`,
повторный `setup_scheduler` → 25 джобов всего, 14 у владельца, 11 у
нового пользователя (без владельческих трёх) — id пересчитаны верно.
Проверка изоляции: `list_projects(new_user_id)` не видит проектов
владельца и наоборот; попытка `archive_project(чужой_project_id, owner_id)`
корректно отклонена `ValueError` вместо тихого успеха.

### 2.4 Безопасность и доступ (функционально)

- Бот отвечает только пользователю из `TELEGRAM_USER_ID` либо
  сохранённому в `authorized_users` (см. F14); остальным — вежливый
  отказ без раскрытия функциональности.
- Оба вебхука от Tasker (`/screen-time`, `/location`) и Mini App API
  требуют собственной проверки перед обработкой payload (см. §3.1).

## Phase 41 — аналитика и календарь: список правок

Пять точечных улучшений Mini App по итогам живого использования (все —
одним списком от пользователя, без предварительного обсуждения плана,
т.к. каждый пункт мал и локален).

### График месяца — все проекты, светлее выходные, листание

`month_breakdown` (`src/core/analytics.py`) переписан: раньше отдавал
только `all_counts` (без разбивки по проектам, без параметра месяца —
всегда "текущий"). Теперь принимает `month_anchor` (любая дата
интересующего месяца) и возвращает разбивку по **каждому активному
проекту**, включая те, где в этом месяце ноль выполненного (нулевая
строка не пропускается — раньше проект без прогресса просто не
попадал бы в список, что выглядело бы как "проекта не существует", а
не как "в этом месяце по нему ничего не сделано"), плюс отдельная
строка "Без проекта" для задач без `project_id`. Эндпоинт
`GET /miniapp/api/analytics/month` получил необязательный параметр
`?month=YYYY-MM` — без него ведёт себя как раньше (текущий месяц).

Фронтенд (`renderMonthChart`) красит бары выходных дней с
`opacity: 0.5` (вычисляется через `new Date(Date.UTC(...)).getUTCDay()`
от `data.year`/`data.month`, не от индекса дня — корректно даже если
месяц начинается не с понедельника). Добавлена навигация `‹ месяц год
›` (`goToAnalyticsMonth`) и свайп по самому графику
(`attachMonthChartSwipe`, порог 40px по X при преобладании над Y).

**Баг, пойманный на живой проверке (не гипотетический — реально
воспроизводился):** `renderMonthChart` строила разметку через
`el.innerHTML = ...` для заголовка+навигации, сразу вешала `.onclick`
на кнопки ‹/›, а ПОТОМ дорисовывала SVG-график и список проектов через
`el.innerHTML += ...`. Присваивание через `+=` — это не "добавить
узлы", а "сериализовать всё текущее содержимое обратно в строку,
приклеить новый кусок и распарсить заново" — при этом заново
создаются ВСЕ узлы внутри `el`, включая уже нарисованные кнопки
навигации, и их `.onclick` слетает молча. Результат: кнопки ‹/›
визуально были на месте и выглядели рабочими, но тап по ним ничего не
делал — при этом прямой вызов `goToAnalyticsMonth()` из консоли
работал прекрасно, что и увело бы от настоящей причины, не будь
проверки через реальный клик по DOM, а не только через вызов функции
напрямую. Исправлено: вся разметка функции собирается в переменные и
`el.innerHTML` присваивается ровно один раз в конце, обработчики
навешиваются после этого единственного присваивания
(`attachMonthNav()`).

Второй баг того же происхождения: `attachMonthChartSwipe(el)` вызывается
из `renderMonthChart` при каждом рендере (в том числе при каждом
листании месяца), а `el` — стабильный узел, не пересоздаётся между
рендерами (только его `innerHTML`). Без защиты `addEventListener`
копился бы с каждым свайпом, и через несколько листаний один жест уже
перескакивал бы через несколько месяцев разом. Исправлено —
`el.dataset.swipeAttached` не даёт слушателям навеситься повторно.

### Диаграмма Ганта — панорамирование пальцем + упаковка по сферам

Раньше диаграмма была статичной: одна полоска на проект, ширина —
процент от экрана. Теперь `GANTT_PX_PER_DAY = 10` — фиксированный
масштаб "пикселей на день", ширина канвы = `totalDays * 10`, шире
экрана. Панорамирование — не самодельная логика перетаскивания (как
у карусели месяцев/недель в другом месте приложения), а нативный
`overflow-x: auto` на обёртке (`.gantt-scroll`) с `-webkit-overflow-
scrolling: touch`: для этой задачи (свободный непрерывный свайп без
snap-to-page) нативный скролл даёт инерцию и отзывчивость "из
коробки" без единой строчки JS-физики. При отрисовке `scrollLeft`
сразу выставляется так, чтобы "сегодня" была по центру видимой
области.

**Упаковка непересекающихся проектов одной сферы в одну строку**
(`packGanttRows`) — жадный алгоритм интервального планирования
("минимум переговорных комнат для непересекающихся встреч"):
группировка по `sphere`, внутри группы сортировка по дате начала,
каждый проект кладётся в первую строку группы, чей последний элемент
уже закончился (`start >= row.lastEnd`), иначе открывается новая
строка. Проекты разных сфер никогда не делят строку, даже если по
времени не пересекаются — сфера сначала, время потом. Проверено на
трёх специально добавленных в `scripts/miniapp_dev_server.py` тестовых
проектах (`_default_projects()`): два проекта сферы "учёба" с
непересекающимися датами корректно легли в одну строку; третий проект
той же сферы, но пересекающийся по времени с первым — получил
отдельную строку, несмотря на совпадение сферы; проект сферы "спорт" —
всегда отдельная строка независимо от пересечения дат с кем угодно.
Все три сценария подтверждены живым чтением DOM после рендера, не
только на глаз.

**Баг, пойманный на живой проверке:** подписи месяцев на оси
(`monthTicks`) вычислялись без проверки расстояния до предыдущей
метки. Если самый ранний проект в диапазоне начинается в последний
день месяца (например, 31 августа — ровно случай тестовых данных),
1-е число ЭТОГО месяца уходит в отрицательный `x` и прижимается к 0
через `Math.max(0, ...)`, а 1-е число СЛЕДУЮЩЕГО месяца оказывается
буквально на расстоянии одного дня (10px) правее — две подписи
рисуются друг на друге, превращаясь в нечитаемую кашу из символов.

всех месяцев радиуса, повторный `ensureMonthData` для уже прогретого
месяца не бьёт по сети.

## Phase 42 — баг: свайп-шторка задач мигала на мыши (desktop)

Жалоба: на компьютере наведение курсора на строку задачи заставляло
шторку с кнопками (важность/событие/дата/проект/архив) мигать шириной,
а осознанный свайп мышью открывал её ненадёжно.

**Причина.** `setupSwipeDrag` (`src/adapters/miniapp_static/index.html`)
слушает `pointermove` на `.swipe-zone` (узкая 72px-полоса у правого
края строки, откуда стартует жест) и на самой открытой шторке
(`.swipe-actions`, свайп вправо закрывает), определяя начало
перетаскивания по накопленному смещению курсора — без проверки,
зажата ли вообще кнопка. На тачскрине это не создавало проблем:
`pointermove` там принципиально не приходит без контакта пальца с
экраном. На мыши `pointermove` сыплется постоянно при любом наведении,
без единого клика — и код принимал обычное движение курсора над зоной
за жест: `startX`/`actionsStartX` при первом наведении ещё нулевые
(или остались от предыдущего клика), из-за чего вычисленное смещение
сразу превышало порог, `dragging` включался, и `setReveal()` начинал
непрерывно перегонять ширину шторки от каждого дрожания мыши —
поскольку `dragging` не сбрасывается назад без настоящего
`pointerup`/`pointercancel` (которых от простого наведения не бывает),
одно случайное прохождение курсора через зону оставляло строку в
"мигающем" состоянии на неопределённое время. К моменту, когда
пользователь действительно начинал осознанный свайп мышью, внутреннее
состояние уже было "замусорено" этим фоновым дрожанием — отсюда и
вторая часть жалобы, ненадёжное открытие.

**Исправление.** В оба `pointermove`-обработчика (`zone` и `actions`)
добавлена проверка `e.buttons !== 1` в самом начале — она отфильтровывает
любое движение указателя без зажатой основной кнопки. Для мыши
`buttons` равен 1 только пока зажата левая кнопка; для тач-контакта
`buttons` тоже равен 1 всё время касания — так что фикс не меняет
поведение жеста на телефоне, только глушит ложные срабатывания от
наведения на десктопе. Проверено синтетическими `PointerEvent`
(`buttons: 0` для имитации наведения — ширина шторки больше не
меняется вообще; `buttons: 1` с полной последовательностью
`pointerdown`→`pointermove`×N→`pointerup` — жест по-прежнему открывает
шторку плавно и полностью, как раньше).

## Phase 43 — баг: задачи в календаре периодически "пропадали"

Повторная жалоба ("опять пропало нормально отображение задач в
календаре") — намёк, что проблема не разовая, а воспроизводится
регулярно. Так и оказалось: не визуальный баг, а рассинхронизация
часовых поясов, дающая о себе знать в определённое время суток.

**Причина.** `GET /miniapp/api/tasks` (и ещё 7 эндпоинтов в
`src/adapters/api.py`) считали "сегодня" через
`datetime.now(ZoneInfo(settings.timezone))` — общую, глобальную
настройку из `.env` (`TIMEZONE`, по умолчанию `Europe/Moscow`), а не
персональный часовой пояс пользователя, который для этого специально
существует с Phase 39/40 (`src/core/user_location.py::user_today`).
Live-проверка на проде: `settings.timezone` действительно так и
остался дефолтным `Europe/Moscow` (UTC+3), при этом ни у одного из 9
авторизованных пользователей, включая владельца, часовой пояс в БД не
задан (`/timezone`, Phase 39, ни разу не вызывалась) — то есть
Phase 40 добавила инфраструктуру per-user часового пояса, но
`api.py` (бэкенд Mini App) забыли на неё перевести, она осталась на
Telegram-хендлерах бота (`f_reminders.py`, `f_goals.py` и т.д.).

Реальный пояс пользователя — UTC+6 (судя по системным данным сессии,
похоже на `Asia/Bishkek`), т.е. на 3 часа впереди `Europe/Moscow`.
Это значит: каждую ночь примерно с 00:00 до 03:00 по местному времени
пользователя сервер всё ещё думает, что "сегодня" — это вчерашний
день (Москва ещё не перевалила через полночь). `boardState.days.today.date`
из этого расчёта используется сразу в нескольких местах фронтенда:
подсветка `.today` в сетке месячного календаря, деление задач на
"вчера"/"сегодня", и — важнее всего — ветвление в `showDayInfo`
(today/будущее → список задач, прошлое → ревью дневника, см. Phase 41).
Если сервер по ошибке считает текущий день уже прошедшим, тап по
сегодняшней дате в календаре показывал бы дневник (для владельца) или
пустоту вместо списка задач — ровно то, что описано как "пропало
отображение задач", и именно в узком ночном окне, а не постоянно —
отсюда и "опять", а не "снова с самого начала".

**Исправление.** `src/adapters/api.py`: все 8 мест, где эндпоинты
Mini App считали "сегодня", переведены на `await user_today(user_id)`
(персональный часовой пояс, с откатом на `settings.timezone`, если
пользователь `/timezone` ни разу не вызывал — поведение не меняется,
пока пояс не задан персонально). Заодно тот же класс бага найден и
исправлен в двух owner-only местах: `f4_diary.py` (граница дня для
записи дневника) и `tasker_webhook.py` (дата экранного времени,
Tasker шлёт итог "за сегодня" без явной даты) — оба переведены на
`user_today(settings.telegram_user_id)`, поскольку обе фичи физически
привязаны к одному владельцу (Phase 40). Не тронуты: два места, где
`settings.timezone` использовался только для поля `added_at` (просто
метка времени создания строки, не граница дня) — там менять нечего.

**Важно: сам по себе код-фикс не переставляет часы прямо сейчас** —
пока ни у кого не задан персональный часовой пояс, `user_today`
откатывается ровно на тот же `settings.timezone`, что и раньше, и
ночное окно рассинхронизации никуда не денется. Чтобы реально
устранить его для себя, владельцу нужно один раз выполнить `/timezone`
в боте (команда уже существует с Phase 39, определяет пояс по
геопозиции автоматически) — тогда `user_today` начнёт использовать
персональный пояс вместо глобального дефолта. Альтернатива —
поправить `TIMEZONE` в `.env` на сервере на фактический пояс
владельца, но это меняет дефолт для всех, кто ещё не задал свой
`/timezone` лично, а не только для владельца.

## Phase 44 — баг: тап по дню в календаре прятал уже показанный список задач

Пользователь уточнил: это НЕ Phase 43 (рассинхронизация часовых
поясов) — отдельная, ранее уже всплывавшая проблема (сформулирована
почти теми же словами, что и требование item 3.1 в Phase 41, где я
ошибочно заключил "уже работает, менять нечего" — не протестировав
именно эту последовательность действий).

**Диагностика.** Бэкенд и сама логика показа списка/дневника оказались
полностью исправны — проверено предельно дотошно, прежде чем искать
дальше: HMAC-подписанный запрос к продовому `/miniapp/api/tasks`
изнутри `api`-контейнера (с настоящим `settings.telegram_bot_token`)
вернул корректные `today`/`dated_tasks` на 85 задач; та же реальная
выдача, скормленная напрямую в **боевой** (побайтово идентичный проду,
проверено `diff`) фронтенд-код в dev-харнессе, рендерила список без
единого исключения, в т.ч. на "мусорных" значениях вроде
`priority: "high priority"`; переключение сегодня → прошлое → сегодня
туда-обратно тоже не ломалось. Это заняло большую часть расследования,
но было не зря: исключило и часовые пояса, и порчу данных, и гонку
в `showDayInfo`/`renderMonthDayDetail`, оставив ровно один
неисследованный путь — саму последовательность тапов.

**Причина.** `loadBoard()` выставляет `calSelectedDay` на сегодняшний
день СРАЗУ при открытии календаря, без единого тапа (item 3, Phase 35)
— список уже показан. Обработчик тапа по плитке при этом переключал:
`calSelectedDay = calSelectedDay === iso ? null : iso` — тап по уже
выбранному дню СВОРАЧИВАЛ список. Ничего на плитке визуально не
объясняет пользователю "этот день уже выбран, повторный тап уберёт
список" — обычная реакция на встречу с календарём — тапнуть по
сегодняшнему числу, "чтобы посмотреть задачи" — и этот самый первый
тап их прятал. Воспроизведено детерминированно: открыть календарь →
список на 12971 символ разметки уже в DOM → один тап по сегодняшней
плитке → `calSelectedDay` в `null`, список пуст.

**Исправление.** Тап по плитке теперь **всегда** устанавливает
`calSelectedDay = iso` — не переключает, только выбирает; повторный
тап по тому же дню — no-op с точки зрения видимости (список остаётся).
Сворачивать список тапом по плитке было решено не за чем: пользы у
этого пути не нашлось, только повод для регрессии. Требование
закреплено в §2 (месячный календарь) отдельным абзацем "Закреплённое
требование", чтобы будущая правка тапа по плитке явно видела, что
именно нельзя тихо сломать в третий раз.

## Phase 45 — вход в веб-версию: код в чате с ботом (три попытки, три разных бага)

До этой фазы приложение открывалось ТОЛЬКО внутри Telegram: единственный
источник личности — подписанный `initData` (`window.Telegram.WebApp.
initData`), а вне Telegram-клиента он пустая строка, и каждый запрос к
`/miniapp/api/*` падал 401 (живьём проверено на `https://shitinez.shop/
miniapp/` в обычном браузере).

Scope явно ограничен пользователем: только телефоны, десктоп-раскладку
не делаем; PWA (`manifest.json`, иконки, service worker), автотёмная
тема (`prefers-color-scheme`) и пересмотр кэш-стратегии — отдельные
более мелкие шаги позже, не блокируют вход.

### Первая попытка — Telegram Login Widget — не заработала, причина вне нашего контроля

Изначально выбрали **Telegram Login Widget** (тот же `telegram_user_id`,
вся мультитенантность Phase 40 работает без правок). Реализация была
технически исправна и подтверждена живьём пошагово: домен зарегистрирован
через `/setdomain` в @BotFather (сам пользователь выполнил, подтверждено
скриншотом переписки), `data-auth-url` — сначала баг (Caddy терминирует
TLS и проксирует внутрь по обычному HTTP, `uvicorn` без `--proxy-headers`
видел только эту внутреннюю схему — `request.base_url` всегда отдавал
`http://`, из-за чего виджет ругался; исправлено добавлением
`--proxy-headers --forwarded-allow-ips="*"` в `docker-compose.yml`),
после чего кнопка виджета корректно отрисовалась.

Дальше уткнулись в то, что чинить было уже не на нашей стороне: сам
Telegram при входе по номеру телефона (когда браузер не залогинен в
Telegram Web) должен прислать код подтверждения — и он **не приходил**,
даже с активной сессией Telegram Web в том же браузере. Долгая совместная
диагностика (Android/iOS попапы, встроенные webview, `FLOOD_WAIT`,
`Cross-Origin-Opener-Policy` — ни один заголовок этого типа на нашей
стороне не стоит, проверено `curl`) не нашла ничего в нашем контроле —
это делегированная Telegram'у часть виджета (`oauth.telegram.org`),
за пределами того, что видит или может исправить наш сервер. Официальная
документация виджета прямо направляет в таких случаях к @BotSupport
(хэштег `#oidc`) — то есть это ожидаемо внешний, не наш баг.

### Вторая попытка — код по username через Bot API — тоже не заработала

Следующая идея: раз человек уже писал боту, боту незачем полагаться на
телефонную верификацию Telegram — он может прислать код сам,
`bot.send_message`. Реализовано через `bot.get_chat(f"@{username}")` —
сайт просит username, резолвит его в `user_id` через Bot API. Живая
проверка сразу после деплоя (реальная попытка входа пользователем)
показала: `getChat("@username")` для обычного приватного пользователя
ненадёжен и отвечает `Bad Request: chat not found`, даже если бот с этим
человеком уже переписывался — подтверждено прямым вызовом с прода тем
же токеном (`docker compose exec api uv run python -c "..."`). Это
ограничение самого Bot API (резолвинг приватных чатов по username не
гарантирован), а не наша ошибка в реализации — но менять пришлось всё
равно, раз сайт не может полагаться на "узнать" пользователя по имени.

### Финальный механизм — инициативу разворачивает не сайт, а сам человек

Раз резолвинг username от сайта к пользователю ненадёжен, а user_id
входящего сообщения боту — надёжен ВСЕГДА (`message.from_user.id`, тот
же источник личности, что у любой другой команды бота), разворачиваем
поток: не сайт ищет человека, а человек сам пишет боту.

**Поток**:
1. Человек пишет боту `/webcode` (`src/handlers/f_web_login.py`,
   зарегистрирован в `telegram_bot.py` перед `orchestrator_router`, как
   и все остальные команды) — `is_authorized(message.from_user.id)`,
   если да — 4-значный код (`src/core/login_codes.py`),
   `message.answer(...)`. Username вообще нигде не участвует, никакого
   похода в Bot API за резолвингом — user_id уже есть, он и есть msg.
   from_user.id.
2. `GET /auth/login` (`src/adapters/web_auth.py`) — один-единственный
   шаг, только поле кода (не два шага, как в версии с username).
3. `POST /auth/verify-code` — прямой lookup по коду, совпадение выдаёт
   ту же сессионную куку, что была с самого начала
   (`src/core/web_session.py`, ни разу не менялся за все три попытки).
4. `POST /auth/logout` — чистит куку.

**`src/core/login_codes.py`** — 4 цифры через `secrets.randbelow`, живут
5 минут, одноразовые. Кулдаун 60 секунд между запросами кода на один
`user_id` — не даёт засыпать свой же чат с ботом кодами при повторных
кликах. Ключ теперь — **сам код**, не username (сайт больше не знает
username вообще), это поменяло модель защиты от перебора: раньше
(username-версия) неверные попытки считались на конкретную запись (5
попыток, потом сгорает) — с прямым lookup по коду это не имеет смысла
(одна попытка = либо код существует, либо нет). Вместо этого — лимит
попыток верификации **по IP** (`can_attempt_verify`/
`record_verify_attempt`, 20 за 5 минут): у 4 цифр всего 10000 вариантов,
без лимита скрипт успел бы перебрать заметную часть пространства кодов
за время жизни любого чужого ожидающего кода.

**Баг, пойманный на живой проверке сразу после деплоя (не гипотетический
— реальная попытка входа пользователем): "неверный код" при вводе сразу
же после получения.** Первая реализация этого модуля держала
`_PENDING`/`_LAST_REQUESTED` в обычных Python-словарях уровня модуля —
рассуждение было "один процесс `api`, без `--workers`, рестарт — не
страшно". Упущено: код **рождается** в процессе `bot` (`/webcode`,
`src/handlers/f_web_login.py`), а **проверяется** в процессе `api`
(`src/adapters/web_auth.py`) — это два независимых контейнера из
`docker-compose.yml`, у каждого своя память процесса. Ни один код,
сгенерированный в `bot`, физически не мог быть виден словарю в `api` —
"неверный код" был гарантирован при любом вводе, а не только при
задержке. Обнаружено сразу на первом реальном логине после деплоя.

Исправлено переездом на Redis (`settings.redis_url`, уже в стеке — им
пользуется `RedisStorage` бота для FSM, доступен из обоих процессов):
все функции `login_codes.py` стали `async`, ключи `webcode:code:{код}`/
`webcode:cooldown:{user_id}`/`webcode:verify_attempts:{ip}` с `EX`-TTL
вместо ручной проверки `expires_at`. `_get_redis()` — ленивый
module-level singleton, тот же паттерн, что `bot_client.py::get_bot()`.
Заодно нашлась и вторая часть того же бага: вызывающий код в
`f_web_login.py` и `web_auth.py` был написан ПОД старую синхронную
версию — после перевода функций в `async` оба места остались без
`await` (не поймано статикой, `ruff` не проверяет пропущенный `await` у
короутин) — если бы не переписал вызовы, `code = await generate_code(...)`
превратился бы в `code = generate_code(...)` (объект короутины вместо
строки кода) и `if not can_request_code(...)` (объект короутины истинен
всегда — ветка "уже отправлен" никогда бы не сработала, а сама генерация
кода не выполнилась бы, так как короутина не была awaited). Тесты (см.
ниже) переведены на `pytest-anyio`-стиль (`anyio` уже был транзитивной
зависимостью FastAPI, отдельного пакета `pytest-asyncio` ставить не
пришлось) с `FakeRedis`-дублёром в `conftest.py` (шесть методов, ровно
то подмножество Redis API, что использует `login_codes.py` — не тащить
`fakeredis` как отдельную зависимость ради этого).

### Баг: нижняя панель вкладок расширенного экрана не отображалась в браузере, тап по «Расширенная аналитика» не работал

Оба симптома нашлись после того, как вход через `/app/` заработал —
раньше эта часть приложения физически не открывалась вне Telegram
(401 на каждый запрос), поэтому баг не мог проявиться раньше. Сам
пользователь верно поставил диагноз на глаз: "экран кажется больше, чем
есть на самом деле".

**Причина.** Разметка экрана держится на `100vh` (`#screen-stack` —
`200vh`, `.app-screen`/`#extended-screen` — `100vh`, плюс несколько
всплывающих окон/шторок) — статичной CSS-единице, которая в большинстве
мобильных браузеров считается по МАКСИМАЛЬНО возможной высоте вьюпорта
(адресная строка скрыта), а не по тому, что реально видно при первой
отрисовке страницы (адресная строка ещё на экране). Внутри Telegram
WebView это маскировалось — `tg.expand()` плюс собственная подгонка
вьюпорта клиента Telegram убирали разницу, поэтому баг не проявлялся,
пока весь путь до сих пор шёл только через Mini App внутри Telegram.
В обычном мобильном браузере (`/app/`, Phase 45) разница между
"максимально возможным" и "реально видимым" — ровно высота адресной
строки: `#extended-screen` (и весь `#screen-stack` целиком) оказывались
выше реального окна браузера, а `.ext-tabbar` (нижняя панель вкладок,
flex-сосед `.screen-content`, корректно прижатый к низу СВОЕГО
контейнера) вместе с ними уезжала за пределы видимой области — не
из-за собственной верстки, а потому что сам контейнер был выше, чем
казалось.

JS-логика свайпа между экранами (`vh()` → `window.innerHeight`, уже
точное значение) не была связана с этой CSS-константой вообще — отсюда
и вторая часть жалобы: тап/свайп на "Расширенная аналитика" технически
срабатывал (JS использовал верную высоту), но визуально анимация
переезжала не туда, куда в итоге упирался статично-заданный CSS-макет,
поэтому выглядело как "не работает".

**Исправление.** Везде, где раньше был голый `Nvh`, добавлена вторая
декларация того же свойства с `Ndvh` сразу следом (`#screen-stack`,
`.app-screen`, `#extended-screen`, `#side-drawer`, `.list.reorder-window`,
`.bottom-sheet`, `.entity-window`) — `dvh` (dynamic viewport height)
отслеживает реально видимую область сам, без JS, обновляется при
скролле/появлении-исчезновении адресной строки. Браузеры без поддержки
`dvh` просто игнорируют вторую декларацию и остаются на `vh`-фоллбэке
(валидный CSS, не ошибка) — деградация, не поломка. Подтверждено в
dev-харнессе: `getBoundingClientRect().height` `#extended-screen`
теперь точно равен `window.innerHeight` (раньше могло разойтись на
высоту адресной строки браузера — в самом харнессе, без реальной
адресной строки, разница и до фикса была не видна, поэтому баг и не
поймали раньше средствами этой сессии, только живым отчётом
пользователя после первого реального открытия `/app/` в браузере).

## Phase 46 — виджеты аналитики: независимые, переключаемые модули

Продолжение разговора о разбивке `index.html` на модули (см. SPEC.md
§5 п.3, известный техдолг ещё с ранних фаз) — на этот раз с конкретным
поводом: количество графиков аналитики должно стать переменным
(включать/выключать по кнопке), и для этого нужна архитектура, где
каждый график независим от остальных — не только физически в своём
файле, но и не завязан на то, что происходит у соседей.

### Контракт виджета и мост к классическому скрипту

Каждый из 4 существующих виджетов (сферы, график месяца, Гант,
ИИ-текст) вынесен в `src/adapters/miniapp_static/js/widgets/*.js` —
фабрика `createXWidget(ctx)`, возвращающая `{id, mount(container),
unmount(), refresh()}`. Логика внутри каждого — 1:1 перенос из старых
`render*`-функций (включая уже исправленные баги Phase 41: единственное
присваивание `innerHTML`, `dataset.swipeAttached`-защита от
дублирующихся слушателей свайпа).

Остальной `index.html` остаётся классическим скриптом (не переписан
целиком — эта фаза, как и рекомендовано, начинает с одного
самодостаточного куска, не всего файла разом). Виджеты не читают
глобальные переменные классического скрипта напрямую — только то, что
явно передано в `ctx` (`window.__coreBridge` — `api`, `escapeHtml`,
`getMonthNamesFull`/`pad2`/`adjMonth`, `getBoardState`/
`getProjectsData`, `bus`).

**Баг, пойманный сразу на первой живой проверке:** `window.__coreBridge`
изначально клал `monthNamesFull: MONTH_NAMES_FULL` — голым значением,
а не геттером. `const MONTH_NAMES_FULL` объявлена ниже по файлу (в
секции месячного календаря), так что прямое обращение к переменной в
момент конструирования моста упиралось в temporal dead zone
("Cannot access 'MONTH_NAMES_FULL' before initialization"). Исправлено
геттером (`getMonthNamesFull: () => MONTH_NAMES_FULL`) — тот же приём,
что уже был у `getBoardState`/`getProjectsData`: обращение к переменной
откладывается до момента, когда её реально вызовет виджет, а не
происходит сразу при сборке объекта моста.

**Диагностика этого бага заняла заметно больше времени, чем сам фикс**
— стоит отдельно зафиксировать причину на будущее: сообщения об ошибке
в консоли браузера персистентны между `navigate()` в рамках одной
вкладки автоматизации — повторная проверка в ТОЙ ЖЕ вкладке после
правки продолжала показывать старую ошибку. Разобрались только открыв
СВЕЖУЮ вкладку — сообщение исчезло. Разница между "код всё ещё
сломан" и "консоль просто не очистилась" — не всегда очевидна, при
следующей похожей ситуации сразу проверять на чистой вкладке.

### Событийная шина вместо вызова по имени

Раньше `loadProjects`/`createProject` в `index.html` дёргали
`renderGanttChart()` напрямую по имени — прямая связь "код проектов
знает о существовании и внутренностях виджета Ганта". Заменено на
`src/adapters/miniapp_static/js/core/bus.js` (обычный `EventTarget`) —
виджет Ганта сам подписывается на `"projects:changed"`, места мутации
проектов просто публикуют событие через `notifyProjectsChanged()`
(`window.__coreBridge.bus?.dispatchEvent(...)` — опциональная цепочка,
не жёсткий вызов: `bus` подставляется модулем-бутстрапом асинхронно, и
падать из-за временного отсутствия подписчика не должно). Заодно
нашёлся и закрыт соседний пробел: `archiveEntity` для проекта вообще
не обновляла Гант раньше (в отличие от `loadProjects`/`createProject`)
— архивированный проект оставался на диаграмме до перезагрузки
страницы. Теперь все три места мутации проектов используют один и тот
же `notifyProjectsChanged()`.

### Реестр и панель — добавить график в будущем — один файл, одна строка

`js/widgets/registry.js` — единственное место, перечисляющее все
виджеты (`id`, `title`, `defaultEnabled`, `create`). `js/widgets/
panel.js` — монтирует только включённые (per-device выбор в
`localStorage`, тот же паттерн, что `getStoredTheme`/`setTheme` в
`index.html` — чисто визуальное предпочтение устройства, не серверные
данные). Настройка — шестерёнка рядом с заголовком "Аналитика", открывает
`#widget-settings-sheet` (тот же паттерн `.bottom-sheet`, что
`#templates-sheet`/`#project-picker-sheet`, включая `attachSheetOverswipeClose`
и интеграцию с общим `#reorder-scrim`/тап-мимо-закрывает). Если все
виджеты выключены — плейсхолдер с подсказкой, не пустой контейнер.

### Порядок исполнения — синхронный вызов встречает отложенный модуль

`loadAnalytics()` вызывается СИНХРОННО в самом низу классического
скрипта (`loadBoard(); loadDigest(); ...; loadAnalytics();`) — не по
ленивому жесту пользователя, как первоначально предполагалось при
планировании фазы (ошибочное допущение, исправленное при перечитывании
кода до, не после, написания бага). `<script type="module">` по
стандарту откладывается до конца парсинга документа (как `defer`) —
на момент, когда движок доходит до вызова `loadAnalytics()`, модуль
почти наверняка ещё не выполнился. Явный "промис готовности"
(`window.__analyticsPanelReady`, `window.__registerAnalyticsPanel`)
вместо предположения о порядке — корректно работает независимо от
того, что физически выполнится раньше.

### Dev-харнесс — раньше отдавал только один файл

`scripts/miniapp_dev_server.py::do_GET` до этой фазы отвечал только на
`/` и `/index.html` (404 на всё остальное) — этого хватало, пока весь
JS жил внутри `index.html`. Добавлено обслуживание `*.js`/`*.mjs` из
`src/adapters/miniapp_static/` по относительному пути (с проверкой, что
резолвленный путь не вышел за пределы директории) — иначе виджеты не
подгрузились бы в харнессе. Прод (`api.py::app.mount("/miniapp",
StaticFiles(...))`) уже отдавал всё дерево рекурсивно, правок не
потребовал.

### Живая проверка

Свежая вкладка (не переиспользованная — см. диагностику выше): все 4
виджета рендерятся, шестерёнка открывает список с корректными
чекбоксами (проверено через `.checked`, не через сериализацию

## Phase 48 — четыре независимых изменения по списку пользователя

Одним сообщением пришёл список из 4 не связанных друг с другом
изменений — план (`EnterPlanMode`/`ExitPlanMode`, с уточняющими

### 1. Тап по строке задачи переключает статус

Проверка кода перед реализацией показала, что справочный текст
приложения ("тап по тексту задачи — правка, курсор встанет туда, куда
нажал") уже был неверным: и в `renderTaskRow` (инбокс), и в
`renderSwipeableTaskRow` (все остальные списки) у заголовка задачи
намеренно не было обработчика клика — единственное, что переключало
статус, это узкий кружок слева. Правка текста реально работает только
в reorder-режиме (после долгого нажатия), и это не менялось.

Добавлен общий обработчик клика на весь ряд (`row` у `renderTaskRow`,
`content` у `renderSwipeableTaskRow`), переключающий статус — с
исключением по тому же селектору, что уже использовал
`attachReorderEntry` для долгого нажатия (`ROW_TAP_IGNORE_SELECTOR`:
кружок, кнопки, `input`, свайп-зона/шторка) — теперь это общая
константа, используемая в обоих местах, а не два независимых списка
исключений, которые могли бы разойтись. Кружок статуса — единственный
элемент, у которого уже есть свой `onclick`, поэтому он явно в списке
исключений: без этого клик по кружку доходил бы и до него, и до
общего обработчика строки, статус переключался бы дважды подряд
(видимо — как будто ничего не произошло, реальный баг, пойманный при
проектировании, не на живой проверке).

Справочный текст поправлен: строка "Изменить текст" убрана (описывала
несуществующее поведение), "Отметить выполненной" теперь описывает тап
по всей строке; строка "Изменить порядок" расширена упоминанием, что
там же, в reorder-режиме, доступна и правка текста.

### 2. Ревью дня — из Postgres, не пересчитывать

У вечерней рефлексии дневника уже считался текстовый ИИ-саммари
(`summarize_diary`, конец `f4_diary.py::_finish`) и сохранялся в
Notion — но нигде не отображался обратно пользователю. Календарь
показывал только оценки (физ./соц./продукт./счастье) и "особенность
дня", живым запросом к Notion (`list_diary_entries`) на каждый тап по
прошедшему дню.

Новая таблица `day_reviews` (`user_id`, `review_date`, `text`,
`UniqueConstraint` на пару первых) — апсерт из
`src/core/day_reviews.py::save_review`, вызывается прямо в
`f4_diary.py::_finish` сразу после того, как `summary` уже посчитан
(внутри того же `try`, что и запись в Notion — либо весь дневник за
день сохранился, либо нет, две записи не могут разойтись). Чтение —
`get_review(user_id, date)`, добавлено в ответ
`/miniapp/api/diary/{entry_date}` третьим полем `review` рядом с уже
читаемыми из Notion оценками — сам запрос к Notion не тронут, просто
дополнен одним быстрым локальным запросом к своей БД. Фронтенд
(`showDayInfo`) рендерит `entry.review`, если есть, тем же классом
`.ai-summary-text`, что и текст ИИ-аналитики — так пользователь видит
одинаково оформленный "текст от ИИ" в обоих местах приложения.

### 3. Кэш ИИ-аналитики — обновление раз в сутки

`/miniapp/api/analytics/summary` до этой фазы звал Claude
(`analyze_productivity`) на каждое открытие вкладки "Аналитика".
Новая таблица `ai_analytics_cache` — одна строка на пользователя
(`user_id` сразу primary key, тот же приём, что у
`ScreenTime.entry_date`, — не нужен отдельный id ради единственной
актуальной строки). `src/core/ai_analytics.py::refresh_summary`
пересчитывает и апсертит; вызывается новой утренней джобой
(`scheduler/jobs.py::_ai_analytics_refresh_job`, 06:30, для всех
авторизованных пользователей — до `materialize_recurring_tasks`
(07:00) и `morning_digest` (08:00), чтобы кэш был готов к обычному
времени открытия Mini App). Эндпоинт теперь просто читает кэш
(`get_cached_summary`); если строки ещё нет (первый день пользователя,
джоба ещё не отработала) — `refresh_summary` вызывается на месте как
аварийный фолбэк, тем же кодом, что и джоба, не дублируя логику.
Фронтенд (`js/widgets/ai-summary.js`) не менялся вовсе — эндпоинт
остался с тем же URL и той же формой ответа `{text}`, просто стал
дешёвым.

### 4. Несколько сфер у проектов и целей

`Project.sphere`/`Goal.sphere` (одна строка) заменены на
`spheres: list[str]` (`postgresql.ARRAY(String)`, `server_default="{}"`
— тем же путём и для проекта, и для цели, хотя у цели список
по-прежнему не может быть пустым, теперь это проверяется в API-слое,
не на уровне БД). Task.sphere (в задачах — одиночная сфера) в этот
пункт не входит, не тронута.

Миграция — один автогенерированный файл, вручную дополненный
data-миграцией между `add_column`/`drop_column`
(`UPDATE projects SET spheres = ARRAY[sphere] WHERE sphere IS NOT NULL`,
аналогично для `goals`). Автогенерация заодно предложила снять
несколько индексов `ix_*_user_id` на таблицах, которые эта фаза вообще
не трогает структурно (`habits`, `tasks`, `reminders` и др.) —
расхождение моделей и БД, не связанное с Phase 48; эти дропы
осознанно не включены в миграцию, чтобы не смешивать с текущей
задачей (см. комментарий в самом файле миграции).

Бэкенд: `SpheresField`/`RequiredSpheresField` (Annotated + validator,
рядом с уже существующими `SphereField`/`RequiredSphereField` для
Task) — каждый элемент списка проверяется по тому же закрытому набору
`_SPHERES`, что и раньше, `RequiredSpheresField` дополнительно требует
непустой список. Автопривязка задач по сфере при "проанализировать"
(`create_goal_endpoint`, `analyze_goal_endpoint`) берёт первую сферу из
списка цели — задача остаётся с одной сферой, как и раньше. Тот же
приём (взять первую сферу списка) — у группировки Ганта по дорожкам
(`packGanttRows`): проект с несколькими сферами не дублируется на
несколько дорожек, это только визуальная группировка.

Фронтенд: `renderSphereChips` стал многовыборным (принимает массив
выбранных значений и колбэк `onToggle`, а не одно значение и
`onSelect`) — тот же визуальный компонент, что и раньше, просто
несколько чипов теперь может быть активно одновременно. При правке
семантика "поле не передано — не трогать" сохранена (`spheres: null`
в JSON = не тронуто), но теперь дополнена и реально работающей
семантикой "передан пустой массив — очистить": до этой фазы у
проекта была скрытая заглушка того же класса — `sphere: draft.sphere
|| null` превращало снятый выбор в `null`, а не в пустую строку, и
`update_project` молча пропускал такое поле как "не изменилось". С
массивом `[]` — валидное, отличимое от `null` значение, поэтому баг
исчез сам собой вместе со сменой типа поля, без отдельного фикса.

Добавлены `tests/test_spheres_validation.py` — чистые unit-тесты на

## Phase 49 — несколько задач за раз + опциональная ИИ-сфера

Первая из четырёх фаз одного большого запроса пользователя (49-52) —
план с явными функциональными/нефункциональными требованиями
согласован заранее (`EnterPlanMode`/`ExitPlanMode`, история решений —
см. PLAN.md). Реализуются и деплоятся последовательно, каждая — свой
цикл, не один общий коммит (в отличие от Phase 48 — эти фичи крупнее и
меньше связаны друг с другом).

### Несколько задач в одном сообщении

`extract_task_fields` (`src/integrations/claude_client.py`) — раньше
извлекал ровно одну задачу из текста; переименован в
`extract_tasks_fields`, возвращает `list[TaskFields]`. Схема тула

строку `Task` на каждый элемент списка внутри одного `session`/один

сбое, ни одной). Ответ пользователю — одна фраза для единственной
задачи (как раньше, не регрессия), нумерованный список строк для

### Опциональная сфера

`TaskFields`/`_EXTRACT_TASKS_TOOL` получили `sphere` — nullable поле,
ограниченное тем же закрытым списком из 5 сфер, что и везде в проекте
(свой локальный `_SPHERES` в `claude_client.py` — файл принципиально
не зависит от `api.py`/`handlers`, заводить импорт ради 5 строк не за
чем). "Опционально, если уверен" — не числовой порог (Claude tool-use
не отдаёт confidence score), а явная инструкция в описании поля схемы:
"только если уверен, иначе null" — тот же практический приём, что уже
неявно применяется в проекте для похожих мягких ИИ-решений
(`propose_projects_from_goals` — "не выдумывай проект ради галочки").

### Живая проверка

БД в тестовом окружении нет (см. Phase 48 — тот же принцип), проверка
живым вызовом функции напрямую против настоящего Claude API
(`./.venv/Scripts/python.exe -c "..."`, вывод — в файл с явной

`pytest`/`ruff` — чисто (изменения в `claude_client.py`/

## Phase 50 — "Завтра" в карусели главного экрана + настройка отображений

Вторая из четырёх фаз одного большого запроса (49-52).

### Реестр вместо жёстких трёх страниц

Карусель главного экрана (Вчера/Сегодня/Неделя) была статичной
разметкой на 3 страницы — индекс "недели" (`2`), подписи (`_dayLabels`),
точки-индикаторы и стартовая позиция скролла были жёстко зашиты в код.
Теперь единственный источник правды — `DAY_VIEWS` (`index.html`):
`[{id, label, locked}]` на 4 записи (Вчера/Сегодня/Завтра/Неделя,
"Сегодня" — `locked: true`, единственная страница, которую нельзя
выключить). "Завтра" не требует нового backend-эндпоинта: `boardState.
dated_tasks` уже содержит все задачи с датой (тот же источник, что и
`tasksForDate(iso)` для дней месячного календаря) — просто ещё один
вызов `tasksForDate` на день вперёд от `boardState.days.today.date`.

### Страницы живут в скрытом пуле, не пересоздаются

Ключевая техническая находка: `.day-page` теперь не всегда дети
`#day-carousel` — все 4 лежат в скрытом `#day-page-pool`
(`display:none`), `rebuildDayCarousel()` физически ПЕРЕНОСИТ
(`appendChild`) включённые страницы в карусель в порядке реестра, а
выключенные — обратно в пул. Тот же приём, что уже применяет
`applyReorderElevation` для reorder-режима (перенос узла в `<body>` с
comment-плейсхолдером) — здесь решает ту же задачу: любой код, который
где-либо в файле держит `document.getElementById("week-carousel")` и
т.п., продолжает работать одинаково независимо от того, в каком
физически контейнере сейчас лежит страница — `getElementById` находит
узел в любом месте документа, лишь бы узел не был удалён совсем.
Точки-индикаторы (`.day-dot`), в отличие от страниц, ничего не хранят —
их проще каждый раз просто пересоздавать заново (`innerHTML`).

`updateDayLabel()` больше не сравнивает индекс с константой `2` —
сравнивает `currentDayViewIds[index]` со строкой `"week"`; начальная
позиция скролла — `currentDayViewIds.indexOf("today")`, а не жёсткая
`clientWidth * 1`.

"нельзя выключить".

### Живая проверка

Dev-харнесс (`scripts/miniapp_dev_server.py` дополнен задачей на
завтрашнюю дату — `_default_tasks` не содержал ни одной, страницу

## Phase 51 — ИИ-подсказка сферы у проекта/цели

Третья из четырёх фаз одного большого запроса (49-52).

### Общий эндпоинт вместо дублирования

`suggest_entity_spheres(title, description, start_date, end_date)`
(`claude_client.py`) — Haiku, forced tool-use, тот же практический
приём "уверен — заполни, не уверен — пустой список", что и в Phase 49
(`_SUGGEST_SPHERES_TOOL`, до двух сфер за раз). Один HTTP-эндпоинт
`POST /miniapp/api/suggest-spheres` обслуживает и проект, и цель —
поля запроса (название/описание/срок) у обеих сущностей достаточно
похожи, чтобы не заводить два почти одинаковых маршрута; ничего не
пишет в БД, только читает черновик формы (ещё не сохранённую сущность)
и возвращает предложение.

### Триггер — простановка даты, не ввод названия

`maybeSuggestSpheres(kind, draft, start, end)` (`index.html`) вызывается
из колбэков `openDatePicker` — и для дат проекта (начало/конец), и для
опорной даты цели (`referenceDate`) — а не на каждое нажатие клавиши в
поле названия. Два независимых условия молчания: если `draft.spheres.
length` уже не пусто (пользователь выбрал сферу вручную — запрос даже
не уходит, проверка синхронная, до `await`) или название пустое —
функция сразу выходит. Ответ применяется, только если
`createEntityDraft === draft` (форма не успела закрыться/смениться,
пока шёл сетевой поход — сравнение по ссылке на объект черновика,
захваченной в момент вызова) и сфера всё ещё не выбрана вручную к
моменту, когда ответ пришёл (та же проверка, второй раз — гонка между
пользователем, руками кликающим чип, и ответом сети, тоже возможна).
Ошибка/таймаут — тихо ничего не делает, тот же принцип, что и везде в
проекте для необязательных ИИ-подсказок.

У цели, в отличие от проекта, точных `start`/`end` на клиенте нет
(период считает сервер из тира и опорной даты) — подсказка идёт по
одному названию, без диапазона; живой прогон (см. ниже) подтвердил,
что для однозначных случаев этого достаточно.

### Живая проверка

Backend — прямой вызов `suggest_entity_spheres` против реального Claude
API: "Подготовка к марафону" (с описанием и сроком) → `["спорт"]`;
"Уборка гаража" → `[]` (не гадает); "Выучить испанский до разговорного
уровня" → `["развитие"]`; "Ремонт на кухне" (с описанием и сроком) →
`[]` (бытовой проект без явной сферы — тоже валидный, ожидаемый ответ).

Frontend — dev-харнесс с мок-эндпоинтом (`miniapp_dev_server.py`,
сопоставление по ключевому слову в названии — реального Claude тут
нет, но для проверки самого механизма достаточно): простановка даты
начала проекта "Подготовка к марафону" без выбранной сферы подсвечивает
чип "спорт" автоматически; тот же проект, но со сферой "развитие",
выбранной ВРУЧНУЮ до простановки даты — после даты чип остаётся
"развитие", ИИ-подсказка не перезаписывает выбор (и, по логике кода,
даже не запрашивается — синхронная проверка отсекает запрос раньше
`await`). Цель "Выучить испанский язык" — простановка периода
подсвечивает чип "учёба". Консоль браузера — чисто. `pytest`/`ruff` —

## Phase 52 — ревью-экран ИИ-предложенных задач

Последняя, самая крупная из четырёх фаз одного большого запроса
(49-52) — и явно сформулированная пользователем как отдельная фича,
с собственными функциональными/нефункциональными требованиями,
согласованная планом до реализации (см. историю решений в PLAN.md).

### Что убрано

`find_tasks_for_entity`/`_LINK_TASKS_TOOL` (`claude_client.py`),
`_analyze_and_link_project`/`_unlinked_candidate_tasks`/
`analyze_project_endpoint`/`analyze_goal_endpoint` (`api.py`) — вся
прежняя механика "Проанализировать и добавить": она молча ЛИНКОВАЛА
уже существующие задачи без привязки (инбокс/будущее) к только что
созданному проекту/цели по совпадению заголовка, без какого-либо
ревью пользователем. `analyze_project_endpoint`/`analyze_goal_endpoint`
к моменту удаления не вызывались фронтендом вообще (мёртвый код —
проверено `grep` по `index.html` перед удалением). `payload.analyze` в
`CreateProjectRequest`/`CreateGoalRequest` остался в схеме (фронтенд
всё ещё его посылает), но бэкенд больше его не читает — это стало
чисто фронтендным триггером следующего шага.

### Новый механизм — генерация, не линковка, всегда через ревью

`suggest_tasks_for_entity(title, description, spheres, start_date,
end_date)` (`claude_client.py`, Sonnet, тот же паттерн, что
`generate_tasks_from_goals`, но на одну сущность, не список целей) —
придумывает НОВЫЕ задачи под проект/цель, ничего не создаёт сама.
Два новых эндпоинта на сущность (`/projects/{id}/suggest-tasks` +
`/projects/{id}/create-tasks`, симметрично для `/goals/{id}/...`):
первый только предлагает и возвращает список названий, второй
создаёт `Task`-строки на то, что пришло в теле запроса (уже
отфильтрованное и, возможно, переименованное пользователем на
фронтенде) — привязка та же, что раньше делала линковка (`project_id`
для проекта, первая сфера списка — для цели).

### Экран ревью — тот же визуальный язык, что список задач, другая семантика

`closeCreateEntitySheet()` → если `draft.analyze` было включено и
сохранение прошло успешно — плашка-лоадер (`#task-suggest-pill`,
фиксированная в левом верхнем углу, CSS-спиннер) на время
`suggest-tasks`; пустой результат — плашка просто исчезает, окно
ревью не открывается вовсе (не показываем пустой список, как и
оговорено в требованиях). Непустой результат — `#task-review-sheet`
(`.entity-window`, тот же паттерн, что форма проекта/цели и `#help-
sheet`) со своим рендером строк (`renderTaskReviewList`, не общий
`renderList`): слева квадратный чекбокс "добавить"
(`.checkbox-square` — новый CSS-модификатор от круглого `.checkbox`,
та же логика `.selected`, что `.done` у обычного, но другая форма —
намеренно не читается как "отметить выполненной"), тап не зачёркивает
текст (это выбор "создавать или нет", не статус).

Долгое нажатие на список включает урезанный reorder-режим: ручка +
текст целиком + тап-по-тексту-правит, теми же низкоуровневыми
утилитами, что и настоящие задачи (`setupDragReorder`,
`startReorderInlineEdit`), но без кнопки архивации/переноса — этих
действий тут нет, сущностей ещё нет в БД, только черновик в памяти
этого окна (`taskReviewItems`). Тап по фону в режиме правки — выход
обратно к выбору чекбоксами (тот же принцип, что у настоящего
reorder-режима — не закрывает всё окно и не теряет уже собранный
список); тап по фону ВНЕ режима правки — закрывает всё окно,
отбрасывая предложения без сохранения. Кнопка "Готово" внизу окна
(`commitTaskReview`) — берёт только отмеченные строки (с учётом
правок текста и порядка), зовёт `create-tasks`, перечитывает доску
целиком (`loadBoard()` — предложенные задачи уходят в инбокс без
даты, как и у `generate_tasks_from_goals`).

### Живая проверка

Backend — прямой вызов `suggest_tasks_for_entity` против реального
Claude API: "Подготовка к марафону" (со сферой/описанием/сроком) → 8
конкретных, по-настоящему выполнимых задач (план тренировок, проверка
кроссовок, тейпер и т.д. — не общие советы); "Выучить испанский" → 7
задач того же уровня конкретности; заведомая бессмыслица (`"asdkjh
askjdh"`) → пустой список, не выдумывает.

Frontend — dev-харнесс с мок-эндпоинтами (`miniapp_dev_server.py`,
`_mockSuggestedTasks` — детерминированный список из 3 названий,
реального Claude тут нет, но для проверки самого механизма
достаточно) — полный цикл, оба сценария (проект и цель): создание с
включённым тумблером → плашка → окно ревью с 3 отмеченными строками →
снятие галочки с одной → долгое нажатие → режим правки (ручка, без
чекбоксов и кнопок) → тап по тексту → переименование → тап по фону
(выход из правки, состояние сохранено — и снятая галочка, и новое
название) → "Готово" → в инбоксе оказались ровно 2 задачи (отмеченная
и переименованная), с верным `project_id`/`sphere`, третья
(непомеченная) не создана. Отдельно проверен путь отказа — крестик
без "Готово" не создаёт ничего, инбокс не меняется. Консоль браузера
— чисто на всех сценариях. `pytest`/`ruff` — чисто.

## Phase 54 — Project и Goal становятся одной сущностью

Вторая, архитектурная фаза того же запроса. Развилки уточнены заранее:
привязка задачи к цели становится настоящей связью (`Task.project_id`,
как у проекта) вместо прежнего нечёткого совпадения по сфере; диалог
постановки цели в Телеграме (`handlers/f_goals.py`) визуально не
меняется — только адаптация вызовов под новый слой.

### Модель данных и миграция

`Project` (`src/models/project.py`) получил `tier: str | None` —
`None` значит обычный проект, `"weekly"`/`"monthly"`/`"yearly"` —
бывшая цель этого тира. Отдельной таблицы/модели `Goal` больше нет
(`src/models/goal.py` удалён целиком); `Task.project_id` (уже была FK
на `projects.id`) без изменений схемы теперь означает "проект ИЛИ
цель" — ссылка была и остаётся на ту же таблицу. Миграция
(`7d586fa9ceee`) добавляет `projects.tier`, переносит все строки
`goals` в `projects` (`text`→`title`, `period_start/period_end`→
`start_date/end_date`, `description`/`color` — `NULL`, id — новые,
без сохранения старых `goals.id`, т.к. ничто на них не ссылалось) и
удаляет таблицу `goals`.

### `core/goals.py` — тонкий адаптер, не новый слой

Сигнатуры всех публичных функций (`create_goal`, `create_goal_now`,
`update_goal`, `list_goals_for_period`, `list_active_goals`,
`set_goal_done`, `archive_goal`) сохранены как были (только новые
опциональные параметры в хвосте) — `handlers/f_goals.py`,
`core/onboarding.py`, `scheduler/jobs.py` не потребовали ни единой
правки вызова (проверено построчным grep: они читают только именованные
параметры функций и поля `title`/`spheres` возвращаемых словарей, не
`period_start`/`period_end` как ключи). Внутри — тонкие обёртки над
`core/projects.py` с `tier=`. Сериализация цели теперь возвращает те
же имена ключей, что и у проекта — `start_date`/`end_date`/
`description` (не `period_start`/`period_end`, как было в первой
версии этой фазы — см. "Найденный и исправленный баг" ниже) — именно
это позволяет фронтенду обрабатывать обе сущности одним и тем же
кодом без ветвления по `kind`.

`core/projects.py`: `list_projects(user_id)` фильтрует `tier IS NULL`
(экран "Проекты" не показывает бывшие цели); новая

чтение одной сущности (нужна `update_goal` для пересчёта периода из
текущего тира без прямого похода в ORM). `create_project`/
`update_project` получили необязательный `tier` (обычные проекты его
не передают, остаётся `None`). Джойн `task_count`/`done_count` по
`project_id` (уже был у проектов) переиспользован и для целей —
раньше был невозможен без настоящей связи, теперь бесплатный побочный
эффект слияния.

**Авто-простановка дат** ("баг" из исходного запроса): при создании
цели, если `start_date`/`end_date` не переданы явно, вычисляются как
раньше — `GOAL_TIER_BOUNDS[tier](reference_date or today)`; если
переданы — используются как есть, тем же путём, что у проекта. То же
правило при правке, если явно передан только тир/опорная дата без
дат.

### Найденный и исправленный баг (в процессе живой проверки)

не закрывая шторку и не теряя `taskReviewItems`. Изменений не
потребовалось — пользовательский отчёт об этом баге не воспроизвёлся.

### Баг 2 — "Перенести на сегодня" на "Вчера": найдена и исправлена настоящая причина

Синтетические тесты (`.click()`/`dispatchEvent` прямо на кнопке) не
воспроизводили баг — эти методы бьют напрямую в элемент, игнорируя
реальный browser hit-test. Причина нашлась через
`document.elementFromPoint(x, y)` по видимым координатам центра
кнопки: возвращался `SPAN.swipe-zone`, не сама кнопка.

`.swipe-zone` — абсолютно спозиционированная полоса 72px у правого
края строки (единственное место старта свайпа, `touch-action: pan-y`,
без явного `z-index`). Кнопка "на сегодня" в `renderSwipeableTaskRow`
(используется у "Вчера", а с Phase 56 будет использоваться и в новом
окне проекта) — обычный flex-элемент потока, прижатый к правому краю
`.swipe-content` прямо перед `.swipe-handle`/`.swipe-zone` — попадает
ровно в эту 72-пиксельную полосу. Абсолютно спозиционированный
сосед без z-index по умолчанию перекрывает обычный поток-элемент в
той же области: реальный тап по кнопке фактически landing на зону,
которая на короткий тап без движения не делает вообще ничего (свайп
не начинается — `dragging` не становится `true`), так и получалось
"кнопка не работает" без видимой ошибки.

Исправление — новый класс `.move-today-btn` (`position: relative;
z-index: 1;`) на кнопке, поднимающий её над зоной/ручкой в этой
конкретной точке перекрытия. Проверено: `elementFromPoint` по центру
кнопки теперь резолвится в саму кнопку (точнее, в её дочерний SVG,
`closest("button")` от него — сама кнопка); полный реалистичный тап
(pointerdown/mousedown/pointerup/mouseup/click, продиспатченный на
элемент, который реально возвращает `elementFromPoint`, а не
напрямую на кнопку) корректно переносит задачу на сегодня. Свайп-жест
в остальной части зоны (вне кнопки) не пострадал — отдельно проверен
тем же live-тестом (`pointerdown`→`pointermove`→`pointerup` по зоне
выше кнопки открывает `.swipe-actions` на полную ширину, как раньше).

### Живая проверка

Dev-харнесс: длинные названия задач — 2 строки + многоточие без
клиппинга в Инбоксе/Сегодня/Вчера/Завтра, свайп-кнопки по-прежнему по
центру и кликабельны; строки проектов/целей и режим переноса —

## Phase 56 — окно проекта/цели по тапу

Обычный тап (не долгое нажатие) по строке проекта/цели
(`renderEntityRow`) открывает модальное окно 90vw/max-height 80vh с
названием, описанием и полноценным списком задач этой сущности —
добавление, свайп-действия, режим переноса, всё то же самое, что у
любого обычного списка задач, только отфильтрованное по
`project_id`. Крестик закрытия справа сверху, слева от него —
шестерёнка, открывающая уже существующую форму правки ("Изменить
проект"/"Изменить цель") поверх этого окна. Применяется и к
проектам, и к целям — по прецеденту Phase 54, где строка/цвет/архив/
правка уже одинаковы для обеих сущностей.

### Данные — без нового backend-эндпоинта

`tasksForProject(entityId)` (рядом с `tasksForDate`) — фильтр по
уже загруженным `boardState.dated_tasks`/`boardState.inbox` (вместе
покрывают весь не-архивированный набор задач пользователя, см.
`build_task_board`), с дедупом по `id`: просроченная-невыполненная
задача попадает СРАЗУ в оба массива (та же логика на бэкенде и в
`rebucketTask`), без дедупа список задвоился бы.

### Состояние — id, не объект

`projectDetailId`/`projectDetailKind` (не сама сущность) +
`getProjectDetailEntity()` — живой поиск в `projectsData`/`goalsData`
по id при каждом обращении. `editProject`/`editGoal` перезагружают эти
коллекции целиком новыми объектами (не мутируют на месте) — держать
ссылку на entity значило бы обновлять заголовок окна устаревшим
значением сразу после правки через шестерёнку (тот же класс бага, что
уже был исправлен для `weekDetailListEl`, Phase 32). `render()`
дополнительно проверяет, что сущность всё ещё существует — если её
заархивировали, пока окно было открыто, окно закрывается само, а не
показывает сломанное состояние.

### Открытие — тап на `content`, без конфликта с долгим нажатием

`content.addEventListener("click", ...)` в `renderEntityRow`
(исключая `.checkbox`/`.swipe-zone`/`.swipe-handle` — у них свой
смысл тапа) — открывает окно. Долгое нажатие (`attachEntityLongPress`)
по-прежнему сразу ведёт в форму правки без сюда: `render()` внутри
неё пересобирает список раньше, чем нативный `click` успевает
всплыть после отпускания, так что узел `content` уже отсоединён к
этому моменту — гонки нет, подтверждено живой проверкой.

### Список задач в окне — тот же приём, что у недельного дня

`#project-detail-list` — статический узел разметки (не пересоздаётся
динамически, в отличие от `weekDetailListEl`), поэтому
`attachReorderEntry` навешан один раз при загрузке с ДИНАМИЧЕСКИМ
ключом (`() => "project:" + projectDetailKind + ":" + projectDetailId`,
тот же приём, что `"cal:" + selectedWeekDate`) — id/kind окна меняются,
пока сам DOM-узел живёт. `renderProjectDetailSheet()` вызывает обычный
`renderList` с `style: "swipe"` (как у всех "настоящих" списков задач,
не `"plain"` — тот зарезервирован только под Инбокс, Phase 55) и
`showMoveToToday: true`.

Новая задача из окна получает привязку через уже существующий
`POST /tasks/{id}/project` (тот же эндпоинт, что `assignTaskProject`
использует для уже созданных задач) — `createTaskFor` получил
необязательный третий параметр `projectId`, для всех прежних вызовов
не передаётся (обратная совместимость). После успешной привязки —
`loadProjects()`/`loadGoals()` (по `projectDetailKind`), чтобы
`task_count` в строке/окне обновился (это кэшированное на сервере
поле, само не пересчитывается на клиенте).

### Z-index — форма правки поверх окна

`#create-entity-sheet` (форма правки) получила `z-index: 27` (была
26, как и у `.entity-window`) — та же техника, что уже применена к
`#templates-sheet`/`#date-picker-sheet`, которым по той же причине
нужно всплывать над уже открытым окном z-index 26. Ветка в цепочке
кликов по `#reorder-scrim` для `projectDetailId !== null` добавлена
СРАЗУ ПОСЛЕ ветки `createEntityKind !== null` — тап по фону при
открытой форме правки поверх окна проекта закрывает сначала именно
форму (тот же принцип "сначала более вложенное состояние", что и у
`taskReviewOpen && taskReviewEditMode`).

### Найденный попутно баг мок-сервера (не продакшна)

Живая проверка окна цели показала чужую задачу проекта внутри
списка. Причина — `scripts/miniapp_dev_server.py` держал отдельные
счётчики id для проектов (`_nextProjectId`) и целей (`_nextGoalId`),
и дефолтные сиды обеих сущностей использовали одни и те же малые id
(1, 2, 3) — `tasksForProject` фильтрует по голому `entity.id` (без
kind, как и на реальном бэкенде: с Phase 54 проекты и цели — одна
таблица с ОДНИМ сиквенсом, коллизия id в принципе невозможна). Не
баг Phase 56 — расхождение мока с реальной моделью данных, тянувшееся
с Phase 54, просто ничто раньше не фильтровало задачи по голому id
сразу у обеих сущностей. Исправлено — сиды `_default_goals()`
переведены в диапазон `_nextGoalId` (101-103 вместо 1-3), счётчик
сдвинут на 104.

### Живая проверка

Dev-харнесс: тап по строке — окно открывается с верными
названием/описанием/списком задач именно этой сущности (чужие задачи
отсутствуют — отдельно проверено после исправления id-коллизии мока);
долгое нажатие по-прежнему сразу открывает форму правки (регрессии
нет); шестерёнка открывает форму правки поверх окна, правка названия

объект); крестик закрывает окно чисто; добавление задачи через
строку в окне — появляется сразу, сохраняет `project_id`, `task_count`

поведение. Консоль браузера — чисто на всех сценариях.
`pytest`/`ruff check`/`ruff format --check` — чисто (106 тестов;
фаза фронтенд+dev-харнесс-only, бэкенд/API не менялись — эндпоинт
`/tasks/{id}/project` уже существовал).

## 3. Нефункциональные требования

### 3.1 Безопасность

- **Секреты только через `.env`**, никогда не хардкодятся и не
  логируются (`CLAUDE.md`). Каждая новая переменная — сразу в
  `.env.example` (с пустым значением) и `src/core/config.py`.
- **Вебхуки Tasker** проверяются по общему секрету
  (`TASKER_WEBHOOK_SECRET`, заголовок `X-Tasker-Secret`,
  `secrets.compare_digest`, 401 при отсутствии/несовпадении —
  `src/adapters/tasker_webhook.py::_verify_secret`).
- **Mini App API** проверяет подпись Telegram `initData`
  (`src/core/telegram_auth.py::verify_miniapp_init_data`, HMAC по
  алгоритму Telegram) на каждый запрос через
  `get_authorized_user` — плюс ту же проверку авторизации
  (`is_authorized`), что и у бота.
- **Никаких покупок/оплат автоматически** — максимум собрать
  список/ссылку и отдать на подтверждение вручную (жёсткое правило
  из `CLAUDE.md`, не только для агента, но и для самого продукта —
  F9 читает выписки, не совершает платежей).
- Все секреты живут в `.env` на сервере, не в git; `.env.example` —
  единственный источник истины по актуальному списку переменных
  (было решено не дублировать список нигде ещё — расходится с
  реальностью быстрее, чем обновляется).

### 3.2 Надёжность и доступность

- Postgres — единственный источник правды для задач и привычек
  (Phase 10); ни один сценарий их использования не должен зависеть
  от доступности Notion API.
- `RedisStorage` для FSM переживает рестарт контейнера (важно —
  вечерний опрос дневника может идти как раз в момент деплоя); без
  `REDIS_URL` — деградация на `MemoryStorage`, без сохранности между
  рестартами.
- Внешние интеграции (Claude через сторонний прокси, Groq STT,
  Nominatim геокодинг, Open-Meteo погода) — все опциональны в том
  смысле, что их отсутствие/сбой не должен ронять остальные
  сценарии (например, `weather_city=""` — строка погоды просто не
  показывается, не ошибка).
- Автодеплой (`git push` → `master`) применяет
  `alembic upgrade head` перед поднятием контейнеров — миграции
  должны быть написаны так, чтобы не терять данные при апгрейде
  (проверено вживую на всех миграциях этой сессии, каждая
  верифицирована на одноразовом Postgres-контейнере перед
  выкладкой).
- **Явный пробел (осознанный):** нет staging-окружения — каждый
  коммит идёт прямо в прод, проверяется живьём после деплоя. Приемлемо
  для однопользовательского личного проекта, но это осознанный риск,
  а не отсутствие проблемы — см. рекомендацию в §5.

### 3.3 Производительность

- Mini App должен открываться мгновенно — ровно поэтому в Phase 3/10
  задачи и привычки читаются из Postgres, а не идут в Notion при
  каждом открытии.
- Оптимистичный UI everywhere в Mini App: любое действие
  (отметка/дата/приоритет/перенос/правка/архивация) сразу отражается
  в интерфейсе, сетевой запрос подтверждает фоном; при ошибке — откат
  состояния и `alert`. Ни одно действие не должно ждать ответа сети,
  чтобы показать результат.
- Batch вместо N запросов там, где действие естественно массовое —
  `POST /tasks/archive-batch` (один `UPDATE ... WHERE id IN (...)`)
  вместо N `POST /tasks/{id}/archive` при выходе из режима переноса
  с несколькими помеченными задачами.

### 3.4 Совместимость и переносимость

- Целевая среда выполнения Mini App — Telegram WebView (мобильный,
  преимущественно). Не предполагается поддержка произвольных
  десктоп-браузеров как первоклассного сценария, но код не должен
  ломаться в них (деградация допустима).
- `Task.priority == "event"` и связанные с ним UI-условности — не
  отдельная сущность/таблица, а конвенция поверх существующего поля,
  сознательно — см. комментарии в `models/task.py`.
- Python 3.12, полностью async — блокирующих вызовов в event loop
  быть не должно (`CLAUDE.md`).

### 3.5 Сопровождаемость

- Один хендлер = один сценарий (`src/handlers/f*.py`) — не смешивать
  логику разных фич в одном модуле, даже похожих.
- STT и LLM-клиент — всегда за интерфейсом
  (`src/integrations/stt.py`, `claude_client.py`), провайдера можно
  сменить одной строкой конфига.
- Notion-интеграция — адаптивное чтение схемы в рантайме (названия и
  типы свойств пользовательских баз не гарантированно совпадают с
  задуманным), не считается фиксированной.
- Тесты — `pytest`, 65 тестов на сегодня, почти все — чистые функции
  без похода в БД/сеть (сборка текста дайджеста, разбор reminders,
  доска задач и т.п.); несколько (`test_api.py`) — через
  `TestClient` на реальном FastAPI-приложении. Линт/форматирование —
  `ruff`.
- **Явный пробел:** CI (`.github/workflows/deploy.yml`) не запускает
  ни `pytest`, ни `ruff` — деплой идёт по одному факту пуша в
  `master`. Тесты — только локальная дисциплина сессии. См.
  рекомендацию в §5.
- **Явный пробел:** `src/adapters/miniapp_static/index.html` — один
  файл на 2170+ строк (разметка + весь CSS + весь JS инлайном), без
  сборки, без модулей, без автотестов. См. рекомендацию в §5.

### 3.6 Юзабилити

- Bottom-line UX принцип, действующий во всех Mini App правках этой
  сессии: жест должен пережить неидеальное исполнение (палец дрогнул,
  съехал с вертикали, свайпнул резко) — не ломаться, а плавно
  подстраиваться. Несколько раундов фиксов drag&drop в истории
  коммитов — прямое следствие этого требования, не разовая прихоть.
- Кнопки, которые сейчас ничего не сделают (пустое поле ввода,
  архивная кнопка на уже помеченной задаче и т.п.) — визуально
  приглушены, а не просто "работают, но никакого эффекта".

**Процессы (docker-compose):** `bot` (aiogram polling + APScheduler в
одном процессе), `api` (FastAPI/uvicorn — Mini App API и статика,
плюс Tasker-вебхуки), `postgres`, `redis`, `caddy` (reverse proxy,
авто-HTTPS). `bot` и `api` — два независимых процесса из одного
образа, оба напрямую читают/пишут в один Postgres без промежуточного
слоя — единственная точка синхронизации между ними это сама БД.

**Слои в коде** (см. также `CLAUDE.md`):
`adapters/` (входные точки — Telegram, HTTP) → `core/` (роутинг,
конфиг, авторизация, общие утилиты) → `handlers/` (один файл на
сценарий F*) → `integrations/` (внешние API за интерфейсом) →
`models/` (SQLAlchemy) + `scheduler/jobs.py` (cron).

**Данные:** Postgres — единственный источник правды для tasks,
habits, reminders, screen_time, authorized_users, chat_messages.
Notion — только Notes и Diary (осознанно, не мигрировались в Phase
10 — см. `PLAN.md`). Redis — только эфемерное состояние диалогов
(FSM), не хранилище данных приложения.

## 5. Рекомендации по улучшению архитектуры

Отсортировано по соотношению цена/польза для следующих правок — не
всё нужно делать сразу, но каждый пункт основан на реальном трении,
которое уже было в этой сессии, не на абстрактной "лучшей практике".

1. **Добавить тестовый gate в CI.** `deploy.yml` сейчас деплоит по
   факту пуша, не глядя на тесты — единственная защита от поломки
   прода это то, что кто-то (сессия или пользователь) не забыл
   прогнать `pytest`/`ruff` локально. Минимальная правка: отдельный
   job (или шаг перед деплоем в том же workflow) `uv run pytest &&
   uv run ruff check .`, который должен пройти прежде, чем шаг деплоя
   вообще начнётся. Дёшево, устраняет самый очевидный класс риска.

2. **Формализовать тестовый харнесс для Mini App.** ✅ Сделано —
   `scripts/miniapp_dev_server.py`: читает настоящий index.html заново
   на каждый запрос (не статическая копия — не расходится), внедряет
   мок (`window.Telegram.WebApp`, `window.fetch` на in-memory доске,
   `window.__gestures.fire`/`dragGrip` — переиспользуемые хелперы для
   synthetic PointerEvent) перед настоящим telegram-web-app.js. Набор
   задач параметризуется через `--count`/`--tasks`. Запуск:
   `uv run python scripts/miniapp_dev_server.py`.

3. **`index.html` (2170+ строк) стоит разбить**, не обязательно
   вводя bundler — уже достаточно вынести JS в separate `.js` файлы,
   загружаемые через `<script type="module" src="...">`
   (ES-модули поддерживаются нативно любым современным WebView, сборка
   не нужна). Естественные границы уже видны по факту работы этой
   сессии: модуль доски задач (state/render/API), модуль
   drag-reorder (`setupDragReorder`/FLIP-логика — уже сейчас
   самодостаточный кусок), модуль недельной карусели, модуль иконок.
   Даёт: возможность писать unit-тесты на чистые куски логики
   (`dragSiblings`, `commitOrder`, `sortByOrder`) без headless-браузера,
   осмысленные диффы в PR вместо "весь файл заново", и меньше риска
   зацепить чужой код при точечной правке.

4. **`src/adapters/api.py` (290 строк, растёт)** уже сейчас смешивает
