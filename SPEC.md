# Спецификация системы

Формальное описание того, что система делает и каким требованиям должна
соответствовать — снимок текущего состояния, а не хронология. Как и
почему дошли до этого состояния (обсуждения, отвергнутые варианты,
разбивка на фазы) — в [`PLAN.md`](PLAN.md), это по-прежнему источник
истины для истории решений. Здесь эта история не повторяется.

Разработка ведётся через Claude Code-сессии (см. `CLAUDE.md` и
`.claude/skills/assistant-dev-workflow/`) — этот документ в первую
очередь для них: следующая сессия, начиная новую фазу, должна суметь
понять систему целиком по нему, не перечитывая весь git log.

## 1. Обзор

Личный Telegram-ассистент для одного пользователя (с опцией пустить
ещё несколько своих аккаунтов через общий пароль, см. F14) — единая
точка входа для задач, заметок, дневника, напоминаний и нескольких
персональных автоматизаций (финансы, экранное время, привычки).
Взаимодействие — голосом или текстом в Telegram, плюс отдельный Mini
App для визуального управления доской задач. Развёрнут на
собственном VPS, без внешних пользователей и без модели монетизации —
нефункциональные требования соответственно рассчитаны на нагрузку
одного человека, не на масштабирование.

## 2. Функциональные требования

### 2.1 Каналы входа

| Канал | Транспорт | Кто дёргает |
|---|---|---|
| Telegram-бот | aiogram long polling | пользователь, голосом или текстом |
| Tasker webhook | `POST /webhooks/tasker/{screen-time,location}` | MacroDroid на телефоне пользователя, по расписанию |
| Mini App | `GET/POST /miniapp/api/*`, статика на `/miniapp/` | тот же пользователь, из Telegram WebView |

Все три канала сходятся на общее хранилище (Postgres/Redis) и общий
слой авторизации (`src/core/auth.py`) — см. §3.1.

### 2.2 Сценарии (F1–F14)

Полные описания и история решений — в `PLAN.md`, §«Фичи v1». Здесь —
краткая сводка того, что каждый ДОЛЖЕН делать сейчас:

| # | Требование |
|---|---|

| — | Сообщение с намерением "заметка" создаёт страницу в Notion Notes без обращения к Claude |

| F5/F12 | В 8:00 бот присылает одно сообщение: задачи на сегодня + погода + привычки без отметки за сегодня |
| F8 | Привычки хранятся в Postgres со streak; пропущенная дневная привычка порождает вечернее напоминание (20:00) |
| F9 | 1-го числа месяца — напоминание с инструкцией; CSV-выписка Т-Банка, присланная документом, разбирается Claude Sonnet на категории трат |

| F11 | По воскресеньям в 19:00 — сводка недели: выполненные/просроченные задачи, средние оценки и хайлайты дневника, стрики привычек |
| F13 | Напоминание с местом геокодируется (Nominatim); `POST /webhooks/tasker/location` раз в ~5 мин сверяет координаты с сохранёнными точками (радиус 200 м) и присылает сработавшие, одноразово |

**Известный пробел:** F8 (привычки) полностью реализован на бэкенде
(`src/core/habits.py`, `/miniapp/api/habits/*`, вечернее напоминание
о пропуске), но нигде не выставлен пользователю — ни команды в боте,
ни разметки в Mini App (`grep habit src/adapters/miniapp_static/index.html`
— пусто). Отметить привычку выполненной сегодня физически неоткуда,
поэтому вечернее напоминание «не забудь отметить привычки» всегда
будет актуально. Нужно либо доделать UI (вероятно в Mini App, тем же
паттерном, что доска задач), либо явно вычеркнуть F8 из v1.

### 2.3 Mini App — доска задач

Не описано в `PLAN.md` (появилось и много раз менялось уже после
Phase 10 несколькими сессиями подряд) — фиксирую здесь как есть.

**Отображение.** Три экрана в горизонтальной карусели — Вчера /
Сегодня / Календарь (неделя, свайпаемая тройками панелей) — плюс
отдельно Инбокс (задачи без даты или просроченные, свёрнут по
умолчанию). Задача в списке показывает: кружок статуса (галочка если
выполнена; булавка, если это событие и не выполнена; иначе пусто),
заголовок (жирный, если приоритет "высокий" и не выполнена;
зачёркнутый и тусклый, если выполнена), время — только для
событий и только если не полночь.

- **MA-1.** Порядок задач внутри дня — только ручной
  (`Task.sort_order`, float), не пересчитывается автоматически ни по
  приоритету, ни по статусу выполнения. Новая или перенесённая на
  другой день/группу задача получает наибольший на данный момент
  `sort_order` (эквивалент `time.time()`) — то есть уходит в конец.
- **MA-2.** Список Вчера/Сегодня/дня календаря не делится на
  подгруппы "события/обычные" — сортировка единая, событие может
  располагаться между обычными задачами и наоборот.
- **MA-3.** Горизонтальный свайп с правого края строки (72px "зона")
  открывает шторку с 4 действиями: важность (тумблер), событие
  (тумблер, взаимоисключающий с важностью), дата/время, архивировать.
  Доступно только на экранах Вчера/Сегодня/Календарь — не в Инбоксе
  (там вместо шторки — всегда видимые кнопки даты и корзины).
- **MA-4. Режим переноса.** Долгое нажатие (~450 мс) в любом месте
  списка включает режим редактирования для этого списка:
  - весь остальной интерфейс затемняется и размывается
    (`backdrop-filter`) и становится некликабельным; сам список
    рисуется поверх этого слоя;
  - кружок статуса каждой задачи заменяется ручкой-хватом слева;
    текст показывается полностью, без усечения, без жирности/
    зачёркивания;
  - перетаскивание — сразу с касания ручки, слежение за пальцем
    через `document`, а не через саму ручку (не зависит от
    надёжности `setPointerCapture` в Telegram WebView — см. §5);
  - тап по тексту задачи — инлайн-правка с курсором в точке тапа,
    двойной тап выделяет весь текст;
  - у каждой задачи — кнопка отложенного удаления (тускнеет и
    помечается, реально не удаляется);
  - выход из режима — тап где угодно вне списка (по затемнению);
    в этот момент помеченные на удаление задачи архивируются одним
    batch-запросом (`POST /miniapp/api/tasks/archive-batch`).
  - строка добавления новой задачи — часть списка (последняя
    строка), без ручки, не участвует в перетаскивании; перетаскиваемые
    задачи не могут пройти мимо неё.
- **MA-5.** Черновик текста в любом поле добавления задачи (включая
  необязательную дату у Инбокса) переживает пересборку списка —
  `render()` перестраивает все списки на любое действие в
  приложении, черновик не должен теряться от несвязанного события.
  Кнопка подтверждения добавления неактивна и приглушена, пока поле
  пустое.
- **MA-6.** Фокус на поле ввода снимается программно при свайпе
  карусели Вчера/Сегодня/Календарь на другой экран (карусель
  прокручивается нативно, без `render()`, иначе клавиатура и фокус
  остаются висеть на невидимом экране). При возврате на экран
  повторный фокус не выставляется — только сохранённый черновик.
- **MA-7.** Выделение текста везде в приложении запрещено
  (`user-select: none`) кроме активного поля инлайн-правки —
  одновременно и осознанный UX-выбор, и обход ненадёжного поведения
  Telegram WebView, где долгое нажатие без этого перехватывалось
  нативным выделением текста раньше, чем JS видел начало жеста.

**Шаблонные задачи (Phase 18).** Отдельная коллекция (`task_templates`,
не часть доски) — список готовых формулировок для быстрого заполнения
дня, вызывается значком-звездой слева от кнопки добавления задачи на
экранах Вчера/Сегодня/Календарь (не Инбокс). Открывается в bottom
sheet, переиспользующим тот же затемняющий фон, что и MA-4.

- Тап по шаблону в обычном режиме — мгновенно создаёт задачу с тем же
  `due_date`, что предложила бы строка добавления в списке, откуда
  открыли sheet; сам sheet закрывается.
- Тот же режим переноса, что MA-4 (долгое нажатие в sheet), с тем же
  набором действий (drag/inline-edit/отложенное удаление), только без
  кружка статуса/даты — у шаблона их просто нет.
- `stale_after_days` (по умолчанию 14, не редактируется через UI) —
  подсветка едва заметным тёплым тинтом шаблонов, которыми давно не
  пользовались. Таймер считается от `due_date` задачи, созданной из
  шаблона (не от даты нажатия), никогда не показывается числом.
- Раз в неделю (воскресенье, 09:00) `_suggest_templates_job` смотрит
  на заголовки задач за 7 дней и предлагает Claude Haiku 0-3 новых
  шаблона (`source="ai"`), если есть что предложить.
- 8 затравочных шаблонов добавлены миграцией при релизе.

**Проекты (Phase 19).** Своя табличка (`projects`: title, description,
sphere, start_date, end_date, archived), отношение к задачам один ко
многим (`Task.project_id`). Раскрывается собственной свёрнутой по
умолчанию секцией "Проекты" (тот же паттерн, что Инбокс) под доской
задач — карточка показывает сферу (если задана), диапазон дат,
прогресс-бар и счётчик `done/total` по непроигнорированным привязанным
задачам. Создание — инлайн-форма в конце списка (название,
описание, сфера-чипсы, даты). Привязка задачи к проекту — 5-я кнопка
свайп-шторки (после важности/события/даты), открывает bottom sheet
(тот же общий `.bottom-sheet` каркас, что и шаблоны) со списком
проектов + "Без проекта". `Task.sphere` тоже добавлен этой миграцией
(глобальная классификация для будущей аналитики и целей, Phase 20) —
пока выставляется только вручную через `/miniapp/api/tasks/{id}/sphere`
(эндпоинт есть, отдельного UI под него в этой фазе нет).

**Цели (Phase 20).** `goals` (sphere, tier, period_start/end nullable,
text) — 5 тиров: weekly/monthly/quarterly/yearly/5year. Бот сам
инициирует опрос по расписанию: недельные — воскресенье 12:00 (на
предстоящую неделю); месячные — 2 числа 10:00 (текущий месяц);
квартальные — 3 числа 10:00, только в месяцы начала квартала (1/4/7/10);
годовые — 4 числа 10:00, только в январе. Пятилетние — только вручную,
командой `/goals5y` (нет естественной границы периода, которую имело бы
смысл сбрасывать по расписанию). Один общий FSM-опрос
(`src/handlers/f_goals.py`) для всех тиров: инлайн-кнопки 5 сфер (та же
таксономия, что `Task.sphere`/`Project.sphere` — учёба/работа/спорт/
развитие/отношения) + "Готово", по каждой выбранной сфере — один вопрос
свободным текстом, можно повторять по кругу.

- Только weekly и monthly автоматически раскладываются на задачи
  (`generate_tasks_from_goals`, Claude Sonnet, с учётом уже существующих
  задач/активных проектов для дедупликации и авто-привязки
  `project_id`). Задачи создаются **без даты** — уходят в инбокс,
  пользователь сам расставляет их по дням (не ставим дату
  автоматически — ИИ не знает реальной загрузки пользователя на
  конкретный день лучше него самого). Квартальные/годовые/пятилетние —
  только фиксируются для будущей аналитики, задачи из них не создаются
  (явно не просилось в исходных требованиях).
- Только monthly дополнительно предлагает новые проекты
  (`propose_projects_from_goals`, Claude Sonnet) — 0-3 проекта со
  сроками по контексту, только если цель реально тянет на отдельную
  многошаговую инициативу.
- Цели накапливаются (append-only, без апдейта существующих) — повторный
  опрос за тот же период просто добавляет ещё строки; агрегация "самое
  свежее" — на будущей аналитике (Phase 24), в этой фазе Mini App-вьюхи
  под цели нет вообще, только Telegram-опрос + бэкенд.

**Повторяющиеся задачи (Phase 21).** Кнопка "🔁 Повторяющаяся" в главной
клавиатуре бота — свободный текст ("каждый понедельник разгрести
почту"), Claude (переиспользуется `parse_reminder`, та же схема разбора
паттерна, что у напоминалок F13 — `weekly_day`/`monthly_day`/
`interval_days`; `once`/`location` отклоняются с просьбой описать
периодичность) сохраняется как `RecurringTaskRule` (title,
schedule_kind, schedule_value — тот же JSON-паттерн, что `Reminder`).
Никаких задач не создаётся заранее ("миллион записей" из требований) —
ежедневная джоба в 07:00 (до утренней сводки в 08:00) материализует
только сегодняшний occurrence как обычную `Task`-строку для каждого
подходящего под сегодня правила (`last_materialized_date` — защита от
повторной материализации в тот же день, тот же приём, что
`last_fired_date` у напоминалок). Дальше это уже обычная задача — ни
утренняя сводка, ни Mini App не нуждаются в отдельной логике под
повторяющиеся, ровно как и требовалось.

**Ночной разбор инбокса (Phase 22).** `_tidy_inbox_job`, 03:00 (до
материализации повторяющихся в 07:00 и утренней сводки в 08:00) —
берёт текущий Инбокс (та же выборка, что `build_task_board`), одним
batched-вызовом Claude Haiku (`tidy_task_titles`) просит причесать
заголовки (опечатки/лишние слова/невнятность), не меняя смысл.
Обновляет только реально изменившиеся заголовки (`changed=true` и
текст отличается) и присылает сводку "было → стало" в Telegram — тихая
ночь без правок ничего не шлёт.

**Совет по задачам на сегодня (Phase 23).** Отдельным сообщением сразу
после утренней сводки (08:00, тот же `_morning_digest`) — смотрит на
невыполненное со вчера, уже стоящее на сегодня и весь бездатный инбокс,
и с учётом графика 5/2 по 8 часов (Claude Sonnet, `suggest_tasks_for_today`)
предлагает, что из инбокса стоит подтянуть на сегодня, не перегружая
день. Пустой список — нормальный исход, тогда сообщение не шлётся.
Кнопки "Добавить"/"Не сегодня" под сообщением; выбранные id хранятся в
FSM-данных (не в `callback_data` — список id может не влезть в лимит
Telegram), по "Добавить" — выставляет `due_date` на сегодня выбранным
задачам.

**Аналитика (Phase 24).** Новая секция внизу доски — свайпаемая
карусель из 4 страниц (тот же native scroll-snap паттерн, что у
карусели Вчера/Сегодня/Календарь, контролируемо продублирован под
своими классами `.analytics-*` — см. комментарий в коде, риск трогать
уже отлаженную `.day-carousel` не стоил общего компонента). Все данные
читаются один раз при загрузке, вне обычного optimistic-UI `render()`-
цикла (только для чтения).

1. **Тортик по сферам** (`GET /miniapp/api/analytics/spheres`) — SVG-
   donut (stroke-dasharray, без внешних библиотек) + легенда с
   процентами. Считает все неархивированные задачи со сферой,
   независимо от статуса "готово".
2. **График месяца** (`GET /miniapp/api/analytics/month`) — bar-chart
   выполненных задач по дням текущего месяца + компактный список
   "по проектам" (суммарно за месяц) под ним — не отдельный
   полноценный график наложением, а текстовая разбивка ради простоты.
3. **Гант по проектам** — переиспользует уже загруженные `projectsData`
   (тот же `GET /miniapp/api/projects`, что раздел "Проекты", отдельный
   эндпоинт не заводили), горизонтальные полосы по `start_date`/
   `end_date`, с оверлеем прогресса (`done_count`/`task_count`) внутри
   полосы. Проекты без обеих дат в гант не попадают.
4. **ИИ-аналитика** (`GET /miniapp/api/analytics/summary`) — Claude
   Sonnet (`analyze_productivity`), обычный текст (не forced tool-use)
   по агрегатам выше: 2-3 наблюдения, что хорошо/что настораживает.
   Считается заново при каждом открытии Mini App (кэша нет — личный
   низкочастотный трафик, цена пересчёта признана приемлемой).

**Кнопка меню чата.** `MINIAPP_URL` (`.env`) → `bot.set_chat_menu_button`
при старте (`telegram_bot.py::main`) — заменяет иконку "/" рядом с
полем ввода на прямой запуск боевого `/miniapp/`, виден сразу в строке
чата в списке чатов, без `/start` и без похода в меню команд. Пусто =
кнопку не трогаем, в лог — предупреждение.

**Главный и расширенный экран (Phase 25).** Доска разделена на два
полноэкранных `.app-screen` внутри `#screen-stack` — главный (карусель
Вчера/Сегодня/Календарь, Инбокс, утренний дайджест) и расширенный
(Проекты, Аналитика — временно перенесены как есть; полноценный
переключатель целей/проектов в стиле задач — следующий инкремент).
`body`/`html` больше не скроллятся сами — скроллится конкретный видимый
`.app-screen`, тело всегда `overflow:hidden`. Сам `.app-screen` тоже

Полоска-переключатель (`.bottom-pill-wrap`) — **последний обычный
элемент внутри `.screen-content`** ("привязана к полотну", не к
экрану/вьюпорту — уточнено в Phase 27): 100vh в Telegram WebView не
всегда совпадает с реально видимой областью (шапка/жесты/полноэкранный
режим), поэтому вариант "прижать к нижнему краю вьюпорта" (`position`
вне потока скролла) на практике оказывался не там, где на самом деле
кончается видимый контент. Простой элемент в конце потока — надёжнее,
всегда сразу после последнего реального блока контента.

- Переход — свайп вверх снизу текущего экрана (тонкая плоская "галочка"

  активации (70px пальцем, не доля высоты экрана), с отставанием от
  пальца по расстоянию (коэффициент 0.55, не по времени/анимации).
  Держание ~0.5с — вибро (`HapticFeedback.impactOccurred`). Зона старта
  жеста (весь `.bottom-pill-wrap`, `pointerdown`) заметно выше самой
  видимой полоски (`padding-top: 30px`, фон совпадает с фоном экрана —
  зона не видна, полоска визуально не растёт), чтобы свайп
  подхватывался, даже если палец стартует не точно на тонкой "галочке".
- Оба перехода — **одним и тем же направлением** (вверх), не парой
  вверх/вниз: `#main-screen` физически всегда в слоте 0, `#extended-screen`

  после доезда мгновенно (без transition) возвращается в слот 0 — тот

  карусели, только переставляется позиция экрана, а не данные внутри
  него (DOM с обработчиками/id не дублируется).
- Тап по подписи — запасной способ переключиться без свайпа.

**Месячный календарь — переработка, тиры целей (Phase 27).**

- **Свайп между месяцами** — активная зона: вся сетка + надпись месяца
  (`#month-cal-swipe-zone` оборачивает `.month-cal-nav`+`.month-cal-grid`).
  Направление жеста (гор./верт.) определяется по первому заметному сдвигу
  (`touch-action: pan-y`, обычный вертикальный скролл экрана не задет);
  порог 40px — тот же класс "стандартный свайп", что и остальные
  пороговые жесты приложения. Кнопки ‹/› остаются как запасной способ.
- **Нет пустых плиток** — ведущие/хвостовые ячейки сетки заполняются
  реальными числами соседних месяцев (`.other-month`, приглушены), тап
  по такой плитке переключает календарь на этот месяц и сразу выделяет
  день. Первое число текущего месяца — нейтрально-красная обводка
  (`--neutral-red`, обводка, не заливка — чтобы не читалось как
  предупреждение), помогает отличить границу месяца среди чужих чисел
  вокруг.
- **Сегодня/выбран** — та же логика, что у `.week-cell` недельного
  календаря: сегодня — лёгкая заливка акцентом
  (`color-mix(... var(--accent) 18% ...)`), выбран — обводка акцентом;
  оба комбинируются на одной плитке естественно (общий `--accent`).
- **Первая строка** чуть выше остальных (`aspect-ratio: 1/1.32`) —
  вмещает подпись дня недели сверху (как `.wc-label` в недельном
  календаре), отдельной строки-шапки под это не заводим, экономим
  высоту: подпись есть только там, где не повторяется на следующих
  строках.
- **Выходные** — число дня подсвечено приглушённым красным
  (`--neutral-red`), тем же нейтральным тоном, что обводка первого
  числа месяца (разные позиции/семантика — обводка vs заливка текста —
  читаются по-разному, несмотря на общий оттенок).
- **Индикатор "как прошёл день" внутри плитки** — максимум один значок
  на плитку: для сегодня/будущего с задачей-событием — иконка геометки
  (переиспользован существующий `eventPinIcon()`, тот же, что уже
  использовался для чекбоксов событийных задач — не новая метафора для
  приложения); для прошлого с заполненной вечерней рефлексией —
  цветной кружок по среднему баллу `physical`/`social`/`productivity`/
  `happiness` (шкала 1-3, см. `handlers/f4_diary.py`): зелёный ≥2.34,
  жёлтый 1.67-2.33, приглушённо-красный <1.67. Паттерн вдохновлён
  привычными mood-календарями (Daylio и подобные) — один цвет на день,
  без текста, читается с одного взгляда по всему месяцу сразу; дни без
  заполненной рефлексии — просто без кружка, не зашумляем сетку.
  Бэкенд: `core/calendar_view.py::month_diary_moods` (переиспользует
  `list_diary_entries`, тот же маленький датасет без серверной
  фильтрации, что и у `/diary/{date}`), эндпоинт
  `GET /miniapp/api/calendar/month-moods?month=YYYY-MM`.
- **Тап по дню** — сразу докручивает экран так, чтобы надпись месяца
  оказалась вверху видимой области (`scrollIntoView({block:"start"})`
  на секции календаря) — иначе после открытия панели информации о дне
  снизу заголовок мог уйти выше видимой части.
- **Порядок секций расширенного экрана** — графики (Аналитика) теперь
  первыми, затем календарь (+ кнопки создания проекта/цели сразу под
  ним), затем переключатель Проекты/Цели — раньше переключатель шёл
  первым.
- **Тиры целей сокращены до трёх** — `weekly`/`monthly`/`yearly`.
  `quarterly` и `5year` убраны целиком: функция периода `quarter_bounds`
  и тир `quarterly` из `GOAL_TIER_BOUNDS` (`core/goals.py`), крон-джоба
  квартального опроса (`scheduler/jobs.py`), команда `/goals5y` и её
  хендлер (`handlers/f_goals.py`), пункты меню бота
  (`adapters/telegram_bot.py`), страницы/точки переключателя и лейблы
  в Mini App. Старые цели этих тиров в БД не трогали (осознанный выбор
  при подтверждении) — остаются в базе, но недоступны через UI ни в
  боте, ни в Mini App.

28).** Отдельные кнопки "+ Проект"/"+ Цель" под календарём убраны —

открывает уже существующую форму `#create-entity-sheet`, предзаполненную
введённым текстом (и, для цели, тиром той страницы, с которой открыли).

- **Создание = закрытие шторки.** Явной кнопки "Отмена" нет — тап по
  затемнённому фону, свайп вниз (`attachSheetOverswipeClose`, уже был) и
  кнопка "Готово" ведут в одну и ту же `closeCreateEntitySheet()`,
  которая сначала пытается сохранить черновик (`commitEntityForm`),
  потом уже закрывает. Без названия (или без сферы у цели — единственное
  по-настоящему обязательное поле после названия) — просто ничего не
  сохраняется, без алертов: блокирующий `alert` несовместим с закрытием
  свайпом. Цвет проекта — не поле «обязательное для заполнения»: если не
  выбран, при создании назначается случайный из `PROJECT_COLORS`.
- **"Не дозаполнено" — красная подсветка плитки.** Только у проектов
  (реально несколько независимо-необязательных полей — описание, сфера,
  даты); `isEntityIncomplete` — `true`, если не хватает хотя бы одного
  из description/sphere/start_date/end_date. Тонкая красная линия снизу
  плитки (`inset box-shadow`, не меняет высоту строки), не бейдж/число —
  ненавязчиво, замечаешь, только если приглядеться, ровно как и
  задумано. У целей сфера обязательна уже на создании — подсвечивать
  особо нечего.
- **Правка — долгое нажатие по строке** (`attachEntityLongPress`, тот же
  таймер/порог сдвига, что у остальных long-press жестов приложения) —
  открывает ту же форму, предзаполненную текущими значениями,
  `createEntityEditingId` вместо `null`. Правка вызывает
  `POST .../edit` (для целей — новый эндпоинт, для проектов уже
  существовал) вместо `POST` создания; ни при каком редактировании поля
  проекта/цели уже привязанные к нему задачи не трогаются — эндпоинты
  правки меняют только сам проект/цель. Известное ограничение: `null` в
  теле `.../edit` значит "не менять", не "очистить" — конкретное поле,
  однажды заполненное, через эту форму пустым не сделать (можно только
  заменить на другое значение); для создания эта проблема не актуальна.
- **Всплывающий календарь** (`#date-picker-sheet`) — общий для дат
  проекта (начало/конец) и опорной даты периода цели, вместо нативного
  `input[type=date]`: компактная карточка по центру экрана поверх формы
  (не ещё один `.bottom-sheet` той же высоты — перекрывали бы друг
  друга), сетка в той же визуальной логике, что у месячного календаря
  (`.month-cal-day`/`.month-cal-grid`). Кнопка "Не указывать" — явный
  сброс к пустому значению.
- **Опорная дата периода цели** — сервер считает `week_bounds`/
  `month_bounds`/`year_bounds` не всегда от сегодня, а от даты, выбранной
  в этом календаре (`reference_date` в запросе), поэтому можно поставить
  недельную цель на неделю через неделю, месячную — на любой будущий
  (или прошлый) месяц; без выбора — прежнее поведение (от сегодня).
  Правка цели пересчитывает период заново, если поменялся тир и/или
  опорная дата — период не редактируется как отдельное поле, это
  производная величина (см. `core/goals.py::update_goal`).

**Критический баг: режим переноса задач визуально не поднимался над
затемнением (Phase 29).** `#screen-stack` — `position: fixed`, а такой
элемент per спецификации CSS безусловно создаёт собственный stacking
context (независимо от z-index/transform). Из-за этого
`.reorder-active-list` (z-index 26) внутри него не мог подняться выше
`.reorder-scrim` (z-index 25, сам тоже `position: fixed`, но СНАРУЖИ
`#screen-stack`) — список навсегда заперт в контексте предка, будь у
него хоть z-index 9999. Баг тихо появился в Phase 25 вместе со
`#screen-stack` и не был замечен раньше. Единственный настоящий выход —
физически вынести DOM-узел списка за пределы `#screen-stack` на время
режима переноса (`applyReorderElevation` в `renderList`): сохраняет
`getBoundingClientRect()`, вставляет comment-маркер на его место,
переносит узел в `<body>` с `position: fixed` и теми же координатами, а
при выходе — возвращает обратно по маркеру. `templates-list` эта
проблема не касалась — он живёт в `#templates-sheet`, который сам уже
верхнеуровневый `position: fixed` сосед `.reorder-scrim`, а не потомок
`#screen-stack`.

**Баг: переход между главным/расширенным экраном показывал прошлую
прокрутку (Phase 29).** `.screen-content` каждого экрана скроллится
независимо и не сбрасывался при переключении — после скролла вниз на
расширенном экране и возврата свайпом был виден низ, а не верх.
`attachScreenTransition` теперь сбрасывает `scrollTop` целевого экрана
в момент, когда становится ясно, что переключение состоится
(`resetTargetScroll`) — и в свайпе, и в тап-фолбэке (`toggleScreen`).

**Круговой свайп аналитики — мигание на обычном свайпе (Phase 33,
продолжение Phase 32).** Снятия `scroll-snap-type` на время прыжка
оказалось недостаточно на быстром/обычном свайпе — нативный
momentum-скролл к моменту телепорта ещё реально доигрывал анимацию, а
JS-присвоение `scrollLeft` его не останавливает (только "спорит" за

способ оборвать недоигранный momentum (скролл физически невозможен,
доигрывать нечего), затем `overflow-x` возвращается. Не проверено на
реальном фликовом свайпе (синтетические `PointerEvent` не создают
настоящей momentum-физики) — логика корректности (индекс/точки)
перепроверена, визуальный эффект от momentum-конфликта нужно
подтвердить на устройстве.

**Месячный календарь — многодневные события скрывались усечением

эта строка сама по себе всегда короче плитки, суффикс-до-обрезки
структурно не может возникнуть. Для дня с одним событием подпись
осталась как раньше — заголовок события.

**Экран "Помощь" (Phase 37).** За 36 фаз в приложении накопилось много

код, который тоже пришлось бы держать в синхроне с UI на каждой фазе —
то же самое обслуживание, что у скриншотов, только дороже.

один раз при загрузке (не зависит от данных). У жестов, которые

дело было только в заливке "сегодня". Поправлено на точно ту же смесь,
что у `.week-cell.today` (`color-mix(in srgb, var(--accent) 18%,

**Шторка шаблонов поверх окна переноса — само окно оставалось чётким

`#templates-sheet` стал корректно всплывать НАД окном переноса, само
окно переноса за шторкой оставалось полностью резким и активным — по

шаблонов не размывает сам себя.

**Автоочистка чата — молча забывала неудалённые сообщения (Phase 38).**
Разбор жалобы "не работает": `_cleanup_old_messages`
(`src/scheduler/jobs.py`) удаляла строку из `chat_messages` СРАЗУ после
`bot.delete_message`, независимо от того, удалилось ли сообщение в
Telegram на самом деле — `except TelegramBadRequest: pass` глотал любую
ошибку (не только "уже удалено", но и, например, временный сбой сети),
а лог рапортовал `len(old_messages)` — количество КАНДИДАТОВ, не
реально удалённых, так что даже полный провал ночи выглядел в логах как
успех. Данные на проде (336 сообщений, накопленных за не более суток)
подтвердили: сам джоб исправно запускается и обычно чистит успешно —
но при любом единичном сбое сообщение терялось из вида навсегда, без
повторной попытки. Исправлено: строка удаляется из БД только если
`bot.delete_message` реально прошёл, либо если Telegram явно ответил
"нечего удалять/нельзя" — тогда, если сообщение ещё не старше 47 часов
(за 48 часов Telegram сам запрещает удаление, дальше пытаться уже
бессмысленно), строка остаётся на повторную попытку следующей ночью.
Лог теперь пишет `удалено N из M` — реальную, а не оптимистичную
цифру.

**Команда /timezone — часовой пояс и место по геопозиции (Phase 39).**
Раньше часовой пояс (`settings.timezone`) и город для погоды
(`settings.weather_city`) были статичными значениями из `.env` —
поменять можно было только правкой конфига и рестартом. Новая команда
`/timezone` присылает кнопку "📍 Отправить геопозицию"
(`request_location=True`), по полученным координатам:

- `resolve_timezone(lat, lon)` — IANA-имя зоны через тот же провайдер,
  что уже используют цели/аналитика для погоды (Open-Meteo,
  `forecast?timezone=auto` сам резолвит зону по координатам — не
  понадобилась ни отдельная библиотека, ни второй внешний сервис);
- `reverse_geocode_label(lat, lon)` — человекочитаемая подпись
  ("Санкт-Петербург, Россия") через Nominatim reverse, только для
  подтверждающего сообщения, ни на что в логике не влияет.

Оба — новые функции в `src/integrations/geocoding.py`, рядом с
существующим `geocode` (используется гео-напоминаниями, F13).

Результат сохраняется в `authorized_users` (новые нулабельные колонки
`latitude`/`longitude`/`timezone`/`location_label`, миграция
`f1a2b4c6d8e0`) — таблица уже была per-Telegram-user (см. F14, механизм
пароля), просто раньше не хранила ничего, кроме факта авторизации.
Схема уже многопользовательская, но **до полноценной
многопользовательской авторизации (см. TECHDEBT.md) реально влияет на
приложение только запись основного владельца**
(`settings.telegram_user_id`) — остальные авторизованные по паролю
могут сохранить свою геопозицию командой уже сейчас (задел на будущее),
но расписание планировщика и погода бота на неё пока не смотрят; ответ
бота честно об этом предупреждает, а не притворяется, что сработало
полностью.

Когда меняет владелец — эффект применяется сразу, без рестарта
процесса:
- `settings.timezone` (обычный, не frozen, pydantic-объект) мутируется
  прямо в хендлере — все последующие `ZoneInfo(settings.timezone)` по
  всему bot-процессу подхватывают новое значение немедленно, без правок
  в каждом месте использования.
- Планировщик — сложнее: `CronTrigger` без явного `timezone=` резолвит
  зону ОДИН РАЗ в момент создания триггера (не держит живую ссылку на
  `scheduler.timezone`), так что просто поменять
  `scheduler.timezone` задним числом ничего не даёт. `setup_scheduler`
  переписан на декларативный список джобов (`_job_specs`, единый
  источник правды — раньше расписание было только внутри
  `setup_scheduler`, теперь ещё используется `reschedule_for_timezone`,
  которая для каждого джоба вызывает `scheduler.reschedule_job(id,
  trigger=CronTrigger(..., timezone=new_tz))`); каждому джобу присвоен
  стабильный явный `id` — раньше не было, был не нужен, теперь
  необходим, чтобы reschedule_job понимал, какой именно джоб трогать.
- `src/core/user_location.py::apply_stored_timezone()` — вызывается на
  старте и bot-, и api-процесса (`FastAPI`-`lifespan`, не устаревший
  `on_event("startup")`), подтягивает то, что уже сохранено в БД,
  поверх дефолта из `.env`. Bot и api — разные процессы с разной
  памятью, у каждого свой `settings`; если `/timezone` сработала без
  последующего деплоя — api-процесс увидит новое значение только после
  своего следующего рестарта (в этом проекте деплой перезапускает оба
  контейнера сразу, так что расхождение живёт недолго).
- Погода (`src/integrations/weather.py::get_weather_summary`) —
  сохранённые координаты владельца теперь приоритетнее
  `settings.weather_city`: точнее (конкретная точка, а не центр города
  по имени) и не нужен лишний geocoding-запрос на каждый вызов
  дайджеста. Без сохранённой геопозиции — прежнее поведение
  (`weather_city` → Open-Meteo geocoding → forecast) не тронуто.

**Ревизия безопасности (Phase 39, по прямому запросу).** Прошлись по
приложению целенаправленно на инъекции и типовые базовые атаки — не
переписывание "для красоты" (расплывчатое "оптимизируй код, нужна
гибкая красивая система" без конкретики оставлено как есть, не наврежу
догадками; если нужен код-ревью/рефакторинг — это отдельная,
самостоятельная задача, не часть этой правки).

- **SQL-инъекции — не обнаружены.** Весь проект систематически ходит в
  БД через SQLAlchemy ORM/query builder (параметризованные запросы), ни
  одного `execute(f"...")`/ручной подстановки значений в SQL-строку не
  нашлось (проверено `grep` по всему `src/`).
- **Хранимый XSS в Mini App — найден и закрыт.** Большинство мест и так
  рендерят пользовательский текст (заголовки задач/проектов/целей)
  безопасно, через `.textContent` (браузер экранирует сам). Но там, где
  разметка собирается одним HTML-блоком через шаблонную строку
  (график "по проектам" в аналитике месяца, гант, легенда сфер, ИИ-
  текст, ревью дня из дневника) — заголовки/текст подставлялись в
  `innerHTML` НЕ экранированными: заголовок проекта вроде
  `<img src=x onerror=...>` выполнился бы прямо в интерфейсе. Заведён
  общий `escapeHtml(str)` (index.html, рядом с `icon()`) — через
  `textContent` временного `<div>`, тот же принцип, что уже
  подразумевали безопасные места, просто явно; применён во всех
  найденных местах. Раньше в одном месте (ИИ-текст) было временное
  `replace(/</g, "&lt;")` — неполное (не экранировало `&`/`>`/кавычки)
  — заменено на общий helper.
- **`sphere` — принимался API без проверки, теперь валидируется.**
  Фронтенд предлагает `sphere` только как закрытый список кнопок
  (`SPHERES` в index.html), но само API (`CreateProjectRequest`,
  `SetTaskSphereRequest`, `EditProjectRequest`, `CreateGoalRequest`,
  `EditGoalRequest`) принимало в этом поле любую строку — прямой запрос
  с валидной подписью initData мог записать в БД что угодно, включая
  HTML/скрипт (который до предыдущего пункта ещё и рендерился бы без
  экранирования — двойная дыра на одной и той же точке входа). Добавлен
  `SphereField`/`RequiredSphereField` (`Annotated[str | None,
  AfterValidator(_validate_sphere)]`) — Pydantic отклоняет запрос
  (422) до того, как значение вообще попадёт в код эндпоинта. Экранирование
  вывода (пункт выше) всё равно остаётся первой линией защиты — эта
  проверка не даёт мусору попасть в БД вообще, а не только не даёт ему
  отрендериться.
- **Сравнение пароля бота — не постоянное время, поправлено.**
  `handle_password_attempt` (`src/handlers/f_auth.py`) сравнивало
  введённый пароль с ожидаемым обычным `!=` — теоретическая утечка по
  времени ответа (чем раньше несовпадение, тем быстрее ответ). Заменено
  на `secrets.compare_digest`, тот же приём, что уже используют секрет
  вебхуков Tasker (`_verify_secret`) и HMAC-проверка `initData`
  Mini App (`verify_miniapp_init_data`, оба были и остаются корректны —
  проверено отдельно, менять было нечего).
- **Проверено и подтверждено корректным, без изменений:**
  `verify_miniapp_init_data` (`src/core/telegram_auth.py`) — валидный
  HMAC-SHA256 по официальному алгоритму Telegram, `hmac.compare_digest`,
  проверка свежести `auth_date`; вебхуки Tasker
  (`src/adapters/tasker_webhook.py::_verify_secret`) — секрет через
  заголовок, `secrets.compare_digest`, 401 при отсутствии/несовпадении.
- **Найдено, не тронуто (не относится к безопасности):**
  `settings.notion_webhook_secret` объявлен в `config.py`, но нигде не
  используется — вебхука от Notion в коде нет (возможно, был
  запланирован и не реализован, либо убран без чистки конфига). Не
  критично и не риск (нечего эксплуатировать без самого эндпоинта), но
  стоит иметь в виду при следующей уборке конфигурации.

## Phase 40 — многопользовательская авторизация

Самая крупная архитектурная работа за всю историю проекта — обсуждена и
согласована с пользователем заранее (два открытых вопроса — судьба
дневника/заметок и посуточность расписания — заданы явно, ответы ниже),
реализована целиком за одну фазу. До этой фазы `AuthorizedUser`/
`is_authorized` (F14) были только пароль-гейтом: кто угодно, кто знает
пароль ("это читинец", не изменился), получал доступ к боту, но все
авторизованные видели и правили ОДИН общий набор данных, а расписание
всегда слало сообщения только основному владельцу
(`settings.telegram_user_id`). Теперь у каждого авторизованного —
свои задачи/привычки/проекты/цели/напоминалки/шаблоны/повторяющиеся
задачи и своё персональное расписание.

### Данные

`user_id: BigInteger` (FK → `authorized_users.telegram_user_id`) —
добавлен на `tasks`/`habits`/`projects`/`goals`/`reminders`/
`task_templates`/`recurring_task_rules` одной миграцией
(`a7c3e9f1b2d4`). Существующие строки бэкофиллены владельцем — ничего
не потерялось, просто стало явно "моим". Миграция сама гарантирует
строку владельца в `authorized_users` перед бэкофиллом (`INSERT ...
ON CONFLICT DO NOTHING`) — раньше `is_authorized` пускала его в обход
этой таблицы (см. ниже), строки там могло не быть вовсе, а без неё FK
не встал бы. Отдельная миграция (`b8d4f2a6c1e3`) переводит
`chat_messages` на составной первичный ключ `(chat_id, message_id)` —
`message_id` уникален только внутри одного чата, не глобально; с
несколькими чатами (несколько пользователей) старый PK рисковал
столкновением между разными людьми. Обе миграции проверены
upgrade+downgrade+повторный upgrade на временном Postgres, плюс полный
прогон всей цепочки миграций с нуля.

Каждая репозиторная функция (`src/core/projects.py`, `goals.py`,
`habits.py`, `task_templates.py`, `recurring_tasks.py`, `analytics.py`,
`calendar_view.py`) и каждый эндпоинт `api.py` теперь принимает/
фильтрует по `user_id` первым параметром. Точечные мутации по id
(`archive_project`, `set_goal_done` и т.д.) — не просто
`session.get(Model, id)`, а `_get_owned(session, id, user_id)`:
запись, принадлежащая другому пользователю, отвечает тем же
`ValueError`/404, что и несуществующая — угаданный/подсмотренный
чужой id не даёт ни доступа, ни даже подтверждения, что что-то по
такому id вообще существует. Batch-операции (`archive_templates_batch`,
`/tasks/archive-batch`) — `user_id` прямо в SQL `WHERE`, не только
`id.in_(ids)`, той же причины ради. Проверено сценарием: владелец не
может архивировать проект другого авторизованного пользователя даже
зная его id (см. живой прогон ниже).

### Личность пользователя — откуда берётся `user_id`

- **Mini App API** — `get_authorized_user` уже резолвил личность из
  подписанного `initData` и раньше (HMAC-SHA256, см. Phase 39), просто
  возвращаемый `user["id"]` до этой фазы никуда не прокидывался
  дальше `_: dict = Depends(...)`. Никакой новой инфраструктуры не
  понадобилось — только реально начать использовать то, что уже было.
- **Бот** — `message.from_user.id`/`callback.from_user.id` напрямую в
  каждом хендлере, который раньше слал/писал от имени
  `settings.telegram_user_id`.
- **Планировщик** — свой контекст, нет входящего сообщения; `user_id`
  приходит как аргумент джобы (см. ниже).

### Планировщик — свои джобы у каждого

Обсуждён и подтверждён явно: расписание учитывает часовой пояс каждого
пользователя индивидуально (не общее время для всех). `setup_scheduler`
стал `async` — на старте перебирает `list_authorized_user_ids()` и
регистрирует персональный набор джобов на каждого через
`register_jobs_for_user`. `_job_specs(bot, storage, user_id, tz_name)`
— единый источник правды расписания (было и в Phase 39, теперь
дополнительно параметризован пользователем и его зоной); каждый job id
включает `user_id` (`f"morning_digest:{user_id}"`) — раньше на имя
джобы был один экземпляр на всё приложение, теперь по одному на
пользователя, id должны быть уникальны в рамках `AsyncIOScheduler`.

Три джобы — `screen_time_digest`, `finance_reminder`, `evening_diary`
— регистрируются **только для владельца**, не для каждого: они
завязаны на что-то физически единственное (конкретный телефон с
MacroDroid, конкретный банк/выписка, Notion-дневник одного воркспейса)
— не "ещё не доделано", осознанное ограничение (см. TECHDEBT.md).

Новый пользователь получает свои джобы СРАЗУ при вводе пароля
(`register_jobs_for_user` в `f_auth.py`), без рестарта процесса — та
же логика, что уже делает `/timezone` (Phase 39) для пересборки
триггеров. `/timezone` тоже стала полностью многопользовательской:
`reschedule_for_timezone` теперь принимает `user_id` и пересобирает
триггеры ТОЛЬКО его личных джобов — раньше эффективно работала только
для владельца, для остальных честно отвечала "сохранил, но не
влияет"; теперь влияет на каждого одинаково. `settings.timezone`
(глобальная мутация, см. Phase 39) остаётся только как дефолт для
владельца и для мест, ещё не ставших per-user — `user_timezone(user_id)`/
`user_today(user_id)` (новые хелперы, `src/core/user_location.py`) —
основной способ узнать "чей сейчас день" где угодно в коде.

### Онбординг

`src/core/onboarding.py::seed_onboarding_data(user_id, today)` —
вызывается сразу после успешного пароля для НОВОГО пользователя
(проверка "не является ли повторным вводом пароля уже авторизованным"
— не пересоздаёт затравку и джобы заново при, например, зависшем
FSM-состоянии). Создаёт: один шаблон ("Разобрать почту"), один
пробный проект, одну пробную цель (тир weekly, сфера "развитие"), две
задачи — одна привязана к проекту (`project_id`), другая — к цели
(через совпадение `sphere`, тот же принцип связи "задача относится к
цели", что и везде в приложении — отдельного `goal_id` у задачи нет).
Дальше — приветственное сообщение с рекомендацией заглянуть в
«Помощь» (Phase 37) для знакомства с жестами.

### Дневник и заметки — осознанно остаются только у владельца

Явный вопрос пользователю, явный ответ: дневник и заметки живут в
Notion, привязанном к ОДНОМУ конкретному воркспейсу/токену, не к
Telegram-пользователю — интегрировать туда несколько независимых
людей нет разумного способа без полной миграции с Notion на Postgres
(отдельная, самостоятельная задача, не часть этой фазы). Пока —
честно "не готово", не тихая пустота:
- Mini App: `api.py::_is_owner`/`_NOT_READY_FOR_OTHERS` — дневник
  (`GET /diary/{date}`) отвечает 403 с понятным текстом для не-владельца;
  индикатор настроения в месячном календаре (`month-moods`) — просто
  пустая карта (плитки не подсвечиваются, без ошибки).
- Бот: `f_notes.py::handle_note` — то же сообщение для не-владельца
  ДО похода в Notion. `f4_diary.py` (вечерний опрос) не тронут вообще
  — просто не регистрируется джобой ни для кого, кроме владельца (см.
  выше), поэтому и трогать нечего.
- Планировщик: `f11_weekly_review.py::build_weekly_review` — раздел
  дневника в итогах недели пустой для не-владельца (`is_owner`
  проверка перед походом в Notion), раздел задач/привычек — как у всех.

Гео-напоминания (`f_reminders.py::check_location_reminders`) — та же
логика, что экранное время: вебхук от Tasker/MacroDroid привязан к
ОДНОМУ конкретному физическому телефону, не абстрактному "текущему
пользователю" — фильтр по `Reminder.user_id == settings.telegram_user_id`
прямо в самой функции, а не через регистрацию джобы (это не джоба
планировщика — вебхук, дёргается извне).

### Побочные находки по дороге

- **Владелец должен быть реальной строкой в `authorized_users`.**
  `_is_primary_owner`/обход БД в `is_authorized` — сохранён (устойчивость
  входа к временно недоступному Postgres), но данные теперь ссылаются
  на эту таблицу по FK, так что `ensure_owner_authorized()` (новое,
  `core/auth.py`) вызывается на старте bot- и api-процессов, гарантируя
  строку идемпотентно.
- **`ChatMessage` PK был потенциальной дырой на многопользовательность**
  (см. миграцию `b8d4f2a6c1e3` выше) — найдено при проектировании
  per-user автоочистки чата, не было бы обнаружено без явной
  многопользовательской работы.
- **Погода стала per-user** (`weather.py::get_weather_summary(user_id)`)
  — естественное следствие того, что `/timezone` (Phase 39) уже хранила
  геопозицию по `user_id`, просто раньше только владельца это
  использовало.
- **Frontend (Mini App) не потребовал ни единой правки** — вся
  многопользовательская логика на сервере, `initData` уже нёс личность
  пользователя с самого начала (Phase 29), фронтенду прозрачно, чьи
  данные он показывает.

### Живой прогон (перед деплоем, на временном Postgres)

Полная цепочка миграций с нуля; `ensure_owner_authorized` + `setup_scheduler`
на пустой БД → 14 джобов (11 общих + 3 владельца). Симуляция нового
пользователя: вставка строки в `authorized_users`, `seed_onboarding_data`,
повторный `setup_scheduler` → 25 джобов всего, 14 у владельца, 11 у
нового пользователя (без владельческих трёх) — id пересчитаны верно.
Проверка изоляции: `list_projects(new_user_id)` не видит проектов
владельца и наоборот; попытка `archive_project(чужой_project_id, owner_id)`
корректно отклонена `ValueError` вместо тихого успеха.

### 2.4 Безопасность и доступ (функционально)

- Бот отвечает только пользователю из `TELEGRAM_USER_ID` либо
  сохранённому в `authorized_users` (см. F14); остальным — вежливый
  отказ без раскрытия функциональности.
- Оба вебхука от Tasker (`/screen-time`, `/location`) и Mini App API
  требуют собственной проверки перед обработкой payload (см. §3.1).

## 3. Нефункциональные требования

### 3.1 Безопасность

- **Секреты только через `.env`**, никогда не хардкодятся и не
  логируются (`CLAUDE.md`). Каждая новая переменная — сразу в
  `.env.example` (с пустым значением) и `src/core/config.py`.
- **Вебхуки Tasker** проверяются по общему секрету
  (`TASKER_WEBHOOK_SECRET`, заголовок `X-Tasker-Secret`,
  `secrets.compare_digest`, 401 при отсутствии/несовпадении —
  `src/adapters/tasker_webhook.py::_verify_secret`).
- **Mini App API** проверяет подпись Telegram `initData`
  (`src/core/telegram_auth.py::verify_miniapp_init_data`, HMAC по
  алгоритму Telegram) на каждый запрос через
  `get_authorized_user` — плюс ту же проверку авторизации
  (`is_authorized`), что и у бота.
- **Никаких покупок/оплат автоматически** — максимум собрать
  список/ссылку и отдать на подтверждение вручную (жёсткое правило
  из `CLAUDE.md`, не только для агента, но и для самого продукта —
  F9 читает выписки, не совершает платежей).
- Все секреты живут в `.env` на сервере, не в git; `.env.example` —
  единственный источник истины по актуальному списку переменных
  (было решено не дублировать список нигде ещё — расходится с
  реальностью быстрее, чем обновляется).

### 3.2 Надёжность и доступность

- Postgres — единственный источник правды для задач и привычек
  (Phase 10); ни один сценарий их использования не должен зависеть
  от доступности Notion API.
- `RedisStorage` для FSM переживает рестарт контейнера (важно —
  вечерний опрос дневника может идти как раз в момент деплоя); без
  `REDIS_URL` — деградация на `MemoryStorage`, без сохранности между
  рестартами.
- Внешние интеграции (Claude через сторонний прокси, Groq STT,
  Nominatim геокодинг, Open-Meteo погода) — все опциональны в том
  смысле, что их отсутствие/сбой не должен ронять остальные
  сценарии (например, `weather_city=""` — строка погоды просто не
  показывается, не ошибка).
- Автодеплой (`git push` → `master`) применяет
  `alembic upgrade head` перед поднятием контейнеров — миграции
  должны быть написаны так, чтобы не терять данные при апгрейде
  (проверено вживую на всех миграциях этой сессии, каждая
  верифицирована на одноразовом Postgres-контейнере перед
  выкладкой).
- **Явный пробел (осознанный):** нет staging-окружения — каждый
  коммит идёт прямо в прод, проверяется живьём после деплоя. Приемлемо
  для однопользовательского личного проекта, но это осознанный риск,
  а не отсутствие проблемы — см. рекомендацию в §5.

### 3.3 Производительность

- Mini App должен открываться мгновенно — ровно поэтому в Phase 3/10
  задачи и привычки читаются из Postgres, а не идут в Notion при
  каждом открытии.
- Оптимистичный UI everywhere в Mini App: любое действие
  (отметка/дата/приоритет/перенос/правка/архивация) сразу отражается
  в интерфейсе, сетевой запрос подтверждает фоном; при ошибке — откат
  состояния и `alert`. Ни одно действие не должно ждать ответа сети,
  чтобы показать результат.
- Batch вместо N запросов там, где действие естественно массовое —
  `POST /tasks/archive-batch` (один `UPDATE ... WHERE id IN (...)`)
  вместо N `POST /tasks/{id}/archive` при выходе из режима переноса
  с несколькими помеченными задачами.

### 3.4 Совместимость и переносимость

- Целевая среда выполнения Mini App — Telegram WebView (мобильный,
  преимущественно). Не предполагается поддержка произвольных
  десктоп-браузеров как первоклассного сценария, но код не должен
  ломаться в них (деградация допустима).
- `Task.priority == "event"` и связанные с ним UI-условности — не
  отдельная сущность/таблица, а конвенция поверх существующего поля,
  сознательно — см. комментарии в `models/task.py`.
- Python 3.12, полностью async — блокирующих вызовов в event loop
  быть не должно (`CLAUDE.md`).

### 3.5 Сопровождаемость

- Один хендлер = один сценарий (`src/handlers/f*.py`) — не смешивать
  логику разных фич в одном модуле, даже похожих.
- STT и LLM-клиент — всегда за интерфейсом
  (`src/integrations/stt.py`, `claude_client.py`), провайдера можно
  сменить одной строкой конфига.
- Notion-интеграция — адаптивное чтение схемы в рантайме (названия и
  типы свойств пользовательских баз не гарантированно совпадают с
  задуманным), не считается фиксированной.
- Тесты — `pytest`, 65 тестов на сегодня, почти все — чистые функции
  без похода в БД/сеть (сборка текста дайджеста, разбор reminders,
  доска задач и т.п.); несколько (`test_api.py`) — через
  `TestClient` на реальном FastAPI-приложении. Линт/форматирование —
  `ruff`.
- **Явный пробел:** CI (`.github/workflows/deploy.yml`) не запускает
  ни `pytest`, ни `ruff` — деплой идёт по одному факту пуша в
  `master`. Тесты — только локальная дисциплина сессии. См.
  рекомендацию в §5.
- **Явный пробел:** `src/adapters/miniapp_static/index.html` — один
  файл на 2170+ строк (разметка + весь CSS + весь JS инлайном), без
  сборки, без модулей, без автотестов. См. рекомендацию в §5.

### 3.6 Юзабилити

- Bottom-line UX принцип, действующий во всех Mini App правках этой
  сессии: жест должен пережить неидеальное исполнение (палец дрогнул,
  съехал с вертикали, свайпнул резко) — не ломаться, а плавно
  подстраиваться. Несколько раундов фиксов drag&drop в истории
  коммитов — прямое следствие этого требования, не разовая прихоть.
- Кнопки, которые сейчас ничего не сделают (пустое поле ввода,
  архивная кнопка на уже помеченной задаче и т.п.) — визуально
  приглушены, а не просто "работают, но никакого эффекта".

```
                              │  Postgres (tasks, habits,      │
                              │  reminders, screen_time,       │
                              │  authorized_users,              │
                              │  chat_messages)                │
                              │  + Notion (Notes, Diary only)  │
                              └───────────────────────────────┘
                                              ▲
                     ┌────────────────────────┼────────────────────────┐
                     │                        │                        │
              ┌──────────────┐       ┌──────────────────┐    ┌──────────────────┐

```

**Процессы (docker-compose):** `bot` (aiogram polling + APScheduler в
одном процессе), `api` (FastAPI/uvicorn — Mini App API и статика,
плюс Tasker-вебхуки), `postgres`, `redis`, `caddy` (reverse proxy,
авто-HTTPS). `bot` и `api` — два независимых процесса из одного
образа, оба напрямую читают/пишут в один Postgres без промежуточного
слоя — единственная точка синхронизации между ними это сама БД.

**Слои в коде** (см. также `CLAUDE.md`):
`adapters/` (входные точки — Telegram, HTTP) → `core/` (роутинг,
конфиг, авторизация, общие утилиты) → `handlers/` (один файл на
сценарий F*) → `integrations/` (внешние API за интерфейсом) →
`models/` (SQLAlchemy) + `scheduler/jobs.py` (cron).

**Данные:** Postgres — единственный источник правды для tasks,
habits, reminders, screen_time, authorized_users, chat_messages.
Notion — только Notes и Diary (осознанно, не мигрировались в Phase
10 — см. `PLAN.md`). Redis — только эфемерное состояние диалогов
(FSM), не хранилище данных приложения.

## 5. Рекомендации по улучшению архитектуры

Отсортировано по соотношению цена/польза для следующих правок — не
всё нужно делать сразу, но каждый пункт основан на реальном трении,
которое уже было в этой сессии, не на абстрактной "лучшей практике".

1. **Добавить тестовый gate в CI.** `deploy.yml` сейчас деплоит по
   факту пуша, не глядя на тесты — единственная защита от поломки
   прода это то, что кто-то (сессия или пользователь) не забыл
   прогнать `pytest`/`ruff` локально. Минимальная правка: отдельный
   job (или шаг перед деплоем в том же workflow) `uv run pytest &&
   uv run ruff check .`, который должен пройти прежде, чем шаг деплоя
   вообще начнётся. Дёшево, устраняет самый очевидный класс риска.

2. **Формализовать тестовый харнесс для Mini App.** ✅ Сделано —
   `scripts/miniapp_dev_server.py`: читает настоящий index.html заново
   на каждый запрос (не статическая копия — не расходится), внедряет
   мок (`window.Telegram.WebApp`, `window.fetch` на in-memory доске,
   `window.__gestures.fire`/`dragGrip` — переиспользуемые хелперы для
   synthetic PointerEvent) перед настоящим telegram-web-app.js. Набор
   задач параметризуется через `--count`/`--tasks`. Запуск:
   `uv run python scripts/miniapp_dev_server.py`.

3. **`index.html` (2170+ строк) стоит разбить**, не обязательно
   вводя bundler — уже достаточно вынести JS в separate `.js` файлы,
   загружаемые через `<script type="module" src="...">`
   (ES-модули поддерживаются нативно любым современным WebView, сборка
   не нужна). Естественные границы уже видны по факту работы этой
   сессии: модуль доски задач (state/render/API), модуль
   drag-reorder (`setupDragReorder`/FLIP-логика — уже сейчас
   самодостаточный кусок), модуль недельной карусели, модуль иконок.
   Даёт: возможность писать unit-тесты на чистые куски логики
   (`dragSiblings`, `commitOrder`, `sortByOrder`) без headless-браузера,
   осмысленные диффы в PR вместо "весь файл заново", и меньше риска
   зацепить чужой код при точечной правке.

4. **`src/adapters/api.py` (290 строк, растёт)** уже сейчас смешивает
